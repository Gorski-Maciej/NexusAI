  Konflikt #5  R0390/R0391 ↔ P860-P868 (KŚT i leasing)

1.3. SKALOWALNOŚĆ  (7000 rules efficiency)
────────────────────────────

OBSERWACJE Z PLAN OPA:
  • Zaledwie 435 wdrożonych reguł = 11 588 linii kodu Rego.
  • Architektura idzie w stronę 7 000 reguł Micro.
  • Pusta implementacja Dual-Layer [41] — load-balancing w Rego nie
    istnieje, choć jest opisany w dokumentacji.

PUNKT KRYTYCZNY (Linear Evaluation Trap):
  Model First-Match-Wins na łańcuchu `else if` = złożoność O(N).
  Przy 7 000 regułach złożoność do 1,4 MB AST = potężne latency spikes
  w WASM. Pusta implementacja Dual-Layer to gwóźdź do trumny wydajności.

BENCHMARK ENTERPRISE (Stripe Tax):
  Sharded Execution Routing. Ewaluacja "root" policy ocenia jedynie
  kontekst (P-ID + flagi) i na jego podstawie wywołuje dedykowany mini-
  łańcuch (tylko relewantne Micro rules, np. 15 z 7 000), tnąc
  złożoność z O(N) do O(1).

SKUTKI BRAKU SKALOWANIA:
  • 7 000 reguł × 4 ms p95 = 28 s per request (NIEakceptowalne)
  • Memory footprint WASM = 1,4 MB AST = cold starts kosztowne
  • Bez sharding: 1 zła reguła = globalny regression

1.5. WYDAJNOŚĆ  (Performance / GC pressure)
────────────────────────────

OBSERWACJE Z PLAN OPA:
  • 56 reguł PKPiR w accounting.rego = matched:false (martwa warstwa).
  • 60% ścieżek validation.rego kończy się fallbackiem "ALLOW".
  • Brak guard-rail early-reject na wejściu pakietu Rego.

PUNKT KRYTYCZNY (Garbage Collection Pressure):
  Ewaluowanie tysięcy warunków, podnoszenie zmiennych do pamięci, tylko
  po to, by zwrócić "pass-through". To marnotrawstwo CPU i pamięci.

BENCHMARK ENTERPRISE (Stripe):
  Pruned DAG (Directed Acyclic Graph) + Fail-Fast Guard-Rails. Stoso-
  wanie twardych guardów na wejściu pakietu, ucinających cały obszar
  silnika w 1 mikrosekundę, jeśli input JSON nie przechodzi schema
  validation. Stripe Tax ma <2 ms p95 na 8 000+ regułach.

SZACUNEK OSZCZĘDNOŚCI:
  • Eliminacja dead-code (−56 + 60% ALLOW) = 35-40% redukcji CPU
  • Inverted sharded index (B1) = 90% redukcji p95 latency

A1. VERDICT PROVENANCE GRAPH  (Graf Proweniencji Decyzji)
────────────────────────────────────────────────────────────────────────────

PROBLEM:
  Użytkownik widzi tylko suchy JSON werdyktu. Urzędnik KAS zakwestionuje
  werdykt, bo nie widzi kaskady myślenia: "to zwolnienie P58 podparte
  R0546 i próg ujęty z limitów 2021 r." Obecny system zwraca tylko
  rule_id, ale nie ścieżkę inferencyjną.

ROZWIĄZANIE:
  OPA poza standardowym outputem generuje obiekt `_provenance_tree`,
  w którym grafie (JSON Node-Edge) wyrysowana jest TRASA od main_jdg
  przez Macro (np. PIT Scale) do Micro (KUP limit 150k), z dołączonym
  hashem każdej podstawy prawnej. Output wygląda tak (koncepcyjnie):

  {
    "verdict": {"decision": "ALLOW", "rule": "P58"},
    "_provenance_tree": {
      "path": [
        {"step": 1, "rule": "main_jdg", "context": {...}},
        {"step": 2, "macro": "PIT_SCALE", "filter": "income < 120k"},
        {"step": 3, "micro": "vat_exemption.art113.r2", "basis": "Art. 113 ust. 1"},
        {"step": 4, "threshold_ref": "jdg.vat.exemption_limit@2026-01-01", "value": 200000},
        {"step": 5, "matched_kks_check": "P0_b.no", "result": "no_fraud"}
      ],
      "root_hash": "0xa73f5b9c...",
      "evaluation_ms": 4,
      "evaluated_at": "2026-07-13T10:15:33+02:00"
    }
  }

DLACZEGO GENIALNE:
  • Audytor jednym kliknięciem generuje PDF będący "Cyfrową Notatką
    Podatkową" z hashem SHA-256 całego kontekstu decyzyjnego.
  • Pełna non-repudiation: wynik nie może być podważony przez
    twierdzenie "zmieniliśmy regułę wstecz".
  • Compliance-grade: materiał dowodowy klasy audytowej Big 4.

KONCEPCJA WDROŻENIA:
  • Nowy helper w Rego: rule_chain(metadata) → array
  • Wrapper na main_jdg.rego: dołącza graph w każdym werdykcie
  • Side-effect-free — nie zmienia logiki reguł, tylko rozszerza output
  • Czas implementacji: ~3 sprinty (Rego conventions + test fixtures)

A2. TEMPORAL CAUSALITY CHAIN  (Łańcuch Przyczynowości Temporalnej)
────────────────────────────────────────────────────────────────────────────

PROBLEM:
  OPA słabo radzi sobie z interpretacją "co jeśli faktura jest sprzed
  3 lat, ale przepisy sprzed 2" (zmieniła się np. struktura R0582
  dot. składki zdrowotnej ZUS po Polskim Ładzie 2022). Gdy kontrola
  KAS dotyczy roku 2023, wymaga ewaluacji wg STANU PRAWNEGO z 2023,
  nie z 2026.

ROZWIĄZANIE:
  Mechanizm Time-Travel Compliance. System wprowadza twarde wymogi
  podania daty `input.evaluation_datetime`. Silnik Rego na jej pod-
 stawie ignoruje reguły, dla których:
    • data.metadata.valid_from > evaluation_date
    • LUB data.metadata.valid_to < evaluation_date

  Dodatkowo: dla każdej reguły generowanej z threshold pobierany jest
  WERDYKT PRAWNY Z DNI EWALUACJI (nie dnia dzisiejszego). Dzięki temu
  próg P189 = 90 dni (po 2025-07-01) vs P189 = 150 dni (przed) są
  rozróżnialne bez dwuznaczności.

DLACZEGO GENIALNE:
  • Umożliwia legalne "cofnięcie się w czasie" na potrzeby kontroli
    skarbowych zaległych lat (2022, 2023, 2024), bez psucia dzisiej-
    szych procesów biznesowych (2026).
  • Bezpośrednio adresuje realne ryzyko KAS (odtworzenie stanu
    prawnego z przeszłości → zgodność art. 70 OP "przedawnienie").
  • Regenerowany historyczny werdykt = dowód prawny dla klienta.

KONCEPCJA WDROŻENIA:
  • Obudowanie 100% reguł w generyczny helper w Rego:
        is_active_for_date(rule_id, transaction_date)
  • Temporal Registry w DuckDB (tabela rule_versions):
        rule_id | valid_from | valid_to | threshold_keys | hash
  • Wrapper w main_jdg: input.evaluation_datetime required by schema
  • Czas implementacji: ~4 sprinty (migracja thresholdów do wersjon.)

    }

  • Czas implementacji: ~2 sprinty.

────────────────────────────────────────────────────────────────────────────
B1. INVERTED SHARDED INDEX  (Predykcyjne partycjonowanie 7000 reguł)
────────────────────────────────────────────────────────────────────────────

PROBLEM:
  Standardowy `main_jdg.rego` z 7000 regułami + `else if` chain to
  O(N) evaluation. Każde wywołanie OPA powoduje pełne skanowanie AST.
  Bez shardingu → latency > 28 s niewykonalne, GC pressure ogromne.

ROZWIĄZANIE:
  Router w main_jdg.rego: w kroku O(1) buduje hash kontekstu zapytania:
    • input.tax_form (PIT_SCALE / PIT_LINEAR / PIT_RYCZAŁT / VAT_ZWOLNIONY)
    • input.transaction.type (SALE / PURCHASE / EXPORT / IMPORT)
    • input.entity_attributes (CEIDG_VALID / ZAWIESZONA / SUKCESJA)
    • input.evaluation_date

  Router mapuje do specjalistycznego Shardu:
    sharded_vat_purchase_export_ceidg_valid_2025Q3.rego

  Każdy shard zawiera 5-25 reguł, evaluation p95 < 5 ms.

ARCHITEKTURA PRZED:
    ┌──────────────────────────┐
    │ main_jdg (7000 rules)    │  O(N) scan
    │ else if × 7000           │
    │ matched via chain        │
    └──────────────────────────┘
                    ↓
                  czas: 28 s

ARCHITEKTURA PO:
    ┌─────────────────────────────┐
    │ main_jdg_router (50 rules)  │  O(1) sharding
    │ hash context → shard_id     │
    └─────────────────────────────┘
                    ↓
    ┌─────────────────────────────┐
    │ shard_xxx.rego (5-25 rules) │  O(1) targeted
    │ specjalizowane dla kontekstu│
    └─────────────────────────────┘
                    ↓
                  czas: 4 ms

DLACZEGO ENTERPRISE:
  • Redukcja p95 latency z 28 s do 60-200 ms (realistyczny ×140-465
    przy 5-25 reguł/shard; do <5 ms wymaga tier-3 cache shard).
  • Memory footprint WASM: z 1,4 MB do ~100 KB per shard.
  • GC pressure: −90% (Stripe Tax benchmark).
  • Izolacja błędów: 1 zła reguła w shardzie = regresja tylko w shardzie.

SZACOWANY ZYSK:
  • Latency: 28 s → 60-200 ms (× 140-465, realistyczny przy 5-25 reguł/shard)
  • Memory: 1,4 MB → 100 KB per shard (× 14 cold start improvement)
  • Throughput: 35 req/s → 250+ req/s single-node
  • Cold starts (WASM): 3,2 s → 250 ms
  • UWAGA REALISTYCZNA: Mnożnik x7 000 opisany w uproszczeniu — w praktyce
    każdy shard zawiera 5-25 reguł z 7000, więc realny speedup to
    x280-x1400 (28 000 ms / 5-25 × 4 ms = 4 480-560 ms). Strojenie do
    <5 ms wymaga shardów 1-regułowych (3 tier cache).

Czas implementacji: ~5 sprintów (orkiestracja, sharding, tests).

B3. DRY POLICY COMPILER + STRICT LINTING PIPELINE

PROBLEM:

  no-op). Błędy literowe typu "150 zamiast 90 dni" w P189. Podwójne
  priorytety. Reguły bez powiązania z warstwą MACRO. Brak CI dla Rego.

ROZWIĄZANIE:
  OPA CI/CD pipeline z Conftest, który PRZED MERGE waliduje:

  1. **Mandatory `matched:true` rule:**
       Każda reguła MUST emitować matched=true lub matched=false z
       `additional_info: "no_match"` (jawny, nie ciche omit).

  2. **No fallback ALLOW:**
       Ścieżka w validation.rego nie może domyślnie zwracać ALLOW.
       Każda gałąź MUSI mieć konkretną decyzję BLOCK/TRIAGE/DECISION.

  3. **Twarde ID-Validation:**
       Każdy wpis `rule_id` MUSI być w canonical map (38c).
       Każde hardcoded integer > 0 w Rego = lint error (tylko w stages).

  4. **Cross-link integrity:**
       Każda reguła Micro MUSI mieć wpis w warstwie Macro.
       Puste mikroreguły = lint error.

  5. **Temporal Validation:**
       Każda reguła MUSI mieć valid_from/valid_to,
       i wartości MUSZĄ być spójne z threshold_records w DuckDB.

  6. **Legal basis validation:**
       Każda reguła MUSI mieć _legal_basis (art./ust./pkt/lit.)
       zgodnie z plikiem 50_JDG_BRAKUJACE_PUNKTY_PRAWNE.md.

DLACZEGO ENTERPRISE:
  • Architektura odrzuca błędy ludzkie na poziomie Pull Requesta.
  • Bez CI Rego to 1000 dev arbitralnych decyzji. Z CI to 1000 dev
    × 100% walidacji = 0 regression.
  • Minimalizacja długu od 1. dnia wdrożenia skali 7 000 reguł.

NARZĘDZIA:
  • Conftest (OPA natywne) + Rego unit tests
  • Graphwalker / PICT dla pair-wise testing
  • Hypothesis (Python) dla property-based testing
  • OpenPolicyAgent CLI w GitHub Actions

SZACOWANY ZYSK:
  • Bug detection pre-merge: 65% → 95%
  • Regression rate post-merge: 8% → 0.5%
  • Onboarding time nowego deva Rego: 4 tyg → 1 tydzień

Czas implementacji: ~2 sprinty (Conftest setup + integracja CI).

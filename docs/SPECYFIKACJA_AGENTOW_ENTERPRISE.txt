1.1. Filozofia architektury
---------------------------

System agentów AI w NexusAI został zaprojektowany jako AUTONOMICZNE BIURO
KSIĘGOWE — zestaw wyspecjalizowanych agentów AI, które:

  a) DZIAŁAJĄ W TLE — użytkownik nie musi wiedzieć, który agent przetwarza
     jego fakturę. System działa jak niewidzialny księgowy.

  b) PODEJMUJĄ DECYZJE — w zielonej strefie (Trust Score ≥ 0.92) agenci
     samodzielnie księgują faktury, wysyłają do KSeF, planują płatności.

  c) UCZĄ SIĘ — każda korekta użytkownika jest natychmiast wykorzystywana
     do poprawy przyszłych decyzji (Active Learning, Bayesian Update).

  d) KOORDYNUJĄ APLIKACJĘ — agenci nie tylko analizują dane, ale także
     sterują interfejsem (Flet UI), kolejką zadań (Taskiq), komunikacją
     (NATS) i bazami danych (SQLite + DuckDB + TigerBeetle).

  e) SĄ ODPORNE — każda decyzja przechodzi przez minimum 2 niezależne
     modele (architektura "zero trust to a single model").

TECHNOLOGIE (z RAPORT_TECHNOLOGII):
  - Python ≥3.13 (free-threaded) — interpreter bez GIL
  - llama-cpp-python — inferencja modeli GGUF
  - NATS JetStream + Taskiq — komunikacja między agentami
  - DuckDB — pamięć episodyczna i analityka
  - SQLite + sqlite-vec — pamięć semantyczna (wektory)
  - TigerBeetle — księga główna (double-entry)
  - msgspec — wszystkie struktury danych
  - stamina — circuit breaker i retry
  - nexus-crypto — proof chain kryptograficzny

1.2. Poziomy autonomii agentów
-------------------------------

System definiuje 4 POZIOMY AUTONOMII dla każdego agenta:

  LEVEL 0 — MANUALNY: Agent tylko proponuje, użytkownik zatwierdza każdą
            decyzję. Idealny dla pierwszych 100 faktur (okres nauki).

  LEVEL 1 — ASYSTENT: Agent podejmuje decyzje w zielonej strefie,
            pyta użytkownika w żółtej i blokuje w czerwonej.

  LEVEL 2 — AUTONOMICZNY: Agent podejmuje decyzje w zielonej i żółtej,
            pyta użytkownika tylko w czerwonej. Standardowy poziom.

  LEVEL 3 — W PEŁNI AUTONOMICZNY: Agent podejmuje wszystkie decyzje,
            informuje użytkownika podsumowaniem dziennym/tygodniowym.
            Wymaga Trust Score > 0.95 przez ostatnie 1000 decyzji.

Przełączanie poziomów:
  - Automatyczne: po osiągnięciu progu zaufania (Bayesian update)
  - Ręczne: użytkownik może zawsze wymusić wyższy/niższy poziom
  - Awaryjne: przy wykryciu anomalii system automatycznie obniża poziom

IMPLEMENTACJA (msgspec.Struct):
  class AutonomyLevel(enum.IntEnum):
      MANUAL = 0
      ASSISTANT = 1
      AUTONOMOUS = 2
      FULL_AUTONOMOUS = 3

  class AutonomyConfig(Struct, kw_only=True):
      level: AutonomyLevel = AutonomyLevel.AUTONOMOUS
      min_trust_for_level: dict[AutonomyLevel, float] = {
          AutonomyLevel.MANUAL: 0.0,
          AutonomyLevel.ASSISTANT: 0.75,
          AutonomyLevel.AUTONOMOUS: 0.92,
          AutonomyLevel.FULL_AUTONOMOUS: 0.98,
      }
      min_decisions_for_promotion: int = 1000
      auto_demote_on_anomaly: bool = True

1.3. Mapa interakcji człowiek ↔ agenci
---------------------------------------

Użytkownik (przedsiębiorca) wchodzi w interakcję z systemem przez:

  A) Dashboard (Flet UI) — podsumowania, alerty, decyzje do podjęcia
  B) Panel decyzyjny — lista decyzji oczekujących na zatwierdzenie
  C) Czat z Komunikatore (Qwen3-Nano) — pytania w języku naturalnym
  D) Raporty tygodniowe/miesięczne — generowane przez AgentAnalytics

System NATOMIAST samodzielnie:

  a) Pobiera faktury (email, upload, API)
  b) Ekstrahuje dane (OCR + walidacja krzyżowa)
  c) Klasyfikuje wydatki (konta księgowe, stawki VAT)
  d) Wysyła do KSeF (obowiązkowy e-spis)
  e) Planuje płatności (priorytety, skonta, terminy)
  f) Uzgodnia salda (DuckDB + TigerBeetle)
  g) Generuje deklaracje (JPK, VAT, PIT, CIT)
  h) Monitoruje terminy (ZUS, US, KSeF)
  i) Wykrywa anomalie (oszustwa, błędy, ryzyko)

2.1. AgentOrchestrator — Centralny Mózg i CFO
===============================================

ROLA:       Naczelny dyrektor finansowy (CFO). Koordynuje wszystkich agentów,
            podejmuje ostateczne decyzje, komunikuje się z użytkownikiem.

MODELE:
  - Granite 3.2 3B (GGUF, IQ4_XS) — Główny Decydent (Actor)
  - Granite Guardian 0.5B (GGUF, Q4_K_M) — Strażnik Merytoryczny
  - Qwen3-Nano 0.5B (GGUF, Q4_K_M) — Komunikator (NL → user)

NOWE MECHANIZMY ENTERPRISE:

  1. DYNAMICZNY TRUST SCORE (Bayesian Update)
     - Trust Score aktualizowany po każdej decyzji:
       P(θ|D) ∝ P(D|θ) × P(θ)
     - Priory: Beta(α, β) gdzie α = liczba poprawnych, β = błędów
     - Wnioskowanie: posterior mean = α / (α + β)
     - Automatyczne obniżanie priory dla nowych kontrahentów

  2. DECISION CACHE (diskcache + sqlite-vec)
     - Każda decyzja jest wektoryzowana i zapisywana w sqlite-vec
     - Przy podobnej fakturze → podobna decyzja (k-NN, k=5)
     - Oszczędność: 80% decyzji nie wymaga inferencji modelu

  3. ADAPTIVE THRESHOLDS
     - Thresholds (0.92/0.75) są dynamiczne:
       auto_post_threshold = 0.92 - (α-β)/(α+β) × 0.1
     - Dla sprawdzonych kontrahentów (α >> β) threshold niższy
     - Dla nowych kontrahentów threshold wyższy (conservative)

  4. PROOF CHAIN (SHA-256)
     - Każda decyzja tworzy wpis w łańcuchu audytowym:
       hash = SHA256(previous_hash + decision_data + timestamp)
     - Niepodważalny dowód dla organów skarbowych

  5. ESCALATION MATRIX
     - Inteligentna eskalacja do człowieka:
       * O której porze dnia? (nie przeszkadza w nocy)
       * Jaki kanał? (push notyfikacja, email, SMS)
       * Jaki priorytet? (krytyczne: SMS, ważne: push, info: email)
       * Czy decyzja może poczekać? (opóźnienie do 24h)

KOMUNIKACJA NATS:
  council.task.request       → Wejście zadania
  council.decision.final     → Wyjście decyzji
  council.decision.review    → Decyzja wymagająca przeglądu
  council.decision.learn     → Korekta / feedback
  council.escalation         → Eskalacja do człowieka
  council.heartbeat          → Heartbeat (co 30s)

UCZENIE SIĘ:
  - Korekty użytkownika → Bayesian update Trust Score
  - Podobne faktury → k-NN z sqlite-vec
  - Wzorce decyzyjne → DuckDB analiza historyczna
  - Threshold adaptation → automatyczna kalibracja


2.2. AgentDataExtraction — Forteca Precyzji
=============================================

ROLA:       Ekstrakcja danych z dokumentów z precyzją przewyższającą
            profesjonalnego księgowego. Zero błędów w polach krytycznych.

MODELE:
  - ParagonDetect (lekkie CNN, ONNX) — klasyfikacja dokumentu
  - Tesseract 5.3 + PaddleOCR + python-docTR + EasyOCR — potrójny OCR
  - Granite Vision Guardian 0.3B — walidacja wizyjna
  - ModernBERT-NER-Finance 0.3B — walidacja semantyczna

NOWE MECHANIZMY ENTERPRISE:

  1. CROSS-VALIDATION MATRIX (4×4)
     - Każde pole jest ekstrahowane przez 4 silniki niezależnie
     - Macierz zgodności: jeśli 3/4 silników zgadza się → akceptuj
     - Jeśli 2/4 → oznacz jako "low confidence", wyślij do Vision Guardian
     - Jeśli < 2/4 → oznacz jako "conflict", wymagana ręczna weryfikacja

  2. ACTIVE LEARNING OCR
     - Każda ręczna korekta użytkownika to nowy przykład treningowy
     - Wektor korekty zapisywany w sqlite-vec (tabela ocr_corrections)
     - Przy kolejnej fakturze od tego kontrahenta: preferuj wzorzec
     - System uczy się układów faktur per-kontrahent

  3. INVOICE TEMPLATE MATCHING
     - Dla każdego kontrahenta budowany jest wzorzec faktury
     - Wzorzec: pozycje pól (bounding boxy), typy danych, formaty
     - Przy kolejnej fakturze: dopasuj do wzorca → szybsza ekstrakcja
     - sqlite-vec: embedding wzorca, k-NN dla szybkiego dopasowania

  4. SEMANTYCZNA WALIDACJA (ModernBERT-NER)
     - NIP: suma kontrolna + Biała Lista MF
     - IBAN: struktura + suma kontrolna + lista zastrzeżonych
     - Kwoty: netto + VAT = brutto (z tolerancją 0.01 PLN)
     - Daty: nie w przyszłości, nie starsze niż 5 lat
     - Kontrahent: czy istnieje w bazie, czy jest aktywny

  5. CONFIDENCE CALIBRATION
     - Każde pole ma indywidualny confidence score (0.0-1.0)
     - Agregacja: weighted average (wagi = historyczna precyzja silnika)
     - Jeśli całościowy confidence < 0.7 → oznacz do weryfikacji

UCZENIE SIĘ:
  - Korekty OCR → online learning (sqlite-vec ocr_corrections)
  - Wzorce faktur → template matching (unsupervised clustering)
  - Precyzja silników → Bayesian update per-field
  - Nowe formaty → automatyczne wykrywanie i kategoryzacja


2.3. AgentAnalytics — Sztab Analityczny
=========================================

ROLA:       Nieustanna analiza kondycji finansowej firmy. Wykrywa trendy,
            anomalie i ryzyka, zanim staną się problemem. Generuje raporty.

MODELE:
  - Hrida-T2SQL-128k (GGUF, IQ3_M) — zamiana NL → SQL (~1.0 GB RAM)
  - Granite 3.2 3B (GGUF, IQ4_XS) — Główny Analityk (~2.4 GB RAM)
  - Fin-RWKV-169M (GGUF, Q4_K_M) — Detektyw Finansowy (~100 MB RAM)
  - Lag-Llama 0.3B (GGUF, Q4_K_M) — Prognoza szeregów czasowych

NOWE MECHANIZMY ENTERPRISE:

  1. PROAKTYWNE MONITOROWANIE (24/7)
     - Cash flow: prognoza na 90 dni z daily update
     - Należności: DSO, przeterminowania, ryzyko windykacji
     - Zobowiązania: terminy, skonta, priorytety płatności
     - VAT: należny/naliczony, split payment, JPK
     - Wynik: P&L, marża, koszty, przychody
     - Anomalie: odchylenia > 2σ od średniej historycznej

  2. NATURAL LANGUAGE INSIGHTS
     - Codzienny brief: "Wczoraj wpłynęło 5 faktur na 12,450 PLN"
     - Alerty: "Kontrahent X zmienił konto bankowe"
     - Rekomendacje: "Zapłać fakturę Y — skonto 2% traci ważność za 3 dni"
     - Generowane przez Granite 3.2 + szablony promptów

  3. RAPORTY AUTOMATYCZNE
     - Dzienne: cash position, nowe faktury, alerty
     - Tygodniowe: P&L, DSO, overdue, top kontrahenci
     - Miesięczne: VAT, PIT/CIT, koszty, inwestycje
     - Kwartalne: analiza porównawcza, trendy, prognozy
     - Każdy raport → DuckDB SQL + Granite 3.2 (podsumowanie NL)

  4. ANOMALY DETECTION (Fin-RWKV + statystyka)
     - Univariate: Z-score, IQR, moving average
     - Multivariate: Mahalanobis distance, Isolation Forest
     - Temporal: change point detection (PELT, Binary Segmentation)
     - Grafowa: sieć powiązań kontrahentów (karuzele VAT)
     - Wynik: (is_anomaly, severity, reason, recommended_action)

UCZENIE SIĘ:
  - Wzorce sezonowe → automatyczne wykrywanie i modelowanie
  - Korekty prognoz → Bayesian update parametrów
  - Nowe typy anomalii → clustering + etykietowanie
  - Preferencje raportowe → personalizacja zakresu i formatu


2.4. AgentQualityValidator — Strażnik Integralności
=====================================================

ROLA:       Niezależny audytor. Weryfikuje każdą decyzję przed wykonaniem.
            Architektura "zero trust" — żaden pojedynczy model nie może
            podjąć ostatecznej decyzji.

MODELE:
  - Granite Guardian 0.5B (GGUF, Q4_K_M) — Strażnik Podatkowy
  - GraphSAGE-Encoder 0.1B (ONNX) — Detektor Oszustw (grafy)
  - FinBERT-ESG 0.1B (GGUF, Q4_K_M) — Analityk Ryzyka
  - Lag-Llama 0.3B (GGUF, Q4_K_M) — Prognoza Płynności

NOWE MECHANIZMY ENTERPRISE:

  1. 4-EYES PRINCIPLE (obowiązkowy dla kwot > 50,000 PLN)
     - Każda decyzja na kwotę > 50k PLN wymaga 2 niezależnych weryfikacji
     - Pierwsza: Granite Guardian (podatki)
     - Druga: GraphSAGE + FinBERT (oszustwa + ryzyko)
     - Jeśli split: wyższy próg (75,000 PLN)

  2. TAX COMPLIANCE ENGINE
     - Sprawdza każdą decyzję pod kątem:
       * Zgodność z aktualnymi stawkami VAT
       * Split payment (obowiązkowy dla kwot > 15,000 PLN)
       * JPK_VAT deklaracja (zgodność struktur)
       * Klasyfikacja PKWiU (poprawność kodów)
     - Wykorzystuje OPA (Open Policy Agent) z regułami Rego
     - Reguły aktualizowane automatycznie z MF (hishel cache)

  3. FRAUD GRAPH SCANNER
     - Buduje graf powiązań: kontrahenci, faktury, konta bankowe
     - Wykrywa:
       * Karuzele VAT (cykliczne transakcje)
       * Słupy (nowi kontrahency, brak historii)
       * Zmiany kont bankowych (częste, nietypowe)
       * Duplikaty (podobne faktury, różne numery)
     - GraphSAGE: embedding węzłów + klasyfikacja anomalii

  4. LIQUIDITY STRESS TEST
     - Dla każdej decyzji > 10,000 PLN sprawdź wpływ na płynność
     - Symulacja Monte Carlo: 1000 scenariuszy cash flow
     - Jeśli ryzyko niedoboru > 5% → WARNING, > 20% → BLOCK
     - Uwzględnia: należności, zobowiązania, sezonowość, VAT

  5. VOTE WEIGHTING
     - Każdy model ma wagę = historyczna precyzja na jego domenie
     - Tax Guardian: 0.35 | Fraud: 0.30 | ESG: 0.20 | Lag-Llama: 0.15
     - Wagi aktualizowane po każdej weryfikacji (Bayesian)

UCZENIE SIĘ:
  - Potwierdzone oszustwa → retraining GraphSAGE (online)
  - Nowe typy ryzyka → reguły w OPA (hot-reload)
  - Precyzja modeli → Bayesian update per-domain
  - Thresholds → adaptive (uczy się z historii decyzji)


2.5. AgentTaxEngine — Automatyczny Doradca Podatkowy
======================================================

ROLA:       Automatyczne wyliczanie podatków VAT, PIT, CIT.
            Optymalizacja podatkowa w ramach prawa.

TECHNOLOGIE:
  - DuckDB (kalkulacje, agregacje)
  - OPA + Rego (reguły podatkowe, first-match-wins)
  - TigerBeetle (księga główna, double-entry)
  - stamina (retry dla API MF)

MECHANIZMY:

  1. VAT ENGINE
     - Automatyczne określanie stawki VAT (23%, 8%, 5%, 0%, ZW)
     - Split payment verification (obowiązkowy ≥ 15,000 PLN)
     - JPK_VAT(7) generowanie (miesięczne/kwartalne)
     - VAT-UE (transakcje wewnątrzwspólnotowe)
     - Korekty VAT (bad debts, import, eksport)

  2. PIT/CIT ENGINE
     - Automatyczne określanie formy opodatkowania
     - Kalkulacja zaliczek (miesięczne/kwartalne)
     - Koszty uzyskania przychodu (KUP)
     - Amortyzacja (środki trwałe, wartości niematerialne)
     - Ulgi i odliczenia (B+R, IP Box, darowizny)

  3. TAX OPTIMIZATION
     - Symulacje "co by było, gdyby" (DuckDB shadow ledger)
     - Rekomendacje: zmiana formy opodatkowania
     - Optymalizacja: split payment, grupy VAT, estoński CIT
     - Ryzyko: interpretacje podatkowe, klauzula GAAR

  4. DEADLINE MANAGEMENT
     - Monitorowanie wszystkich terminów podatkowych
     - Automatyczne przypomnienia (email, push, SMS)
     - Priorytetyzacja: US > ZUS > KSeF > inne
     - Alerty o zbliżających się terminach (7, 3, 1 dzień)

UCZENIE SIĘ:
  - Interpretacje podatkowe → reguły w OPA (semi-automatic)
  - Optymalizacje → DuckDB analiza historyczna
  - Błędy → automatyczna korekta + powiadomienie
  - Nowe przepisy → aktualizacja reguł (manual + AI assist)


2.6. AgentCashManager — Zarządca Płynności
=============================================

ROLA:       Zarządzanie przepływami pieniężnymi. Planowanie płatności,
            optymalizacja salda, minimalizacja kosztów finansowych.

TECHNOLOGIE:
  - DuckDB (prognozy, analizy)
  - TigerBeetle (księga, transfery)
  - Lag-Llama (prognoza szeregów czasowych)
  - Fin-RWKV (wykrywanie anomalii)

MECHANIZMY:

  1. CASH FLOW FORECAST (90 dni)
     - Dzienne saldo: otwarcie + wpływy - wypływy = zamknięcie
     - Trzy scenariusze: optymistyczny (p25), bazowy (p50), pesymistyczny (p75)
     - Uwzględnia: faktury, VAT, ZUS, US, wynagrodzenia, koszty stałe
     - Lag-Llama: predykcja szeregów czasowych z daily update

  2. PAYMENT OPTIMIZER
     - Priorytetyzacja płatności:
       * Krytyczne: US, ZUS, ZUS (kary za opóźnienie)
       * Wysoki priorytet: skonta (oszczędność > koszt kapitału)
       * Średni: dostawcy strategiczni
       * Niski: dostawcy elastyczni
     - Optymalizacja: delayed payment bez ryzyka windykacji
     - Batchnig: grupuj płatności tego samego dnia

  3. LIQUIDITY BUFFER
     - Minimalny bufor: 30 dni kosztów stałych
     - Docelowy bufor: 90 dni (zalecany dla MŚP)
     - Alert: gdy bufor < 30 dni → automatyczne ograniczenie wydatków
     - Nadwyżka: rekomendacje lokat/kont oszczędnościowych

  4. WORKING CAPITAL OPTIMIZATION
     - DSO (Days Sales Outstanding) → target < 30 dni
     - DPO (Days Payables Outstanding) → target > 45 dni
     - DIO (Days Inventory Outstanding) → target < 15 dni
     - Cash Conversion Cycle = DSO + DIO - DPO → target < 0

UCZENIE SIĘ:
  - Wzorce płatności kontrahentów → personalizacja prognoz
  - Sezonowość → automatyczne wykrywanie i modelowanie
  - Opóźnienia → korekta wag (Bayesian)
  - Optymalne batchowanie → reinforcement learning

3.1. Active Learning Loop
--------------------------

System agentów uczy się w pętli zamkniętej (closed-loop learning):

  ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
  │ DECYZJA  │───→│ KOREKTA  │───→│ NAUKA    │───→│ POPRAWA  │
  │ Agenta   │    │ Usera    │    │ Modelu   │    │ Threshold│
  └──────────┘    └──────────┘    └──────────┘    └──────────┘
       ↑                                               │
       └───────────────────────────────────────────────┘

Algorytm:

  1. Agent podejmuje decyzję (z Trust Score)
  2. Jeśli Trust Score < threshold → pytamy użytkownika
  3. Użytkownik: zatwierdza / koryguje / odrzuca
  4. Różnica między decyzją agenta a korektą użytkownika:
     Δ = |decision_agent - decision_user|
  5. Bayesian update Trust Score z Δ
  6. Jeśli Δ > 0.1 → dodaj przykład do Active Learning Dataset
  7. Jeśli dataset ≥ 100 → trigger fine-tuningu (online)
  8. Adjust thresholds (adaptive calibration)

Implementacja w DuckDB:

  CREATE TABLE agent_learning_log (
      id UUID PRIMARY KEY,
      decision_id UUID REFERENCES decisions(id),
      agent_name TEXT NOT NULL,
      predicted_value JSONB,
      corrected_value JSONB,
      delta FLOAT NOT NULL,
      timestamp TIMESTAMP DEFAULT NOW(),
      feedback_type TEXT CHECK (feedback_type IN ('accept', 'correct', 'reject')),
      model_version TEXT
  );

  CREATE TABLE calibration_stats (
      agent_name TEXT NOT NULL,
      total_decisions INT DEFAULT 0,
      correct_decisions INT DEFAULT 0,
      precision FLOAT DEFAULT 0.0,
      recall FLOAT DEFAULT 0.0,
      avg_delta FLOAT DEFAULT 0.0,
      last_calibration TIMESTAMP,
      alpha FLOAT DEFAULT 1.0,  -- Bayesian prior parameters
      beta FLOAT DEFAULT 1.0
  );

  -- Bayesian update: alpha += correct, beta += incorrect
  -- Posterior precision = alpha / (alpha + beta)

3.3. Trust Score Adaptation (Bayesian update)
-----------------------------------------------

Trust Score nie jest prostą średnią — to Bayesian posterior:

  Priory:   Beta(α₀, β₀)  gdzie α₀ = 1, β₀ = 1 (uniform)
  Likelihood: Bern(y|θ)   gdzie y = {1 if correct, 0 if incorrect}
  Posterior: Beta(α₀ + Σy, β₀ + n - Σy)

  Trust Score = E[θ|D] = α / (α + β)

  Confidence = 1 - Var[θ|D] = 1 - αβ / ((α+β)²(α+β+1))

  Gdzie:
    α = α₀ + poprawne decyzje
    β = β₀ + błędne decyzje
    n = α + β - α₀ - β₀ = liczba decyzji

Implementacja w nexus_ai/agents/learning.py:

  class BayesianTrustScore:
      def __init__(self, alpha: float = 1.0, beta: float = 1.0):
          self.alpha = alpha
          self.beta = beta

      def update(self, correct: bool) -> None:
          if correct:
              self.alpha += 1
          else:
              self.beta += 1

      @property
      def trust_score(self) -> float:
          return self.alpha / (self.alpha + self.beta)

      @property
      def confidence(self) -> float:
          total = self.alpha + self.beta
          variance = (self.alpha * self.beta) / (total**2 * (total + 1))
          return max(0.0, 1.0 - variance * 12)  # scaled to [0,1]

      @property
      def needs_more_data(self) -> bool:
          return (self.alpha + self.beta) < 30  # < 30 decyzji = niepewny

3.4. Confidence Calibration przez DuckDB
------------------------------------------

Każdy agent ma swoją tablicę kalibracyjną w DuckDB:

  CREATE TABLE model_calibration (
      model_name TEXT NOT NULL,
      predicted_confidence FLOAT NOT NULL,  -- 0.0-1.0, bucketed
      actual_accuracy FLOAT NOT NULL,       -- observed accuracy
      sample_count INT NOT NULL DEFAULT 0,
      last_updated TIMESTAMP DEFAULT NOW()
  );

  -- Jeśli model mówi "jestem w 90% pewien" ale ma 70% accuracy →
  -- confidence jest skalowany: calibrated = accuracy / confidence

  Calibrated Trust Score = Trust Score × (accuracy_at_bucket / confidence)

  Gdzie accuracy_at_bucket to rzeczywista precyzja dla decyzji
  z podobnym poziomem zaufania (Platt scaling / isotonic regression).

4.2. Gwarancje dostarczenia (Exactly-once, DLQ)
-------------------------------------------------

  a) AT-LEAST-ONCE DELIVERY
     Każda wiadomość jest trwale zapisywana w JetStream.
     Po przetworzeniu: manual ack.
     Jeśli worker umrze → redelivery do innego workera.

  b) DEAD LETTER QUEUE (DLQ)
     Po 3 nieudanych próbach → wiadomość do DLQ.
     DLQ przechowuje: original message + error trace + attempt count.
     Administrator może: przejrzeć, poprawić, retry, odrzucić.

  c) DUPLICATE DETECTION
     Każde zadanie ma task_id = blake2b(task_name + sorted(kwargs)).
     JetStream duplicate_window = 2 min.
     Identyczne zadania w oknie → automatycznie odrzucone.

  d) MAX ACK PENDING
     Domyślnie: 5. Dynamicznie dostosowywany przez WorkerGuard.
     Przy wysokim CPU/RAM → zmniejszany.
     Przy niskim CPU/RAM → zwiększany (max 15).

4.3. Priority Queue i QoS
---------------------------

  Każde zadanie ma priorytet (1-10, 1 = najwyższy):

    1  — Krytyczne: błąd systemu, awaria KSeF, deadline podatkowy
    2  — Pilne: płatność z skontem, faktura od kluczowego klienta
    3  — Wysoki: nowa faktura > 50,000 PLN, podejrzenie oszustwa
    4-5 — Normalny: standardowa faktura, zapytanie analityczne
    6-7 — Niski: raport tygodniowy, aktualizacja wzorców
    8-9 — Background: aktualizacja modeli, regeneracja embeddingów
    10 — Idle: heartbeat, health check

  QoS (Quality of Service):
    - P0-P1: dedicate 1 worker process (z 2)
    - P2-P3: max 50% worker capacity
    - P4-P7: remaining capacity
    - P8-P10: only when idle

4.4. Circuit Breaker i retry z backoffem
-----------------------------------------

  Wykorzystuje stamina (z RAPORT_TECHNOLOGII):

    @stamina.retry(
        on=(NatsError, TimeoutError),
        attempts=3,
        timeout=30.0,
        # Exponential backoff z jitterem
    )
    async def publish_with_retry(topic: str, data: bytes) -> None:
        ...

  Circuit Breaker:
    - Próg: 5 błędów w 30 sekund
    - Otwarcie: 60 sekund (cooldown)
    - Half-open: po 60s przepuść 1 żądanie testowe
    - Jeśli OK → zamknij. Jeśli błąd → otwórz na 120s.
    - Stan publikowany na: system.breakers.{agent_name}

================================================================================
5. DECISION ENGINE — Wielowarstwowy Silnik Decyzyjny
================================================================================

5.1. Strefy decyzyjne (Dynamic Thresholds)
--------------------------------------------

  Thresholds nie są stałe — adaptują się Bayesian:

    auto_post = 0.92 - adjustment
    review = 0.75 - adjustment

    adjustment = (alpha_vendor - beta_vendor) / (alpha_vendor + beta_vendor) * 0.1

  Gdzie alpha_vendor, beta_vendor = Bayesian params dla kontrahenta.

  Przykład:
    - Znany kontrahent (100 faktur, 98 poprawnych):
      alpha=98, beta=2 → adjustment = 0.096
      auto_post = 0.92 - 0.096 = 0.824 ← niższy próg (łatwiej auto-post)

    - Nowy kontrahent (5 faktur, 4 poprawne):
      alpha=4, beta=1 → adjustment = 0.06
      auto_post = 0.92 - 0.06 = 0.86 ← wyższy próg (ostrożniej)

    - Podejrzany kontrahent (10 faktur, 6 poprawnych):
      alpha=6, beta=4 → adjustment = 0.02
      auto_post = 0.92 - 0.02 = 0.90 ← bardzo wysoki próg

5.2. Konsensus między agentami
--------------------------------

  Ostateczna decyzja = weighted vote agentów:

    final_decision = majority_vote(weighted_decisions)

    gdzie:
      - AgentOrchestrator:    waga = 0.35
      - AgentTaxEngine:       waga = 0.25
      - AgentQualityValidator: waga = 0.40 (niezależny audytor)

    Jeśli split decyzji:
      - 2/3 zgoda → akceptuj decyzję większości
      - 1/3 zgoda → REVIEW (eskaluj do człowieka)
      - 0/3 zgoda → BLOCK (błąd systemu)

5.3. Eskalacja do człowieka
-----------------------------

  Eskalacja następuje gdy:
    a) Trust Score < review_threshold
    b) QualityValidator zwróci ERROR
    c) Konsensus między agentami < 2/3
    d) Kwota > max_auto_post (domyślnie 100,000 PLN)
    e) Nowy kontrahent > 50,000 PLN
    f) Zmiana konta bankowego kontrahenta

  Komunikator (Qwen3-Nano) generuje:

    "Dzień dobry Panie Piotrze,

    Faktura nr FV/2026/12345 od 'Nowy Kontrahent Sp. z o.o.'
    na kwotę 75,000 PLN wymaga Twojej decyzji.

    System proponuje: ZATWIERDŹ (trust score: 0.82)
    Ryzyko: NOWY KONTRAHENT (współpraca < 30 dni)

    Opcje:
    1. Zatwierdź — faktura zostanie zaksięgowana i wysłana do KSeF
    2. Prześlij do weryfikacji — poprosimy o dodatkowe dokumenty
    3. Odrzuć — faktura wróci do skrzynki odbiorczej

    Twoja decyzja? (1/2/3)"

  Mechanizm:
    - Użytkownik odpowiada (kliknięcie w UI lub tekst)
    - System zapisuje decyzję w agent_learning_log
    - Bayesian update Trust Score
    - Jeśli decyzja użytkownika różni się od propozycji → active learning

5.4. Audit trail (Proof Chain)
--------------------------------

  Każda decyzja tworzy niepodważalny dowód w łańcuchu SHA-256:

    block = {
        "index": previous.index + 1,
        "timestamp": now(),
        "decision_id": uuid,
        "agent_decisions": [...],
        "user_decision": None | "approve" | "correct" | "reject",
        "previous_hash": previous.hash,
        "nonce": random_int,
        "hash": sha256(serialize(block))
    }

  Implementacja przez nexus-crypto (SHA-256):

    from nexus_crypto import Sha256Hasher

    class ProofChain:
        def __init__(self):
            self.chain = []
            self.load_from_db()  # DuckDB: SELECT * FROM proof_chain

        def add_block(self, decision: AgentDecision) -> str:
            previous_hash = self.chain[-1].hash if self.chain else "0" * 64
            block_data = {
                "index": len(self.chain),
                "decision_id": decision.decision_id,
                "decision": msgspec.json.encode(decision).decode(),
                "timestamp": pendulum.now("UTC").isoformat(),
                "previous_hash": previous_hash,
            }
            hasher = Sha256Hasher()
            hasher.update(msgspec.json.encode(block_data))
            block_data["hash"] = hasher.hexdigest()
            self.chain.append(block_data)
            return block_data["hash"]

5.5. Confidence voting między modelami
----------------------------------------

  Każdy model głosuje z wagą = historyczna precyzja × confidence:

    class ConfidenceVote(Struct, kw_only=True):
        model_name: str
        model_weight: float = 0.0  # historyczna precyzja
        vote: str  # POST | REVIEW | BLOCK
        confidence: float = 0.0   # confidence tej decyzji
        weighted_vote: float = 0.0  # model_weight × confidence

    class VotingResult(Struct, kw_only=True):
        votes: list[ConfidenceVote]
        total_weight: float
        weighted_post: float
        weighted_review: float
        weighted_block: float
        winner: str  # POST | REVIEW | BLOCK
        consensus: bool = False  # True if votes > 0.66 majority
        uncertainty: float = 0.0

  Jeśli uncertainty > 0.3 → eskalacja do człowieka.

6.5. Adaptive Thresholds (Bayesian Inference)
-----------------------------------------------

  Thresholds adaptują się dynamicznie:

    agent_threshold = base_threshold - correction

    correction = (α - β) / (α + β) × max_correction

    gdzie:
      α = poprawne decyzje w tej domenie
      β = błędne decyzje w tej domenie
      max_correction = 0.1 (maksymalna korekta)

    Dla nowych domen (α + β < 30):
      correction *= (α + β) / 30  # conservative start

    Dla znanych domen (α + β ≥ 100):
      correction = min(correction, max_correction)  # full correction

7.3. Split payment verification
---------------------------------

  Zgodnie z polskim prawem (od 2019):
    - Obowiązkowy dla kwot > 15,000 PLN brutto (od 2024: 8,000 PLN)
    - Sprawdzany przez AgentTaxEngine

  Mechanizm:
    1. AgentTaxEngine sprawdza kwotę brutto
    2. Jeśli ≥ threshold → oznacz do split payment
    3. AgentOrchestrator tworzy 2 transfery w TigerBeetle:
       - netto na konto główne
       - VAT na konto VAT (Subkonto)
    4. AgentQualityValidator weryfikuje poprawność

7.4. RODO / GDPR compliance
-----------------------------

  System zapewnia zgodność z RODO:
    - Dane osobowe: przechowywane w SQLCipher (AES-256)
    - Anonimizacja: automatyczna po 5 latach
    - Backup: szyfrowany, z weryfikacją SHA-256
    - Eksport: możliwość eksportu wszystkich danych użytkownika
    - Usunięcie: pełne usunięcie danych na żądanie

7.5. KSeF compliance
----------------------

  System zapewnia zgodność z Krajowym Systemem e-Faktur:
    - Struktura FA(1), FA(2) zgodna ze schematem MF
    - Podpis elektroniczny (SHA-256 + certyfikat)
    - Automatyczna wysyłka w ciągu 1h od zatwierdzenia
    - Przechowywanie UPO (Urzędowe Poświadczenie Odbioru)
    - Backup offline: faktury są zawsze dostępne lokalnie

7.6. Proof Chain kryptograficzny
----------------------------------

  SHA-256 chain dla niepodważalnego audytu:
    - Każda decyzja → block w łańcuchu
    - Każdy block zawiera hash poprzedniego
    - Modyfikacja dowolnego bloku → wszystkie kolejne unieważnione
    - Eksport do pliku dla organów skarbowych
    - Implementacja przez nexus-crypto (Sha256Hasher)

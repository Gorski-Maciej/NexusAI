1.1. Filozofia architektury
---------------------------

System agentów AI w NexusAI został zaprojektowany jako AUTONOMICZNE BIURO
KSIĘGOWE — zestaw 5 wyspecjalizowanych agentów, które:

  a) DZIAŁAJĄ W TLE — użytkownik nie musi wiedzieć, który agent przetwarza
     jego fakturę. System działa jak niewidzialny, perfekcyjny księgowy.

  b) PODEJMUJĄ DECYZJE — w zielonej strefie (Trust Score ≥ 0.92) agenci
     samodzielnie księgują (AUTO_POST). W żółtej (0.75-0.92) proponują
     i pytają (SUGGEST). W czerwonej (<0.75) pytają użytkownika (ASK_USER).

  c) UCZĄ SIĘ NA DWÓCH WARSTWACH:
     - Cognitive Audit Trail: korekty → embeddingi → auto-naprawa reguł OPA
     - Dynamiczny Podręcznik Błędów: few-shot learning w DuckDB

  d) KOORDYNUJĄ APLIKACJĘ — agenci sterują UI (Flet), kolejką (Taskiq),
     komunikacją (NATS), bazami danych i księgą główną (TigerBeetle).

  e) SĄ ODPORNE — każda decyzja przez minimum 2 niezależne modele
     (architektura "zero trust to a single model").

TECHNOLOGIE (wyłącznie z RAPORT_TECHNOLOGII):
  - Python ≥3.13 (free-threaded) — interpreter bez GIL
  - llama-cpp-python — inferencja modeli GGUF
  - NATS JetStream + Taskiq — komunikacja między agentami
  - DuckDB — pamięć episodyczna, analityka, Error Handbook
  - SQLite + sqlite-vec — pamięć semantyczna, Cognitive Audit Trail
  - TigerBeetle — księga główna (double-entry)
  - msgspec — wszystkie struktury danych
  - stamina — circuit breaker i retry
  - nexus-crypto — proof chain kryptograficzny (SHA-256)
  - OPA + Rego — deterministyczny silnik reguł (auto-naprawiany)

1.2. JEDEN poziom automatyzacji (DecisionMode)
-----------------------------------------------

System używa JEDNEGO poziomu automatyzacji zamiast czterech:

  DecisionMode.AUTO_POST  (Trust ≥ 0.92):  Agent sam księguje,
                        użytkownik tylko informowany.

  DecisionMode.SUGGEST    (Trust ≥ 0.75):  Agent proponuje decyzję,
                        użytkownik zatwierdza jednym kliknięciem.

  DecisionMode.ASK_USER   (Trust < 0.75):  Agent pyta użytkownika,
                        przedstawia 2-5 opcji do wyboru.

Człowiek ZAWSZE jest decydentem. Agent wykonuje pracę i przedstawia opcje.

IMPLEMENTACJA (msgspec.Struct, zgodnie z kodem):

  class DecisionMode(enum.StrEnum):
      AUTO_POST = "auto_post"
      SUGGEST   = "suggest"
      ASK_USER  = "ask_user"

Próg AUTO_POST jest adaptacyjny (Bayesian per kontrahent):
  auto_post_threshold = 0.92 - (α-β)/(α+β) × 0.1

1.3. GENIALNY POMYSŁ #1: Cognitive Audit Trail (warstwa deterministyczna)
--------------------------------------------------------------------------

Każda korekta użytkownika tworzy blok poznawczy w łańcuchu dowodowym:

  DECYZJA → KOREKTA → EMBEDDING (sqlite-vec 768d) → k-NN →
  → AUTO-NAPRAWA REGUŁ OPA (po 10 korektach tego samego typu)

Łańcuch SHA-256 staje się AKTYWNYM systemem uczącym się, nie tylko pasywnym
rejestrem. Implementacja w ContinuousLearningProvider (base.py).

1.4. GENIALNY POMYSŁ #2: Dynamiczny Podręcznik Błędów (warstwa probabilistyczna)
---------------------------------------------------------------------------------

Online few-shot learning — model Granite 3.2 uczy się z każdej korekty
BEZ fine-tuningu, BEZ trenowania:

  KOREKTA → DuckDB error_handbook → kwerenda przed inferencją →
  → "Podręcznik Błędów z Przeszłości" w prompcie →
  → Granite 3.2 widzi: ❌ błędna decyzja → ✅ poprawna decyzja

Priorytetyzacja przykładów: NIP → kategoria → kwota → globalne.
Im więcej korekt, tym mądrzejszy model. Implementacja w DynamicErrorHandbook
(error_handbook.py).

1.5. Mapa interakcji człowiek ↔ agenci
---------------------------------------

Użytkownik (przedsiębiorca) wchodzi w interakcję przez:
  A) Dashboard (Flet UI) — podsumowania, alerty, decyzje
  B) Panel decyzyjny — decyzje oczekujące (SUGGEST/ASK_USER)
  C) Czat z Komunikatorem (Qwen3-Nano) — pytania NL
  D) Raporty automatyczne (AgentAnalytics)

System samodzielnie:
  a) Pobiera faktury (email, upload, KSeF, folder)
  b) Ekstrahuje dane (4 silniki OCR + walidacja krzyżowa)
  c) Weryfikuje kontrahentów (Biała Lista, GUS BIR)
  d) Wysyła do KSeF (AgentDataExtraction)
  e) Prognozuje cash flow (AgentAnalytics)
  f) Waliduje podatkowo (AgentQualityValidator + OPA)
  g) Księguje (TigerBeetle double-entry)
  h) Uczy się z każdej korekty (Cognitive Audit Trail + Error Handbook)

2.1. AgentOrchestrator — Centralny Mózg i Wirtualny CFO
=========================================================

ROLA:       Naczelny dyrektor finansowy. Koordynuje 4 agentów wykonawczych,
            podejmuje ostateczne decyzje, komunikuje się z użytkownikiem.

MODELE (13 modeli GGUF łącznie, ładowane leniwie):
  - Granite 3.2 3B (GGUF, IQ4_XS) — Główny Decydent (Actor) ~2.4 GB
  - Granite Guardian 0.5B (GGUF, Q4_K_M) — Strażnik Merytoryczny ~300 MB
  - Qwen3-Nano 0.5B (GGUF, Q4_K_M) — Komunikator ~400 MB

  RAM stały: ~2.98 GB

KLUCZOWE MECHANIZMY ENTERPRISE:

  1. DYNAMICZNY TRUST SCORE (Bayesian Update)
     - Trust Score = E[θ|D] = α / (α + β)
     - Aktualizowany po każdej decyzji

  2. COGNITIVE AUDIT TRAIL
     - Korekty → embeddingi w sqlite-vec → auto-naprawa OPA
     - Po 10 korektach tego samego typu → reguła aktualizowana

  3. DYNAMICZNY PODRĘCZNIK BŁĘDÓW
     - Few-shot learning z DuckDB przed każdą inferencją
     - Model Granite 3.2 widzi przykłady błędów z przeszłości

  4. DECISION CACHE (diskcache + sqlite-vec)
     - k-NN (k=5) dla podobnych decyzji
     - Oszczędność: ~80% decyzji bez inferencji

  5. ADAPTIVE THRESHOLDS
     - auto_post = 0.92 - (α-β)/(α+β) × 0.1
     - Dynamiczne per kontrahent

  6. PROOF CHAIN SHA-256 (nexus-crypto)
     - Każda decyzja → block w łańcuchu
     - Niepodważalny dowód dla US

  7. 4-EYES PRINCIPLE
     - Obowiązkowy dla kwot > 50,000 PLN
     - Dwie niezależne weryfikacje (Guardian + QualityValidator)

PROCES DECYZYJNY (7 kroków):
  1. Decision Cache: k-NN w podobnych decyzjach
  2. AgentDataExtraction → ekstrakcja (4 silniki OCR)
  3. Actor (Granite 3.2) + Guardian (Granite Guardian) → ocena
     (z wstrzyknięciem Podręcznika Błędów do promptu)
  4. AgentQualityValidator → walidacja (tax + fraud + ESG)
  5. Weighted Voting → konsensus
  6. Cognitive Audit Trail → sprawdź podobne korekty
  7. Ostateczna decyzja: AUTO_POST / SUGGEST / ASK_USER

STREFA DECYZYJNA:
  AUTO_POST (≥0.92 adaptive) → automatyczne księgowanie
  SUGGEST   (≥0.75 adaptive) → propozycja dla użytkownika
  ASK_USER  (<0.75)           → pytanie z opcjami

KOMUNIKACJA NATS:
  council.task.request       → wejście zadania
  council.decision.final     → wyjście decyzji
  council.decision.review    → decyzja do przeglądu
  council.decision.learn     → korekta/feedback
  council.escalation         → eskalacja
  council.heartbeat          → heartbeat (co 30s)

UCZENIE SIĘ:
  - Korekty → Bayesian update + Error Handbook + Cognitive Audit Trail
  - Podobne faktury → k-NN z sqlite-vec (decision_patterns)
  - Wzorce decyzyjne → DuckDB analiza historyczna

3. SYSTEM UCZENIA SIĘ — Continuous Learning Framework
================================================================================

3.1. Active Learning Loop (pętla zamknięta)
--------------------------------------------

  DECYZJA Agenta → KOREKTA Usera → DWA SYSTEMY UCZĄCE SIĘ RÓWNOLEGLE:

    ├─→ Cognitive Audit Trail: embedding → k-NN → auto-naprawa OPA
    └─→ Dynamiczny Podręcznik Błędów: DuckDB → few-shot w prompcie

  Implementacja (DuckDB):
    CREATE TABLE agent_learning_log (
        id UUID PRIMARY KEY,
        decision_id UUID,
        agent_name TEXT NOT NULL,
        predicted_value JSONB,
        corrected_value JSONB,
        delta FLOAT NOT NULL,
        timestamp TIMESTAMP DEFAULT NOW(),
        feedback_type TEXT CHECK (IN ('accept','correct','reject'))
    );

3.2. Cognitive Audit Trail (samouzdrawiające się reguły OPA)
-------------------------------------------------------------

  Każda korekta tworzy CognitiveProofBlock:
    - Embedding korekty 768d w sqlite-vec
    - k-NN (cosine similarity) dla podobnych przypadków
    - Po 10 korektach tego samego typu → automatyczna aktualizacja reguł OPA

  Implementacja w ContinuousLearningProvider (base.py):
    - record_feedback(correction_embedding=...) → CognitiveProofBlock
    - find_similar_corrections() → k-NN w sqlite-vec
    - should_auto_patch_opa() → True po min_samples_for_opa_update

  Przykład:
    1. User koryguje stawkę VAT z 23% na 8% dla kategorii "spożywcze"
    2. Embedding faktury zapisany w CognitiveProofBlock
    3. Kolejna faktura "spożywcza" → k-NN → podobny embedding
    4. System automatycznie proponuje 8% VAT
    5. Po 10 korektach → reguła OPA auto-aktualizowana

3.3. Dynamiczny Podręcznik Błędów (few-shot learning)
------------------------------------------------------

  Przed każdą inferencją Granite 3.2:
    1. DuckDB error_handbook: SELECT ... WHERE vendor_nip = ? ORDER BY timestamp DESC LIMIT 3
    2. Formatowanie: "Podręcznik Błędów z Przeszłości"
    3. Wstrzyknięcie do promptu modelu
    4. Model widzi: ❌ co AI zdecydowało → ✅ co było poprawne

  Priorytetyzacja:
    Level 1: Ten sam NIP + kategoria (exact match)
    Level 2: Ten sam NIP (vendor-specific learning)
    Level 3: Ta sama kategoria + podobna kwota (±50%)
    Level 4: Najczęściej korygowane globalnie

  Implementacja w DynamicErrorHandbook (error_handbook.py):
    - record_correction() → DuckDB INSERT
    - build_few_shot_prompt() → formatowanie do promptu
    - query_relevant() → priorytetyzowane wyszukiwanie

3.4. Bayesian Trust Score z propagacją
---------------------------------------

  Trust Score = posterior Beta distribution:
    Prior:       Beta(α₀=1, β₀=1)
    Posterior:   Beta(α₀+Σy, β₀+n-Σy)
    Trust Score  = E[θ|D] = α / (α + β)
    Confidence   = 1 - Var[θ|D]

  Gdzie: α = poprawne decyzje, β = błędne decyzje.

3.5. Confidence Calibration przez DuckDB
-----------------------------------------

  CREATE TABLE model_calibration (
      model_name TEXT NOT NULL,
      predicted_confidence FLOAT NOT NULL,
      actual_accuracy FLOAT NOT NULL,
      sample_count INT DEFAULT 0
  );

  Calibrated Score = Trust Score × (accuracy / confidence)

3.6. OCR Online Learning
--------------------------

  Korekty OCR → sqlite-vec → preferuj skorygowaną wartość:
    CREATE TABLE ocr_corrections (
        id UUID PRIMARY KEY,
        contractor_nip TEXT NOT NULL,
        field_name TEXT NOT NULL,
        ocr_value TEXT,
        corrected_value TEXT NOT NULL,
        embedding FLOAT[768]  -- sqlite-vec
    );

3.7. Adaptive Thresholds
--------------------------

  agent_threshold = base_threshold - correction
  correction = (α - β) / (α + β) × max_correction

  Dla nowych (α+β < 30): conservative (correction × (α+β)/30)
  Dla znanych (α+β ≥ 100): full correction

5. DECISION ENGINE — Wielowarstwowy Silnik Decyzyjny
================================================================================

5.1. Strefy decyzyjne (Dynamic Thresholds)
--------------------------------------------

  auto_post = 0.92 - adjustment
  review    = 0.75 - adjustment

  adjustment = (α_vendor - β_vendor) / (α_vendor + β_vendor) × 0.1

  Przykład:
    Znany kontrahent (100 faktur, 98 OK):  auto_post = 0.824
    Nowy kontrahent (5 faktur, 4 OK):      auto_post = 0.86
    Podejrzany (10 faktur, 6 OK):          auto_post = 0.90

5.2. Konsensus między agentami (Weighted Voting)
--------------------------------------------------

  Ostateczna decyzja = ważony głos:
    AgentOrchestrator:     waga = 0.40
    AgentQualityValidator: waga = 0.60 (niezależny audytor)

  Jeśli consensus > 0.66 → akceptuj.
  Jeśli uncertainty > 0.3 → eskalacja.

5.3. Eskalacja do człowieka
-----------------------------

  Eskalacja gdy:
    a) Trust Score < review_threshold
    b) QualityValidator → ERROR
    c) Konsensus < 0.66
    d) Kwota > 100,000 PLN
    e) Nowy kontrahent > 50,000 PLN
    f) Zmiana konta bankowego

  Komunikator (Qwen3-Nano) generuje wiadomość NL z opcjami.

5.4. Proof Chain SHA-256
--------------------------

  Implementacja przez nexus-crypto:
    - Każda decyzja → block w łańcuchu
    - hash = SHA256(previous + decision + timestamp)
    - Niepodważalny dowód dla organów skarbowych

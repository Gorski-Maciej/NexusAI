0.1. Transformacja: od reaktywnego do proaktywnego
---------------------------------------------------

PRZED (reaktywny, v4.0):
  Użytkownik wrzuca fakturę → Agent przetwarza → Koniec
  Agenci czekają na zdarzenia zewnętrzne.

PO (proaktywny ENTERPRISE, v5.0):
  Agenci NIE czekają — sami inicjują zadania, znajdują faktury,
  monitorują terminy i przedstawiają przedsiębiorcy gotowe decyzje.

  06:00 — Daily Briefing: "Dzień dobry. Wpłynęły 3 faktury na 12 450 PLN..."
  07:00 — KSeF Fetch: automatyczne pobranie nowych faktur
  08:00 — Bank Sync: wykrycie nowych transakcji
  09:00 — Dunning: windykacja należności
  10:00 — Vendor Monitor: Biała Lista MF, zmiany kont
  14:00 — Tax Alert: "Jutro mija termin ZUS — 4 200 PLN"
  16:00 — Payment Batch: przygotowanie paczki przelewów
  18:00 — Evening Summary: "Dziś zaksięgowano 5 faktur..."
  22:00 — Resource Optimizer: auto-unload nieużywanych modeli

Człowiek ZAWSZE jest decydentem. Agent wykonuje CAŁĄ pracę
przygotowawczą, analizuje i przedstawia opcje.

0.4. ResourceOptimizer — samooptymalizujące się zasoby
--------------------------------------------------------

  Monitorowanie przez psutil (z RAPORT_TECHNOLOGII):
    - RAM % (próg: 80%)
    - CPU % (próg: 70%)
    - Wolne miejsce na dysku
    - Liczba rdzeni CPU

  Auto-unload modeli:
    - Warunek 1: RAM > 80% → odładuj najmniej używane modele
    - Warunek 2: model idle > 30 min → odładuj
    - Faktyczne odładowanie przez ModelManager.unload(model_path)

  Dynamiczne skalowanie workerów:
    - Niskie obciążenie (< 40% RAM, < 30% CPU) → +1 worker (max 4)
    - Wysokie obciążenie (> 80% RAM lub > 70% CPU) → -1 worker (min 1)

  Implementacja:
    - ResourceOptimizer.should_unload_models(loaded_models) → list[str]
    - ResourceOptimizer.optimal_worker_count(current) → int
    - ResourceOptimizer.mark_model_used(model_name) → odświeża timestamp

  Integracja z Orchestratorem:
    orchestrator = AgentOrchestrator(...)
    await orchestrator.start()  # uruchamia ProactiveWorkflowScheduler
    await orchestrator.stop()   # zatrzymuje ProactiveWorkflowScheduler
    result = await orchestrator.execute_proactive_workflow("daily_briefing")
    schedule = orchestrator.get_proactive_schedule()
    stats = orchestrator.get_proactive_stats()

0b. GENIALNY POMYSŁ v5.2: Progressive Autonomy — Agent, Który Rośnie
================================================================================

0b.1. Agent, który rośnie z przedsiębiorcą
---------------------------------------------

Problem: Nawet z Action Cards, użytkownik wciąż klika to samo co tydzień.
Standardowa faktura od znanego kontrahenta → "Zaksięguj". Kolejny laptop
→ "Amortyzacja liniowa". Agent jest mądry, ale się NIE ADAPTUJE.

Rozwiązanie: Progressive Autonomy — agent obserwuje wzorce decyzyjne
konkretnego przedsiębiorcy i stopniowo przejmuje rutynowe decyzje.

  TYDZIEŃ 1:  0% autonomii — wszystkie decyzje przez Action Cards
  TYDZIEŃ 2: 40% — rutynowe faktury od znanych kontrahentów → AUTO_POST
  TYDZIEŃ 4: 70% — większość decyzji automatyczna
  MIESIĄC 3: 90%+ — przedsiębiorca widzi tylko podsumowanie

Cel: Decision Autonomy Score ≥ 90% w ciągu 3 miesięcy.

0b.2. Cztery wymiary uczenia
-------------------------------

  Vendor Trust:
    "Zawsze akceptujesz faktury od XYZ" → obniżony próg AUTO_POST
    - fully_trusted (≥20 faktur, ≥95% akceptacji) → threshold = 0.75
    - trusted (≥10 faktur, ≥90%) → threshold = 0.82
    - learning (≥3 faktury) → threshold = 0.88
    - new (<3) → threshold = 0.92 (domyślny)

  Category Preference:
    "Zawsze wybierasz amortyzację liniową dla IT"
    - Każda kategoria ma preferowaną akcję i opcję
    - Confidence rośnie z liczbą decyzji

  Amount Threshold:
    "Sprawdzasz ręcznie wszystko > 20k PLN"
    - 5 przedziałów kwotowych (micro, small, medium, large, xlarge)
    - Każdy z własnym should_auto_post

  Time Pattern:
    "W piątki odrzucasz wszystko"
    - Autonomy history śledzone codziennie
    - Trend: up / down / stable

0b.3. Decision Autonomy Score
-------------------------------

  AUTO_POST / (AUTO_POST + ASK_USER) × 100%

  Obliczany z ostatnich 7 dni (sliding window).
  Maksymalny poziom: 95% (zawsze 5% rezerwy dla wyjątków).

  Cotygodniowy raport:
    "📈 Autonomia: 73% (+2% od zeszłego tygodnia).
    Przejąłem 45 decyzji, Ty podjąłeś tylko 12.
    8 dojrzałych wzorców decyzyjnych."

0b.4. UserDecisionProfile — implementacja
--------------------------------------------

  Plik: nexus_ai/agents/user_decision_profile.py (~400 linii)

  Klasy msgspec:
    - DecisionPattern     — pojedynczy wzorzec (vendor_trust, category, amount)
    - VendorTrustProfile  — profil zaufania kontrahenta (trust_level, adaptive_threshold)
    - CategoryPreference  — preferencja kategorii (preferred_action, preferred_option)

================================================================================

0d.1. Cztery komponenty KnowledgeMesh
----------------------------------------

Agenci przestają działać w izolacji — tworzą SIATKĘ WIEDZY z Collective
Bayesian Field, Predictive Task Router i Cross-Agent Experience Replay.

  KnowledgeMesh (nexus_ai/agents/knowledge_mesh.py)
  ├── CollectiveBayesianField      — współdzielony Trust Score Beta(α,β)
  │                                   per vendor, aktualizowany przez
  │                                   wszystkie agenty
  ├── PredictiveTaskRouter         — dynamiczny DAG agentów
  │   ├── Trust < 0.30 → BLOCK (Circuit Breaker)
  │   ├── Trust ≥ 0.92 → SKIP QualityValidator
  │   └── Trust 0.30-0.92 → standardowy pipeline
  ├── CrossAgentExperienceReplay   — agenci publikują eventy,
  │                                   inne agenty reagują przez
  │                                   CROSS_AGENT_RULES
  └── MeshProtocol                 — route(), update_trust(),
                                      share_experience(),
                                      get_threshold_adjustments()

0d.2. Predykcyjny routing z Circuit Breaker
----------------------------------------------

  KnowledgeMesh.route(vendor_nip, amount) → RouteDecision:
    {
      target_agents: ["extraction", "quality", "analytics"],
      skip_agents: [],               # lub ["quality"] dla trusted
      threshold_adjustments: {"orchestrator": +0.05, "quality": +0.08},
      circuit_breaker_active: false  # true gdy Trust < 0.30
    }

  Circuit Breaker (Trust < 0.30):
    → Anuluj przetwarzanie
    → Wymagaj ręcznej weryfikacji
    → Wyślij alert do administratora

  SKIP (Trust ≥ 0.92):
    → Pomiń QualityValidator
    → Pomiń Cognitive Audit Trail (vendor doskonale znany)
    → Obniżone progi dla Extraction

0d.3. CROSS_AGENT_RULES — reguły propagacji doświadczeń
----------------------------------------------------------

  CrossAgentExperienceReplay definiuje reguły:

    extraction.low_consensus → QualityValidator: INCREASE_SCRUTINY
      → "OCR nie zgadza się dla tego vendora — sprawdź dokładniej"

    quality.tax_error → Extraction: HIGH_SCRUTINY
      → "Wykryto błąd podatkowy — zwiększ precyzję OCR dla tego NIP"

    quality.tax_error → Orchestrator: LOWER_AUTO_POST_THRESHOLD
      → "Ten vendor ma błędy — podnieś próg AUTO_POST"

    quality.fraud_detected → ALL: HIGH_ALERT
      → "Wykryto fraud! Wszystkie agenty na najwyższą czujność"

    analytics.anomaly_detected → QualityValidator: INCREASE_SCRUTINY
      → "Anomalia finansowa — sprawdź dokładniej"

    analytics.anomaly_detected → Orchestrator: REVIEW_REQUIRED
      → "Anomalia wymaga przeglądu"

0d.4. Integracje: Extraction + QualityValidator + Analytics (5/5 agentów)
---------------------------------------------------------------------------

  AgentDataExtraction (v5.3 → v5.5):
    - _publish_mesh_events() po każdej ekstrakcji
    - Analizuje macierz walidacji krzyżowej 4×4
    - Konsensus < 75% → obniża Trust + 'extraction.low_consensus' (v5.5: usunięto and confidence < 0.7)
    - Confidence ≥ 85% → podnosi Trust Score

  AgentQualityValidator (v5.3):
    - _publish_mesh_events() po każdej walidacji
    - Tax ERROR → obniża Trust + 'quality.tax_error'
    - Fraud ERROR → obniża Trust + 'quality.fraud_detected'
    - ESG ERROR → 'analytics.anomaly_detected'
    - All OK → podnosi Trust Score

  AgentAnalytics (v5.5 — NOWY):
    - _publish_mesh_events() na końcu analyze()
    - 4 tiery publikacji:
      1. 🔴 Z-score > 3σ (high) → 'analytics.anomaly_detected' → QV TRIGGER_DEEP_CHECK + Orch LOWER_THRESHOLD + 1× update_trust(correct=False)
      2. 🟡 Z-score 2-3σ (medium) → event bez obniżania Trust
      3. ⚠️ Risk flags (overdue, high_amount) → event + update_trust dla overdue
      4. 💰 Cashflow/forecast → event z detection_method="cashflow_analysis"

    - Zgodność z CROSS_AGENT_RULES w knowledge_mesh.py

0e.2. MultiModelEnsemble — ≥2 modele + diversity check
---------------------------------------------------------

  Implementacja w MultiModelEnsemble (decision_trace.py):

    Głosy:
    - Actor (Granite 3.2 3B) — główny decydent
    - Guardian (Granite Guardian 0.5B) — strażnik merytoryczny
    - Handbook (DynamicErrorHandbook) — few-shot examples

    Diversity check:
    - Jeśli wszystkie modele dają ten sam werdykt → ostrzeżenie
      o braku dywersyfikacji (all_same_verdict = true)
    - Shannon entropy: 0.0 = brak dywersyfikacji
    - Wymagane ≥2 modele (MIN_MODELS = 2)

    Fallback:
    - Jeśli <2 modele dostępne → requires_human = true
    - Weighted voting: wagi per model (historyczna precyzja)

0e.3. ConfidenceCalibrator — Platt Scaling
---------------------------------------------

  Implementacja w ConfidenceCalibrator (decision_trace.py):

    Problem: Model mówi 95% confidence, ale w rzeczywistości ma 80%
    Rozwiązanie: Platt Scaling online (SGD z decay rate 0.99)

    calibrated = sigmoid(a × raw + b)
    a, b — parametry uczone online po każdej decyzji

    Reliability diagram:
    - 10-binowy wykres kalibracji
    - predicted vs actual accuracy per bin
    - Perfect calibration: diagonal line

    Metoda update(raw_trust, actual_outcome):
    - Aktualizuje a, b przez SGD
    - decay_rate = 0.99 (starsze próbki mają mniejszą wagę)

0e.4. AgentTelemetryStore — DuckDB + Parquet
-----------------------------------------------

  AgentTelemetryStore (nexus_ai/agents/telemetry_store.py):

    5 tabel DuckDB:
    - decisions    — każda decyzja (id, vendor, amount, mode, trust, ...)
    - corrections  — każda korekta (id, decision_id, reason, ...)
    - routes       — każdy routing (id, decision_id, target_agents, ...)
    - traces       — każdy trace (id, decision_id, span_count, ...)

1.2. JEDEN poziom automatyzacji (DecisionMode)
-----------------------------------------------

System używa JEDNEGO poziomu automatyzacji zamiast czterech (L0-L3):

  DecisionMode.AUTO_POST (Trust ≥ 0.92 adaptive):
    Agent samodzielnie księguje, wysyła do KSeF, planuje płatności.
    Użytkownik tylko informowany (dashboard, powiadomienie).

  DecisionMode.SUGGEST (Trust ≥ 0.75 adaptive):
    Agent proponuje decyzję z uzasadnieniem (2-5 opcji).
    Użytkownik zatwierdza jednym kliknięciem lub modyfikuje.

  DecisionMode.ASK_USER (Trust < 0.75):
    Agent przedstawia problem z kontekstem i rekomendacjami.
    Użytkownik podejmuje ostateczną decyzję.

Człowiek ZAWSZE jest decydentem. Agent wykonuje pracę i przedstawia opcje.
To agent steruje aplikacją — człowiek podejmuje kluczowe decyzje.

IMPLEMENTACJA (msgspec.StrEnum, zgodnie z kodem):

  class DecisionMode(enum.StrEnum):
      AUTO_POST = "auto_post"
      SUGGEST   = "suggest"
      ASK_USER  = "ask_user"

Próg AUTO_POST jest adaptacyjny (Bayesian per kontrahent):
  auto_post_threshold = 0.92 - (α-β)/(α+β) × 0.1

  Gdzie: α = poprawne decyzje, β = błędne decyzje.

Przykład:
  Znany kontrahent (100 faktur, 98 OK): auto_post = 0.824
  Nowy kontrahent (5 faktur, 4 OK):     auto_post = 0.86
  Podejrzany (10 faktur, 6 OK):         auto_post = 0.90

1.3. GENIALNY POMYSŁ #1: Cognitive Audit Trail (warstwa deterministyczna)
---------------------------------------------------------------------------

Każda korekta użytkownika tworzy blok poznawczy (CognitiveProofBlock)
w łańcuchu dowodowym. Łańcuch SHA-256 staje się AKTYWNYM systemem
uczącym się, nie tylko pasywnym rejestrem:

  DECYZJA → KOREKTA → EMBEDDING 768d (sqlite-vec) → k-NN →
  → PO 10 KOREKTACH TEGO SAMEGO TYPU → AUTO-NAPRAWA REGUŁ OPA

Implementacja w ContinuousLearningProvider (base.py):

  class CognitiveProofBlock(Struct, kw_only=True):
      correction_id: str
      decision_id: str
      agent: str
      predicted: dict[str, Any]
      corrected: dict[str, Any]
      embedding: list[float]       # 768d w sqlite-vec
      similar_count: int = 1       # liczba podobnych korekt
      auto_patched: bool = False   # czy auto-naprawiono OPA

  # Metody:
  - record_feedback(correction_embedding=...) → dodaje CognitiveProofBlock
  - find_similar_corrections() → k-NN (cosine) w sqlite-vec
  - should_auto_patch_opa() → True po min_samples_for_opa_update (10)

Przykład:
  1. User koryguje stawkę VAT z 23% na 8% dla kategorii "spożywcze"
  2. Embedding faktury (768d) zapisany w CognitiveProofBlock
  3. Kolejna faktura "spożywcza" → k-NN → podobny embedding
  4. System automatycznie proponuje 8% VAT
  5. Po 10 korektach → reguła OPA w tax/rules.rego auto-aktualizowana

1.4. GENIALNY POMYSŁ #2: Dynamiczny Podręcznik Błędów (warstwa probabilistyczna)
---------------------------------------------------------------------------------

Online few-shot learning — model Granite 3.2 uczy się z każdej korekty
BEZ fine-tuningu, BEZ trenowania, tylko przez smart prompt engineering:

  KOREKTA → DuckDB error_handbook → kwerenda przed inferencją →
  → "Podręcznik Błędów z Przeszłości" w prompcie →
  → Granite 3.2 widzi: ❌ błędna decyzja → ✅ poprawna decyzja

Priorytetyzacja przykładów:
  Level 1: Ten sam NIP + kategoria (exact match) — vendor-specific learning
  Level 2: Ten sam NIP (ogólny kontekst kontrahenta)
  Level 3: Ta sama kategoria + podobna kwota (±50%)
  Level 4: Najczęściej korygowane globalnie (top-N)

Implementacja w DynamicErrorHandbook (error_handbook.py):

  class HandbookExample(Struct, kw_only=True):
      id: str
      decision_id: str
      agent: str
      vendor_nip: str
      category: str
      amount_gross: int           # w groszach
      decision_snapshot: str      # JSON: co agent zdecydował
      correct_decision: str       # JSON: co było poprawne
      reason: str                 # dlaczego user skorygował
      timestamp: str              # ISO 8601
      embedding: list[float]      # 768d — opcjonalnie

  class HandbookQuery(Struct, kw_only=True):
      vendor_nip: str | None = None
      category: str | None = None
      amount_gross: int = 0
      max_examples: int = 3       # max przykładów do promptu

  # DuckDB: CREATE TABLE error_handbook (... FLOAT[768])
  # Metody:
  - record_correction() → INSERT do DuckDB
  - query_relevant() → priorytetyzowane SELECT z DuckDB
  - build_few_shot_prompt() → formatowanie "Podręcznik Błędów"

Im więcej korekt, tym mądrzejszy model — bez żadnego fine-tuningu.

2.2. Gwarancje dostarczenia: At-least-once + DLQ
--------------------------------------------------

  AT-LEAST-ONCE DELIVERY:
    Każda wiadomość trwale zapisana w JetStream przed dostarczeniem.
    Manual ack po przetworzeniu — worker nie ack → redelivery.
    Ochrona przed duplikatami: task_id = blake2b(task_name + kwargs).
    Duplicate window: 2 minuty (identyczne zadania odrzucane).

  DEAD LETTER QUEUE:
    Po 3 nieudanych próbach → wiadomość do DLQ.
    DLQ przechowuje: oryginalna wiadomość + stack trace + próby.
    Retry z backoffem: 1s → 2s → 4s (exponential, z jitterem).
    Administrator: przegląd, retry, poprawa, odrzucenie.

  MAX ACK PENDING:
    Dynamicznie dostosowywany przez WorkerGuard.
    Przy wysokim CPU/RAM → zmniejszany (max 5).
    Przy niskim CPU/RAM → zwiększany (max 15).

2.3. Priority Queue z QoS
---------------------------

  Każde zadanie ma priorytet (1-10, 1 = najwyższy):

    1  — Krytyczne: błąd systemu, awaria KSeF, deadline podatkowy
    2  — Pilne: płatność z skontem, faktura od kluczowego klienta
    3  — Wysoki: nowa faktura > 50,000 PLN, podejrzenie oszustwa
    4-5 — Normalny: standardowa faktura, zapytanie analityczne
    6-7 — Niski: raport tygodniowy, aktualizacja wzorców
    8-9 — Background: aktualizacja modeli, regeneracja embeddingów
    10 — Idle: heartbeat, health check

  QoS (Quality of Service):
    P0-P1: dedicated 1 worker thread (z 2 dostępnych)
    P2-P3: max 50% worker capacity
    P4-P7: remaining capacity
    P8-P10: tylko gdy idle

2.4. Circuit Breaker (stamina) i retry z backoffem
----------------------------------------------------

  Implementacja przez stamina (z RAPORT_TECHNOLOGII):

    @stamina.retry(
        on=(NatsError, TimeoutError),
        attempts=3,
        timeout=30.0,
    )
    async def publish_with_retry(topic: str, data: bytes) -> None:
        ...

  Circuit Breaker:
    - Próg: 5 błędów w ciągu 30 sekund
    - Open: 60 sekund cooldown
    - Half-open: po 60s przepuść 1 request testowy
    - Jeśli OK → close. Jeśli błąd → open na 120s.
    - Stan publikowany na: system.circuit-breakers.{agent}

KLUCZOWE MECHANIZMY ENTERPRISE:

  1. DYNAMICZNY TRUST SCORE (Bayesian Update)
     - Trust Score = E[θ|D] = α / (α + β)
     - Prior: Beta(α₀=1, β₀=1), Posterior: Beta(α₀+Σy, β₀+n-Σy)
     - Aktualizowany po każdej decyzji i każdej korekcie

  2. COGNITIVE AUDIT TRAIL
     - Każda korekta → embedding 768d w sqlite-vec
     - k-NN (cosine) → podobne korekty z przeszłości
     - Po 10 korektach tego samego typu → auto-naprawa reguł OPA

  3. DYNAMICZNY PODRĘCZNIK BŁĘDÓW (few-shot learning)
     - DuckDB error_handbook → 3 najlepsze przykłady przed inferencją
     - "Podręcznik Błędów z Przeszłości" wstrzyknięty w prompt Granite 3.2
     - Model uczy się z każdej korekty BEZ fine-tuningu

  4. DECISION CACHE (diskcache + sqlite-vec k-NN)
     - Każda decyzja wektoryzowana w sqlite-vec (768d)
     - Podobna faktura → podobna decyzja (k-NN, k=5)
     - max_distance < 0.1 → użyj cache
     - Oszczędność: ~80% decyzji bez inferencji LLM

  5. ADAPTIVE THRESHOLDS
     - auto_post = 0.92 - (α-β)/(α+β) × 0.1
     - Dla znanych kontrahentów (α>>β) → niższy próg
     - Dla nowych → wyższy próg (conservative)
     - Dynamiczne per kontrahent

  6. PROOF CHAIN SHA-256 (nexus-crypto)
     - Każda decyzja → block w łańcuchu kryptograficznym
     - hash = SHA256(previous + decision + timestamp)
     - Niepodważalny dowód dla US

  7. 4-EYES PRINCIPLE
     - Obowiązkowy dla kwot > 50,000 PLN
     - Dwie niezależne weryfikacje (Guardian + QualityValidator)

4. DECISION ENGINE — Wielowarstwowy Silnik Decyzyjny
================================================================================

4.1. Strefy decyzyjne (Dynamic Thresholds)
--------------------------------------------

Thresholds NIE są stałe — adaptują się Bayesian per kontrahent:

  auto_post = 0.92 - adjustment
  review    = 0.75 - adjustment
  adjustment = (α_vendor - β_vendor) / (α_vendor + β_vendor) × 0.1

Gdzie:
  α_vendor = poprawne decyzje dla tego kontrahenta
  β_vendor = błędne decyzje dla tego kontrahenta

Przykład:
  Znany kontrahent (100 faktur, 98 poprawnych):
  α=98, β=2 → adjustment = 0.096, auto_post = 0.92 - 0.096 = 0.824

  Nowy kontrahent (5 faktur, 4 poprawne):
  α=4, β=1 → adjustment = 0.06, auto_post = 0.92 - 0.06 = 0.86

  Podejrzany kontrahent (10 faktur, 6 poprawnych):
  α=6, β=4 → adjustment = 0.02, auto_post = 0.92 - 0.02 = 0.90

Mapowanie strefy na DecisionMode (implementacja w orchestrator.py):

  AUTO_POST (Trust ≥ auto_post)    → DecisionMode.AUTO_POST
  REVIEW    (Trust ≥ review)        → DecisionMode.SUGGEST
  BLOCK     (Trust < review)        → DecisionMode.ASK_USER
  ESCALATED (manualna eskalacja)   → DecisionMode.ASK_USER

4.2. Konsensus między agentami (Weighted Voting)
--------------------------------------------------

Ostateczna decyzja = ważony głos dwóch niezależnych głosów:

  AgentOrchestrator:     waga = 0.40  (decyzja wykonawcza)
  AgentQualityValidator: waga = 0.60  (niezależny audytor)

Jeśli consensus > 0.66 → akceptuj.
Jeśli uncertainty > 0.3 → eskalacja do człowieka.

Implementacja (zgodnie z msgspec.Struct w models.py):

  class ConfidenceVote(Struct, kw_only=True):
      agent: str
      weight: float = 0.0        # historyczna precyzja agenta
      vote: str                   # POST | REVIEW | BLOCK
      confidence: float = 0.0
      weighted_vote: float = 0.0  # weight × confidence

  class VotingResult(Struct, kw_only=True):
      votes: list[ConfidenceVote]
      total_weight: float
      winner: str
      consensus: bool = False     # True jeśli > 0.66 majority
      uncertainty: float = 0.0

4.4. Proof Chain SHA-256 (niepodważalny audyt)
------------------------------------------------

Implementacja przez nexus-crypto (z RAPORT_TECHNOLOGII):

  from nexus_crypto import Sha256Hasher

  class ProofChain:
      def __init__(self):
          self.chain: list[ProofBlock] = []
          self.load_from_db()  # DuckDB: proof_chain

      def add_block(self, decision: AgentDecision) -> str:
          previous_hash = self.chain[-1].hash if self.chain else "0"*64
          block_data = {
              "index": len(self.chain),
              "decision_id": decision.decision_id,
              "decision": msgspec.json.encode(decision),
              "timestamp": pendulum.now("UTC").isoformat(),
              "previous_hash": previous_hash,
          }
          hasher = Sha256Hasher()
          hasher.update(msgspec.json.encode(block_data))
          return hasher.hexdigest()

5.4. Bayesian Trust Score z propagacją
----------------------------------------

Trust Score = posterior Beta distribution:

  Prior:       Beta(α₀=1, β₀=1)          # uniform
  Likelihood:  Bern(y|θ)                 # y ∈ {0,1}
  Posterior:   Beta(α₀+Σy, β₀+n-Σy)

  Trust Score = E[θ|D] = α / (α + β)
  Confidence  = 1 - Var[θ|D]

Gdzie: α = poprawne decyzje, β = błędne decyzje.

Implementacja (czysty Python, brak zależności):

  class BayesianTrustScore:
      def __init__(self, alpha: float = 1.0, beta: float = 1.0):
          self.alpha = alpha
          self.beta = beta

      def update(self, correct: bool) -> None:
          if correct: self.alpha += 1
          else: self.beta += 1

      @property
      def trust_score(self) -> float:
          return self.alpha / (self.alpha + self.beta)

      @property
      def confidence(self) -> float:
          total = self.alpha + self.beta
          variance = (self.alpha * self.beta) / (total**2 * (total + 1))
          return max(0.0, 1.0 - variance * 12)

  6. diskcache zastąpiony — usunięty z zależności

================================================================================
DODATEK A: GENIALNY POMYSŁ v5.1: Action Cards — "Zasada 1-Click CFO"
================================================================================

9.1. Filozofia: Agent = Ekspert, Człowiek = Decydent
-------------------------------------------------------

Problem: Tradycyjne aplikacje księgowe przypominają Excela — 80 parametrów,
listy rozwijane, formularze. Przedsiębiorca nie jest księgowym.

Rozwiązanie: Action Cards — jedna decyzja = jedna karta = jeden klik.

  Agent wykonuje 95% pracy:
  - OCR + walidacja krzyżowa (4 silniki)
  - Weryfikacja kontrahenta (Biała Lista MF, GUS BIR)
  - Kalkulacja podatków (OPA/Rego)
  - Przygotowanie księgowań (TigerBeetle double-entry)
  - Spakowanie wszystkiego w hidden_payload każdego przycisku

  Człowiek widzi:
  - 1-2 zdania podsumowania (bez żargonu)
  - 2-4 przyciski z prostymi etykietami
  - Trust Score (zielony/żółty/czerwony)

  Człowiek klika 1 przycisk → Agent wykonuje resztę.

9.2. Struktury danych (msgspec.Struct)
-----------------------------------------

  ActionCardOption:
    - option_id: str
    - label: str                   # Tekst przycisku (max 40 znaków)
    - description: str             # Opis dla laika
    - is_recommended: bool         # Zielony przycisk = rekomendacja AI
    - action_type: str             # confirm | alternative | reject | escalate
    - hidden_payload: dict         # PEŁNE parametry księgowe (ukryte)
    - trust_impact: float          # Wpływ na Trust Score

  ActionCard:
    - card_id: str
    - decision_id: str             # Referencja do AgentDecision
    - title: str                   # Nagłówek — 1 zdanie
    - summary: str                 # TL;DR — 2-3 zdania dla laika
    - options: list[ActionCardOption]  # 2-4 przyciski
    - trust_score: float           # 0.0-1.0
    - urgency: str                 # critical | high | normal | low
    - context: dict                # Kwota, kontrahent, data (do UI)

  ActionCardFeed:
    - cards: list[ActionCard]      # "Skrzynka decyzyjna"
    - total_pending: int
    - urgent_count: int
    - greeting: str                # Powitanie NL

  ActionCardResponse:
    - card_id: str
    - decision_id: str
    - selected_option_id: str      # Który przycisk kliknięto
    - action_type: str             # Przekazane z ActionCardOption
    - user_comment: str

9.3. ActionCardGenerator
--------------------------

  Klasa w nexus_ai/agents/proactive_workflow.py (~300 linii).

  Metody:
    generate_action_card(decision, document_type, urgency) → ActionCard
      - Wybiera szablon (6 typów)
      - Buduje podsumowanie NL (bez żargonu)
      - Pakuje pełne dane księgowe w hidden_payload każdego przycisku

    generate_card_from_decision(decision) → ActionCard (async)
      - Wersja asynchroniczna z opcjonalnym ulepszeniem przez Qwen3-Nano
      - Model tłumaczy surowe dane na język laika
      - Prompt zabrania żargonu (WN, MA, PKWiU, MPP, JPK)

    build_daily_feed(pending_decisions) → ActionCardFeed
      - Buduje "skrzynkę decyzyjną" na dziś
      - Sortuje wg priorytetu (critical → high → normal)
      - Generuje spersonalizowane powitanie

  Szablony decyzji (6):
    INVOICE_STANDARD, INVOICE_HIGH_AMOUNT, INVOICE_NEW_VENDOR,
    TAX_ALERT, ASSET_CLASSIFICATION, PAYMENT_BATCH

  Każdy szablon definiuje 2-4 opcje z action_type:
    confirm (rekomendowane), alternative, reject, escalate

9.4. Integracja z AgentOrchestrator
-------------------------------------

  Nowe metody w orchestrator.py:

    card_generator: ActionCardGenerator          # Property
    generate_action_card(decision, doc_type)      # 1 karta z decyzji
    build_daily_decision_feed() → ActionCardFeed  # Feed na dziś
    handle_user_card_response(card_id, ...)       # Obsługa kliknięcia

  Flow:
    1. process_invoice() → AgentDecision (SUGGEST/ASK_USER)
    2. generate_action_card(decision) → ActionCard
    3. build_daily_decision_feed() → ActionCardFeed → NATS ui.feed.pending
    4. UI (Flet) wyświetla karty jedna po drugiej
    5. Użytkownik klika przycisk → handle_user_card_response()
       - confirm → record_user_feedback (Cognitive Audit Trail)
       - reject  → record_user_feedback (BLOCK)
       - alternative → karta zostaje w pending (użytkownik może wrócić)
    6. Agent wykonuje hidden_payload

  Topiki NATS:
    ui.feed.pending  — publikacja feedu kart
    ui.feed.action   — odpowiedź użytkownika

1.2. JEDEN poziom automatyzacji (DecisionMode)
-----------------------------------------------

System używa JEDNEGO poziomu automatyzacji zamiast czterech (L0-L3):

  DecisionMode.AUTO_POST (Trust ≥ 0.92 adaptive):
    Agent samodzielnie księguje, wysyła do KSeF, planuje płatności.
    Użytkownik tylko informowany (dashboard, powiadomienie).

  DecisionMode.SUGGEST (Trust ≥ 0.75 adaptive):
    Agent proponuje decyzję z uzasadnieniem (2-5 opcji).
    Użytkownik zatwierdza jednym kliknięciem lub modyfikuje.

  DecisionMode.ASK_USER (Trust < 0.75):
    Agent przedstawia problem z kontekstem i rekomendacjami.
    Użytkownik podejmuje ostateczną decyzję.

Człowiek ZAWSZE jest decydentem. Agent wykonuje pracę i przedstawia opcje.
To agent steruje aplikacją — człowiek podejmuje kluczowe decyzje.

IMPLEMENTACJA (msgspec.StrEnum, zgodnie z kodem):

  class DecisionMode(enum.StrEnum):
      AUTO_POST = "auto_post"
      SUGGEST   = "suggest"
      ASK_USER  = "ask_user"

Próg AUTO_POST jest adaptacyjny (Bayesian per kontrahent):
  auto_post_threshold = 0.92 - (α-β)/(α+β) × 0.1

  Gdzie: α = poprawne decyzje, β = błędne decyzje.

Przykład:
  Znany kontrahent (100 faktur, 98 OK): auto_post = 0.824
  Nowy kontrahent (5 faktur, 4 OK):     auto_post = 0.86
  Podejrzany (10 faktur, 6 OK):         auto_post = 0.90

1.3. GENIALNY POMYSŁ #1: Cognitive Audit Trail (warstwa deterministyczna)
---------------------------------------------------------------------------

Każda korekta użytkownika tworzy blok poznawczy (CognitiveProofBlock)
w łańcuchu dowodowym. Łańcuch SHA-256 staje się AKTYWNYM systemem
uczącym się, nie tylko pasywnym rejestrem:

  DECYZJA → KOREKTA → EMBEDDING 768d (sqlite-vec) → k-NN →
  → PO 10 KOREKTACH TEGO SAMEGO TYPU → AUTO-NAPRAWA REGUŁ OPA

Implementacja w ContinuousLearningProvider (base.py):

  class CognitiveProofBlock(Struct, kw_only=True):
      correction_id: str
      decision_id: str
      agent: str
      predicted: dict[str, Any]
      corrected: dict[str, Any]
      embedding: list[float]       # 768d w sqlite-vec
      similar_count: int = 1       # liczba podobnych korekt
      auto_patched: bool = False   # czy auto-naprawiono OPA

  # Metody:
  - record_feedback(correction_embedding=...) → dodaje CognitiveProofBlock
  - find_similar_corrections() → k-NN (cosine) w sqlite-vec
  - should_auto_patch_opa() → True po min_samples_for_opa_update (10)

Przykład:
  1. User koryguje stawkę VAT z 23% na 8% dla kategorii "spożywcze"
  2. Embedding faktury (768d) zapisany w CognitiveProofBlock
  3. Kolejna faktura "spożywcza" → k-NN → podobny embedding
  4. System automatycznie proponuje 8% VAT
  5. Po 10 korektach → reguła OPA w tax/rules.rego auto-aktualizowana

1.4. GENIALNY POMYSŁ #2: Dynamiczny Podręcznik Błędów (warstwa probabilistyczna)
---------------------------------------------------------------------------------

Online few-shot learning — model Granite 3.2 uczy się z każdej korekty
BEZ fine-tuningu, BEZ trenowania, tylko przez smart prompt engineering:

  KOREKTA → DuckDB error_handbook → kwerenda przed inferencją →
  → "Podręcznik Błędów z Przeszłości" w prompcie →
  → Granite 3.2 widzi: ❌ błędna decyzja → ✅ poprawna decyzja

Priorytetyzacja przykładów:
  Level 1: Ten sam NIP + kategoria (exact match) — vendor-specific learning
  Level 2: Ten sam NIP (ogólny kontekst kontrahenta)
  Level 3: Ta sama kategoria + podobna kwota (±50%)
  Level 4: Najczęściej korygowane globalnie (top-N)

Implementacja w DynamicErrorHandbook (error_handbook.py):

  class HandbookExample(Struct, kw_only=True):
      id: str
      decision_id: str
      agent: str
      vendor_nip: str
      category: str
      amount_gross: int           # w groszach
      decision_snapshot: str      # JSON: co agent zdecydował
      correct_decision: str       # JSON: co było poprawne
      reason: str                 # dlaczego user skorygował
      timestamp: str              # ISO 8601
      embedding: list[float]      # 768d — opcjonalnie

  class HandbookQuery(Struct, kw_only=True):
      vendor_nip: str | None = None
      category: str | None = None
      amount_gross: int = 0
      max_examples: int = 3       # max przykładów do promptu

  # DuckDB: CREATE TABLE error_handbook (... FLOAT[768])
  # Metody:
  - record_correction() → INSERT do DuckDB
  - query_relevant() → priorytetyzowane SELECT z DuckDB
  - build_few_shot_prompt() → formatowanie "Podręcznik Błędów"

Im więcej korekt, tym mądrzejszy model — bez żadnego fine-tuningu.

1.5. Mapa interakcji: człowiek ↔ agent ↔ aplikacja
-----------------------------------------------------

Użytkownik (przedsiębiorca) wchodzi w interakcję przez:
  A) Dashboard (Flet UI) — podsumowania, alerty, decyzje
  B) Panel decyzyjny — decyzje oczekujące (SUGGEST/ASK_USER)
  C) Czat z Komunikatorem (Qwen3-Nano) — pytania NL
  D) Raporty automatyczne (AgentAnalytics) — dzienne/tyg./mies.

System (agenci) samodzielnie:
  a) Pobiera faktury (email, upload, KSeF API, folder sieciowy)
  b) Ekstrahuje dane (4 silniki OCR + walidacja krzyżowa)
  c) Klasyfikuje wydatki (konta księgowe, stawki VAT, PKWiU)
  d) Sprawdza kontrahentów (Biała Lista MF, GUS BIR)
  e) Wysyła do KSeF (FA(1), FA(2) — obowiązkowy e-spis)
  f) Księguje w TigerBeetle (double-entry)
  g) Planuje płatności (priorytety, skonta, terminy, MPP)
  h) Uzgodnia salda (DuckDB reconciliation)
  i) Generuje deklaracje (JPK_V7, VAT-7, PIT/CIT)
  j) Monitoruje terminy (ZUS, US, KSeF, skonta)
  k) Wykrywa anomalie (oszustwa, błędy, ryzyko, karuzele VAT)
  l) Prognozuje cash flow (90 dni, 3 scenariusze)
  m) Optymalizuje podatki (symulacje "co by było, gdyby")
  n) Amortyzuje środki trwałe
  o) Uczy się z każdej korekty na DWÓCH WARSTWACH jednocześnie

2.2. Gwarancje dostarczenia: At-least-once + DLQ
--------------------------------------------------

  AT-LEAST-ONCE DELIVERY:
    Każda wiadomość trwale zapisana w JetStream przed dostarczeniem.
    Manual ack po przetworzeniu — worker nie ack → redelivery.
    Ochrona przed duplikatami: task_id = blake2b(task_name + kwargs).
    Duplicate window: 2 minuty (identyczne zadania odrzucane).

  DEAD LETTER QUEUE:
    Po 3 nieudanych próbach → wiadomość do DLQ.
    DLQ przechowuje: oryginalna wiadomość + stack trace + próby.
    Retry z backoffem: 1s → 2s → 4s (exponential, z jitterem).
    Administrator: przegląd, retry, poprawa, odrzucenie.

  MAX ACK PENDING:
    Dynamicznie dostosowywany przez WorkerGuard.
    Przy wysokim CPU/RAM → zmniejszany (max 5).
    Przy niskim CPU/RAM → zwiększany (max 15).

2.3. Priority Queue z QoS
---------------------------

  Każde zadanie ma priorytet (1-10, 1 = najwyższy):

    1  — Krytyczne: błąd systemu, awaria KSeF, deadline podatkowy
    2  — Pilne: płatność z skontem, faktura od kluczowego klienta
    3  — Wysoki: nowa faktura > 50,000 PLN, podejrzenie oszustwa
    4-5 — Normalny: standardowa faktura, zapytanie analityczne
    6-7 — Niski: raport tygodniowy, aktualizacja wzorców
    8-9 — Background: aktualizacja modeli, regeneracja embeddingów
    10 — Idle: heartbeat, health check

  QoS (Quality of Service):
    P0-P1: dedicated 1 worker thread (z 2 dostępnych)
    P2-P3: max 50% worker capacity
    P4-P7: remaining capacity
    P8-P10: tylko gdy idle

2.4. Circuit Breaker (stamina) i retry z backoffem
----------------------------------------------------

  Implementacja przez stamina (z RAPORT_TECHNOLOGII):

    @stamina.retry(
        on=(NatsError, TimeoutError),
        attempts=3,
        timeout=30.0,
    )
    async def publish_with_retry(topic: str, data: bytes) -> None:
        ...

  Circuit Breaker:
    - Próg: 5 błędów w ciągu 30 sekund
    - Open: 60 sekund cooldown
    - Half-open: po 60s przepuść 1 request testowy
    - Jeśli OK → close. Jeśli błąd → open na 120s.
    - Stan publikowany na: system.circuit-breakers.{agent}

2.5. OpenTelemetry tracing na każdej wiadomości
--------------------------------------------------

  Każda wiadomość NATS zawiera:
    message.headers["trace_id"] = generate_trace_id()
    message.headers["span_id"] = generate_span_id()

  OpenTelemetry:
    - Spany: publish, subscribe, process, ack
    - Metryki: messages/sec, latency p99, error rate per agent
    - Export: DuckDB Parquet (offline) + OTLP (online)
    - Trace: od requestu do finalnej decyzji (end-to-end)

3.1. AgentOrchestrator — Centralny Mózg i Wirtualny CFO
=========================================================

ROLA:
    Naczelny dyrektor finansowy (CFO). Koordynuje 4 agentów wykonawczych,
    podejmuje ostateczne decyzje, komunikuje się z użytkownikiem.

MODELE (13 modeli GGUF łącznie, ładowane leniwie przez llama-cpp-python):
  - Granite 3.2 3B (GGUF, IQ4_XS) — Główny Decydent (Actor) ~2.4 GB RAM
  - Granite Guardian 0.5B (GGUF, Q4_K_M) — Strażnik Merytoryczny ~300 MB
  - Qwen3-Nano 0.5B (GGUF, Q4_K_M) — Komunikator (NL→user) ~400 MB

  RAM stały: ~2.98 GB

KLUCZOWE MECHANIZMY ENTERPRISE:

  1. DYNAMICZNY TRUST SCORE (Bayesian Update)
     - Trust Score = E[θ|D] = α / (α + β)
     - Prior: Beta(α₀=1, β₀=1), Posterior: Beta(α₀+Σy, β₀+n-Σy)
     - Aktualizowany po każdej decyzji i każdej korekcie

  2. COGNITIVE AUDIT TRAIL
     - Każda korekta → embedding 768d w sqlite-vec
     - k-NN (cosine) → podobne korekty z przeszłości
     - Po 10 korektach tego samego typu → auto-naprawa reguł OPA

  3. DYNAMICZNY PODRĘCZNIK BŁĘDÓW (few-shot learning)
     - DuckDB error_handbook → 3 najlepsze przykłady przed inferencją
     - "Podręcznik Błędów z Przeszłości" wstrzyknięty w prompt Granite 3.2
     - Model uczy się z każdej korekty BEZ fine-tuningu

  4. DECISION CACHE (diskcache + sqlite-vec k-NN)
     - Każda decyzja wektoryzowana w sqlite-vec (768d)
     - Podobna faktura → podobna decyzja (k-NN, k=5)
     - max_distance < 0.1 → użyj cache
     - Oszczędność: ~80% decyzji bez inferencji LLM

  5. ADAPTIVE THRESHOLDS
     - auto_post = 0.92 - (α-β)/(α+β) × 0.1
     - Dla znanych kontrahentów (α>>β) → niższy próg
     - Dla nowych → wyższy próg (conservative)
     - Dynamiczne per kontrahent

  6. PROOF CHAIN SHA-256 (nexus-crypto)
     - Każda decyzja → block w łańcuchu kryptograficznym
     - hash = SHA256(previous + decision + timestamp)
     - Niepodważalny dowód dla US

  7. 4-EYES PRINCIPLE
     - Obowiązkowy dla kwot > 50,000 PLN
     - Dwie niezależne weryfikacje (Guardian + QualityValidator)

PROCES DECYZYJNY (7 kroków):
  Krok 1: Decision Cache — k-NN w podobnych decyzjach (80% pomija dalsze kroki)
  Krok 2: AgentDataExtraction → ekstrakcja danych (4 silniki OCR)
  Krok 3: Dynamiczny Podręcznik Błędów → pobierz 3 podobne korekty z DuckDB
  Krok 4: Actor (Granite 3.2) + Guardian (Granite Guardian) → ocena z few-shot
  Krok 5: AgentQualityValidator → walidacja (tax + fraud + ESG + liquidity)
  Krok 6: Weighted Voting → konsensus (Orchestrator 0.40 + QualityValidator 0.60)

4. DECISION ENGINE — Wielowarstwowy Silnik Decyzyjny
================================================================================

4.1. Strefy decyzyjne (Dynamic Thresholds)
--------------------------------------------

Thresholds NIE są stałe — adaptują się Bayesian per kontrahent:

  auto_post = 0.92 - adjustment
  review    = 0.75 - adjustment
  adjustment = (α_vendor - β_vendor) / (α_vendor + β_vendor) × 0.1

Gdzie:
  α_vendor = poprawne decyzje dla tego kontrahenta
  β_vendor = błędne decyzje dla tego kontrahenta

Przykład:
  Znany kontrahent (100 faktur, 98 poprawnych):
  α=98, β=2 → adjustment = 0.096, auto_post = 0.92 - 0.096 = 0.824

  Nowy kontrahent (5 faktur, 4 poprawne):
  α=4, β=1 → adjustment = 0.06, auto_post = 0.92 - 0.06 = 0.86

  Podejrzany kontrahent (10 faktur, 6 poprawnych):
  α=6, β=4 → adjustment = 0.02, auto_post = 0.92 - 0.02 = 0.90

Mapowanie strefy na DecisionMode (implementacja w orchestrator.py):

  AUTO_POST (Trust ≥ auto_post)    → DecisionMode.AUTO_POST
  REVIEW    (Trust ≥ review)        → DecisionMode.SUGGEST
  BLOCK     (Trust < review)        → DecisionMode.ASK_USER
  ESCALATED (manualna eskalacja)   → DecisionMode.ASK_USER

4.2. Konsensus między agentami (Weighted Voting)
--------------------------------------------------

Ostateczna decyzja = ważony głos dwóch niezależnych głosów:

  AgentOrchestrator:     waga = 0.40  (decyzja wykonawcza)
  AgentQualityValidator: waga = 0.60  (niezależny audytor)

Jeśli consensus > 0.66 → akceptuj.
Jeśli uncertainty > 0.3 → eskalacja do człowieka.

Implementacja (zgodnie z msgspec.Struct w models.py):

  class ConfidenceVote(Struct, kw_only=True):
      agent: str
      weight: float = 0.0        # historyczna precyzja agenta
      vote: str                   # POST | REVIEW | BLOCK
      confidence: float = 0.0
      weighted_vote: float = 0.0  # weight × confidence

  class VotingResult(Struct, kw_only=True):
      votes: list[ConfidenceVote]
      total_weight: float
      winner: str
      consensus: bool = False     # True jeśli > 0.66 majority
      uncertainty: float = 0.0

4.4. Proof Chain SHA-256 (niepodważalny audyt)
------------------------------------------------

Implementacja przez nexus-crypto (z RAPORT_TECHNOLOGII):

  from nexus_crypto import Sha256Hasher

  class ProofChain:
      def __init__(self):
          self.chain: list[ProofBlock] = []
          self.load_from_db()  # DuckDB: proof_chain

      def add_block(self, decision: AgentDecision) -> str:
          previous_hash = self.chain[-1].hash if self.chain else "0"*64
          block_data = {
              "index": len(self.chain),
              "decision_id": decision.decision_id,
              "decision": msgspec.json.encode(decision),
              "timestamp": pendulum.now("UTC").isoformat(),
              "previous_hash": previous_hash,
          }
          hasher = Sha256Hasher()
          hasher.update(msgspec.json.encode(block_data))
          return hasher.hexdigest()

5.4. Bayesian Trust Score z propagacją
----------------------------------------

Trust Score = posterior Beta distribution:

  Prior:       Beta(α₀=1, β₀=1)          # uniform
  Likelihood:  Bern(y|θ)                 # y ∈ {0,1}
  Posterior:   Beta(α₀+Σy, β₀+n-Σy)

  Trust Score = E[θ|D] = α / (α + β)
  Confidence  = 1 - Var[θ|D]

Gdzie: α = poprawne decyzje, β = błędne decyzje.

Implementacja (czysty Python, brak zależności):

  class BayesianTrustScore:
      def __init__(self, alpha: float = 1.0, beta: float = 1.0):
          self.alpha = alpha
          self.beta = beta

      def update(self, correct: bool) -> None:
          if correct: self.alpha += 1
          else: self.beta += 1

      @property
      def trust_score(self) -> float:
          return self.alpha / (self.alpha + self.beta)

      @property
      def confidence(self) -> float:
          total = self.alpha + self.beta
          variance = (self.alpha * self.beta) / (total**2 * (total + 1))
          return max(0.0, 1.0 - variance * 12)

    accountant  → dostęp do decyzji, raportów, korekt

7.2. Audit log każdej decyzji (Proof Chain SHA-256)
------------------------------------------------------

  CREATE TABLE audit_log (
      id UUID PRIMARY KEY,
      user_id UUID REFERENCES users(id),
      agent TEXT NOT NULL,
      action TEXT NOT NULL,           -- 'decision', 'correction', 'view'
      resource TEXT NOT NULL,         -- 'invoice:123', 'report:monthly'

      ip_address TEXT,

  );

Każda decyzja → Proof Chain SHA-256 przez nexus-crypto.

7.3. 4-Eyes Principle (obowiązkowy > 50k PLN)
-----------------------------------------------

  Dla każdej decyzji > 50,000 PLN:
  - Pierwsza weryfikacja: Granite Guardian (kontrola podatkowa)
  - Druga weryfikacja: GraphSAGE + FinBERT (oszustwa + ryzyko)
  - Jeśli rozbieżne → próg podniesiony do 75,000 PLN

7.4. Split Payment Verification
---------------------------------

  Zgodnie z polskim prawem:
  - Obowiązkowy dla kwot > 15,000 PLN brutto
  - AgentQualityValidator: sprawdź kwotę → oznacz do MPP
  - AgentOrchestrator: 2 transfery (netto + VAT)
  - Weryfikacja poprawności przez OPA

7.5. RODO / GDPR compliance
------------------------------

  - Dane w SQLCipher (AES-256, z RAPORT_TECHNOLOGII)
  - Anonimizacja po 5 latach (automatyczna)
  - Backup szyfrowany (AEAD ChaCha20-Poly1305, nexus-crypto)
  - Eksport wszystkich danych na żądanie
  - Pełne usunięcie danych (prawo do bycia zapomnianym)

7.6. KSeF compliance
----------------------

  - Struktury FA(1), FA(2) zgodne z XSD MF
  - xsdata + lxml (z RAPORT_TECHNOLOGII) — generowanie XML
  - Podpis SHA-256 + certyfikat (nexus-crypto)
  - Wysyłka w 1h od zatwierdzenia
  - Backup offline faktur

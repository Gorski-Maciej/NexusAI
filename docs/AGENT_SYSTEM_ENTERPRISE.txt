System agentów AI NexusAI został zaprojektowany jako AUTONOMICZNE BIURO
KSIĘGOWE — 10 wyspecjalizowanych agentów, które:

1.2. Cztery filary systemu agentów
------------------------------------

  FILAR 1 — DECYZJA (Decision Engine)
  AgentOrchestrator koordynuje 10 agentów w procesie decyzyjnym.
  Każda decyzja przechodzi przez: ekstrakcję → ocenę → walidację → audyt.
  Wynik: AUTO_POST (≥0.92), REVIEW (≥0.75), BLOCK (<0.75).

  FILAR 2 — NAUKA (Continuous Learning Framework)
  Każda korekta użytkownika to nowy przykład treningowy.
  Bayesian update Trust Score po każdej decyzji.
  sqlite-vec: k-NN dla podobnych przypadków.
  OPA: semi-automatic rule generation po N korektach.

  FILAR 3 — PAMIĘĆ (Memory Systems)
  Cztery typy pamięci: episodyczna (DuckDB), semantyczna (sqlite-vec),
  proceduralna (OPA), robocza (NATS KV Store).
  Decision Cache: diskcache + sqlite-vec k-NN (80% decyzji bez inferencji).

  FILAR 4 — ODPORNOŚĆ (Resilience)
  Zero trust to a single model — każda decyzja ≥2 modele.
  4-Eyes Principle dla kwot > 50,000 PLN.
  Circuit breaker (stamina) — otwarcie po 5 błędach/30s.
  DLQ — Dead Letter Queue dla nieudanych wiadomości.

1.3. Poziomy autonomii (L0-L3)
--------------------------------

  LEVEL 0 — MANUALNY
  Agent tylko proponuje decyzje. Użytkownik zatwierdza KAŻDĄ.
  Idealny dla okresu nauki (pierwsze 100 faktur).
  Trust Score wymagany: 0.0 (nie ma auto-decyzji).

  LEVEL 1 — ASYSTENT
  Agent podejmuje decyzje w zielonej strefie (≥0.92).
  Pyta użytkownika w żółtej strefie (0.75-0.92).
  Blokuje w czerwonej strefie (<0.75).
  Trust Score wymagany: ≥0.75 dla auto.

  LEVEL 2 — AUTONOMICZNY (domyślny)
  Agent podejmuje decyzje w zielonej i żółtej strefie.
  Pyta użytkownika TYLKO w czerwonej strefie.
  Standardowy poziom dla znanych kontrahentów.
  Trust Score wymagany: ≥0.92 dla full auto.

  LEVEL 3 — W PEŁNI AUTONOMICZNY
  Agent podejmuje WSZYSTKIE decyzje samodzielnie.
  Informuje użytkownika raportem dziennym/tygodniowym.
  Wymaga Trust Score > 0.95 przez ostatnie 1000 decyzji.
  Osiągalny po ~6 miesiącach współpracy.

  Przełączanie poziomów:
  - Automatyczne: po osiągnięciu progu zaufania (Bayesian)
  - Ręczne: użytkownik może wymusić wyższy/niższy poziom
  - Awaryjne: przy wykryciu anomalii → automatyczne obniżenie

  Implementacja (msgspec.Struct — zgodnie z RAPORT_TECHNOLOGII):

  class AutonomyLevel(enum.IntEnum):
      MANUAL = 0
      ASSISTANT = 1
      AUTONOMOUS = 2
      FULL_AUTONOMOUS = 3

  class AutonomyConfig(Struct, kw_only=True):
      level: AutonomyLevel = AutonomyLevel.AUTONOMOUS
      min_trust_for_level: dict[AutonomyLevel, float] = {
          AutonomyLevel.MANUAL: 0.0,
          AutonomyLevel.ASSISTANT: 0.75,
          AutonomyLevel.AUTONOMOUS: 0.92,
          AutonomyLevel.FULL_AUTONOMOUS: 0.98,
      }
      min_decisions_for_promotion: int = 1000
      auto_demote_on_anomaly: bool = True

1.4. Mapa interakcji: człowiek ↔ agent ↔ aplikacja
-----------------------------------------------------

  Użytkownik (przedsiębiorca) wchodzi w interakcję przez:
    A) Dashboard (Flet UI) — podsumowania, alerty, decyzje
    B) Panel decyzyjny — lista decyzji oczekujących (2-5 opcji)
    C) Czat z Komunikatorem (Qwen3-Nano) — pytania NL
    D) Raporty — dzienne/tygodniowe/miesięczne (AgentAnalytics)

  System (agenci) samodzielnie:
    a) Pobiera faktury (email, upload, KSeF API, folder)
    b) Ekstrahuje dane (4 silniki OCR + walidacja krzyżowa)
    c) Klasyfikuje wydatki (konta księgowe, stawki VAT, PKWiU)
    d) Sprawdza kontrahentów (Biała Lista MF, GUS BIR, KRD)
    e) Wysyła do KSeF (FA(1), FA(2) — obowiązkowy e-spis)

    g) Uzgodnia salda (DuckDB reconciliation + TigerBeetle)
    h) Generuje deklaracje (JPK_V7, VAT-7, PIT/CIT)
    i) Monitoruje terminy (ZUS, US, KSeF, skonta)
    j) Wykrywa anomalie (oszustwa, błędy, ryzyko, karuzele VAT)
    k) Prognozuje cash flow (90 dni, 3 scenariusze)
    l) Optymalizuje podatki (symulacje "co by było, gdyby")
    m) Uczy się z każdej korekty użytkownika

2.2. Gwarancje dostarczenia: Exactly-once + DLQ
-------------------------------------------------

  AT-LEAST-ONCE DELIVERY:
    Każda wiadomość trwale zapisana w JetStream przed dostarczeniem.
    Manual ack po przetworzeniu — worker nie ack → redelivery.
    Ochrona przed duplikatami: task_id = blake2b(task_name + kwargs).
    Duplicate window: 2 minuty (identyczne zadania odrzucane).

  DEAD LETTER QUEUE:
    Po 3 nieudanych próbach → wiadomość do DLQ.
    DLQ przechowuje: oryginalna wiadomość + stack trace + próby.
    Retry z backoffem: 1s → 2s → 4s (exponential, z jitterem).
    Administrator: przegląd, retry, poprawa, odrzucenie.

  MAX ACK PENDING:
    Dynamicznie dostosowywany przez WorkerGuard.
    Przy wysokim CPU/RAM → zmniejszany (max 5).
    Przy niskim CPU/RAM → zwiększany (max 15).

2.3. Priority Queue z QoS
---------------------------

  Każde zadanie ma priorytet (1-10, 1 = najwyższy):

    1  — Krytyczne: błąd systemu, awaria KSeF, deadline podatkowy
    2  — Pilne: płatność z skontem, faktura od kluczowego klienta
    3  — Wysoki: nowa faktura > 50,000 PLN, podejrzenie oszustwa
    4-5 — Normalny: standardowa faktura, zapytanie analityczne
    6-7 — Niski: raport tygodniowy, aktualizacja wzorców
    8-9 — Background: aktualizacja modeli, regeneracja embeddingów
    10 — Idle: heartbeat, health check

  QoS (Quality of Service):
    P0-P1: dedicated 1 worker thread (z 2 dostępnych)
    P2-P3: max 50% worker capacity
    P4-P7: remaining capacity
    P8-P10: tylko gdy idle

2.4. Circuit Breaker (stamina) i retry z backoffem
----------------------------------------------------

  Implementacja przez stamina (z RAPORT_TECHNOLOGII):

    @stamina.retry(
        on=(NatsError, TimeoutError),
        attempts=3,
        timeout=30.0,
    )
    async def publish_with_retry(topic: str, data: bytes) -> None:
        ...

  Circuit Breaker:
    - Próg: 5 błędów w ciągu 30 sekund
    - Open: 60 sekund cooldown
    - Half-open: po 60s przepuść 1 request testowy
    - Jeśli OK → close. Jeśli błąd → open na 120s.
    - Stan publikowany na: system.circuit-breakers.{agent}

2.5. OpenTelemetry tracing na każdej wiadomości
--------------------------------------------------

  Każda wiadomość NATS zawiera:
    message.headers["trace_id"] = generate_trace_id()
    message.headers["span_id"] = generate_span_id()

  OpenTelemetry:
    - Spany: publish, subscribe, process, ack
    - Metryki: messages/sec, latency p99, error rate per agent
    - Export: DuckDB Parquet (offline) + OTLP (online)
    - Trace: od requestu do finalnej decyzji (end-to-end)

3.1. AgentOrchestrator — Centralny Mózg i CFO
===============================================

  ROLA:
    Naczelny dyrektor finansowy (CFO). Koordynuje 10 agentów,
    podejmuje ostateczne decyzje, komunikuje się z użytkownikiem.

  MODELE (GGUF przez llama-cpp-python, zgodnie z RAPORT_TECHNOLOGII):
    - Granite 3.2 3B (GGUF, IQ4_XS) — Główny Decydent (Actor) ~2.4 GB RAM
    - Granite Guardian 0.5B (GGUF, Q4_K_M) — Strażnik Merytoryczny ~300 MB
    - Qwen3-Nano 0.5B (GGUF, Q4_K_M) — Komunikator (NL→user) ~400 MB

  KLUCZOWE MECHANIZMY ENTERPRISE:

    1. DYNAMICZNY TRUST SCORE
       - Bayesian update po każdej decyzji: P(θ|D) ∝ P(D|θ) × P(θ)
       - Prior: Beta(α, β), posterior mean = α / (α + β)
       - Automatyczne dostosowanie dla nowych kontrahentów

    2. DECISION CACHE (diskcache + sqlite-vec k-NN)
       - Każda decyzja wektoryzowana w sqlite-vec (768d)
       - Podobna faktura → podobna decyzja (k-NN, k=5)
       - Oszczędność: 80% decyzji bez inferencji modelu

    3. ADAPTIVE THRESHOLDS
       - auto_post = 0.92 - (α-β)/(α+β) × 0.1
       - Dla znanych kontrahentów (α>>β) → niższy próg
       - Dla nowych → wyższy próg (conservative)

    4. PROOF CHAIN SHA-256
       - Każda decyzja → block w łańcuchu kryptograficznym
       - hash = SHA256(previous + decision + timestamp)
       - Niepodważalny dowód dla US (przez nexus-crypto)

    5. ESCALATION MATRIX
       - Inteligentna eskalacja: pora dnia, kanał, priorytet
       - Krytyczne: SMS push, ważne: powiadomienie, info: email
       - Opóźnienie do 24h dla niskiego priorytetu

  PROCES DECYZYJNY (5 kroków):
    Krok 1: Odbierz zadanie (council.task.request)
    Krok 2: Deleguj do AgentDataExtraction (invoice.received)
    Krok 3: Oceń przez Granite 3.2 Actor + Guardian 0.5B
    Krok 4: Wyślij do walidacji (quality.check.request)
    Krok 5: Finalna decyzja (council.decision.final)

  STREFA DECYZYJNA:
    AUTO_POST (≥0.92)  → automatyczne księgowanie
    REVIEW    (≥0.75)  → wymagana weryfikacja
    BLOCK     (<0.75)  → blokada + eskalacja

  UCZENIE SIĘ:
    - Korekty użytkownika → Bayesian update Trust Score
    - Podobne faktury → k-NN z sqlite-vec (decision_patterns)
    - Wzorce decyzyjne → DuckDB analiza historyczna
    - Thresholds → adaptacyjna kalibracja per kontrahent


3.2. AgentDataExtraction — Forteca Precyzji
=============================================

  ROLA:
    Ekstrakcja danych z dokumentów z precyzją > 99.9%.
    Zero błędów w polach krytycznych (NIP, kwoty, IBAN).

  MODELE I SILNIKI (zgodnie z RAPORT_TECHNOLOGII):
    - ParagonDetect (lekkie CNN, ONNX) — klasyfikacja ~50 MB RAM
    - Tesseract 5.3 — systemowy, druk klasyczny ~0 MB
    - PaddleOCR 2.8 — DL, różne czcionki ~250 MB
    - python-docTR 0.9 — układ strony (DBNet+PARSeq) ~350 MB
    - EasyOCR 1.7 — rezerwowy, różne języki ~300 MB
    - Granite Vision Guardian 0.3B — walidacja wizyjna ~250 MB
    - ModernBERT-NER-Finance 0.3B — walidacja semantyczna ~200 MB

  KLUCZOWE MECHANIZMY ENTERPRISE:

    1. CROSS-VALIDATION MATRIX (4×4)
       - Każde pole ekstrahowane przez 4 silniki niezależnie
       - 3/4 zgoda → akceptuj | 2/4 → Vision Guardian | <2/4 → ręczna
       - Statystycznie niemożliwe: 4 algorytmy ≠ ten sam błąd

    2. ACTIVE LEARNING OCR (Online Learning)
       - Każda korekta → wektor w sqlite-vec (ocr_corrections)
       - Przy kolejnej fakturze: k-NN → preferuj skorygowaną wartość
       - System uczy się układów faktur per-kontrahent

    3. INVOICE TEMPLATE MATCHING
       - Wzorce faktur per kontrahent (embeddingi 768d)
       - Pozycje pól (bounding boxy), formaty danych
       - sqlite-vec: k-NN dla szybkiego dopasowania wzorca

    4. SEMANTYCZNA WALIDACJA
       - NIP: suma kontrolna (wagi 6,5,7,2,3,4,5,6,7) + Biała Lista MF
       - IBAN: MOD-97 checksum + lista zastrzeżonych

4.1. Dynamiczne strefy decyzyjne (Bayesian thresholds)
--------------------------------------------------------

  Thresholds NIE są stałe — adaptują się Bayesian:

    auto_post = 0.92 - adjustment
    review    = 0.75 - adjustment
    adjustment = (α_vendor - β_vendor) / (α_vendor + β_vendor) × 0.1

    Gdzie:
      α_vendor = poprawne decyzje dla tego kontrahenta
      β_vendor = błędne decyzje dla tego kontrahenta

    Przykład:
      Znany kontrahent (100 faktur, 98 poprawnych):
      α=98, β=2 → adjustment = 0.096
      auto_post = 0.92 - 0.096 = 0.824 ← niższy próg (łatwiej)

      Nowy kontrahent (5 faktur, 4 poprawne):
      α=4, β=1 → adjustment = 0.06
      auto_post = 0.92 - 0.06 = 0.86 ← wyższy próg (ostrożnie)

      Podejrzany kontrahent (10 faktur, 6 poprawnych):
      α=6, β=4 → adjustment = 0.02
      auto_post = 0.92 - 0.02 = 0.90 ← bardzo wysoki próg

    from nexus_crypto import Sha256Hasher

    class ProofChain:
        def __init__(self):
            self.chain = []
            self.load_from_db()  # DuckDB: proof_chain

        def add_block(self, decision: AgentDecision) -> str:
            previous_hash = self.chain[-1].hash if self.chain else "0"*64
            block_data = {
                "index": len(self.chain),
                "decision_id": decision.decision_id,
                "decision": msgspec.json.encode(decision),
                "timestamp": pendulum.now("UTC").isoformat(),
                "previous_hash": previous_hash,

            hasher = Sha256Hasher()
            hasher.update(msgspec.json.encode(block_data))
            return hasher.hexdigest()

5.2. Bayesian Trust Score z propagacją
----------------------------------------

  Trust Score = posterior Beta distribution:

    Prior:       Beta(α₀=1, β₀=1)          # uniform
    Likelihood:  Bern(y|θ)                 # y ∈ {0,1}
    Posterior:   Beta(α₀+Σy, β₀+n-Σy)

    Trust Score = E[θ|D] = α / (α + β)
    Confidence  = 1 - Var[θ|D]

    Gdzie:
      α = 1 + poprawne decyzje
      β = 1 + błędne decyzje

  Implementacja (czysty Python, żadnych zależności):

    class BayesianTrustScore:
        def __init__(self, alpha: float = 1.0, beta: float = 1.0):
            self.alpha = alpha
            self.beta = beta

        def update(self, correct: bool) -> None:
            if correct: self.alpha += 1
            else: self.beta += 1

        @property
        def trust_score(self) -> float:
            return self.alpha / (self.alpha + self.beta)

        @property
        def confidence(self) -> float:
            total = self.alpha + self.beta
            variance = (self.alpha * self.beta) / (total**2 * (total + 1))
            return max(0.0, 1.0 - variance * 12)

5.7. Adaptive Thresholds (Bayesian Inference)
-----------------------------------------------

    correction = (α - β) / (α + β) × max_correction

    Dla nowych (α+β < 30):     correction *= (α+β)/30  (conservative)
    Dla znanych (α+β ≥ 100):   full correction

    decision_patterns   (768d, cosine)  — wzorce decyzyjne

  Funkcje odległości: cosine, l2, inner_product, manhattan.
  Kwantyzacja int8: 4× mniej RAM, ~2% spadek dokładności.

6.3. Procedural Memory (OPA/Rego)
-----------------------------------

  Reguły podatkowe i compliance w OPA:

    package tax.rules

    split_payment_required[invoice_id] {
        invoice := input.invoices[_]
        invoice.amount_gross > 1500000   # w groszach, > 15k PLN
        invoice.currency == "PLN"
    }

  Hot-reload: zmiany reguł nie wymagają restartu.

6.4. Working Memory (NATS KV Store)
--------------------------------------

  Krótkoterminowa pamięć (TTL 1h):
    - Bieżący stan agenta (loaded_models, active_tasks)
    - Cache decyzji (diskcache zapasowy)
    - Blokady (mutex dla operacji krytycznych)
    - Sesje użytkowników

  Buckety: nexus-config, nexus-rules, nexus-features, nexus-workers

6.5. Decision Cache (diskcache + sqlite-vec)
----------------------------------------------

    1. Każda decyzja → embedding 768d w sqlite-vec
    2. Nowa faktura → k-NN (k=5) w decision_patterns
    3. Jeśli max_distance < 0.1 → użyj cache decyzji
    4. Oszczędność: ~80% decyzji bez inferencji LLM
    5. diskcache: zapasowy cache dla szybkiego dostępu

7.3. 4-Eyes Principle (obowiązkowy > 50k PLN)
-----------------------------------------------

    Dla każdej decyzji > 50,000 PLN:
    - Pierwsza weryfikacja: Granite Guardian (kontrola podatkowa)
    - Druga weryfikacja: GraphSAGE + FinBERT (oszustwa + ryzyko)
    - Jeśli rozbieżne → próg podniesiony do 75,000 PLN

7.4. Split Payment Verification
---------------------------------

    Zgodnie z polskim prawem:
    - Obowiązkowy dla kwot > 15,000 PLN brutto
    - AgentTaxEngine: sprawdź kwotę → oznacz do MPP
    - AgentOrchestrator: 2 transfery (netto + VAT)
    - AgentQualityValidator: weryfikacja poprawności

7.5. RODO / GDPR compliance
-----------------------------

    - Dane w SQLCipher (AES-256, z RAPORT_TECHNOLOGII)
    - Anonimizacja po 5 latach (automatyczna)
    - Backup szyfrowany (AEAD ChaCha20-Poly1305, nexus-crypto)
    - Eksport wszystkich danych na żądanie
    - Pełne usunięcie danych (prawo do bycia zapomnianym)

7.6. KSeF compliance
----------------------

    - Struktury FA(1), FA(2) zgodne z XSD MF
    - xsdata + lxml (z RAPORT_TECHNOLOGII) — generowanie XML
    - Podpis SHA-256 + certyfikat (nexus-crypto)
    - Wysyłka w 1h od zatwierdzenia
    - Backup offline faktur

7.7. Proof Chain kryptograficzny (SHA-256)
-------------------------------------------

    Łańcuch skrótów SHA-256 przez nexus-crypto:
    - Każda decyzja → block
    - Każdy block zawiera hash poprzedniego
    - Modyfikacja → wszystkie kolejne unieważnione
    - Eksport dla US w formacie PDF/JSON

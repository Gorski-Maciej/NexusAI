ATAK 1: Obejście Sharded Routera — DOMESTIC_SALE z transgraniczną
──────────────────────────────────────────────────────────────────
🔴 KRYTYCZNY | passes: 1/5

OPIS:
Routing.context buduje transaction_type na podstawie:
  - input.invoice.direction == "SALE"
  - input.vendor.country != "PL"
Jeśli atakujący ustawi input.vendor.country = "PL" ale faktyczna
dostawa jest za granicę (np. input.delivery.country = "DE") —
router sklasyfikuje jako DOMESTIC_SALE zamiast EXPORT.

OCZEKIWANE ZACHOWANIE SYSTEMU:
System powinien wykryć transgraniczność na podstawie MIEJSCA
DOSTAWY, nie tylko siedziby sprzedawcy.

RZECZYWISTE ZACHOWANIE:
  ⚠️ build_transaction_type sprawdza tylko:
    1. direction == "SALE" + procedure == "EXPORT" → EXPORT
    2. direction == "SALE" + vendor.country != "PL" → CROSS_BORDER_SALE
    3. direction == "SALE" → DOMESTIC_SALE
  🚨 Brak: sprawdzenia delivery.country dla usług!
  🚨 Brak: sprawdzenia miejsca świadczenia VAT!

LUKA W REGUŁACH: main_jdg.rego — build_transaction_type
KONSEKWENCJE: Transgraniczna usługa może być zaklasyfikowana
jako krajowa → brak OSS/IOSS → błędna stawka VAT

ATAK 3: Wyścig między PAS-ami — RISK (PAS 0) vs ZUS (PAS 7)
────────────────────────────────────────────────────────────
🟠 WYSOKA | passes: 2/5

OPIS:
W main_jdg.rego, PAS 0 (risk.decide) ewaluuje się PRZED
PAS 7 (zus.decide). Jeśli ustawi BLOCK_AND_ALERT w _routing,

OCZEKIWANE: BLOCK_AND_ALERT w PAS 0 naprawdę zatrzymuje

RZECZYWISTE:

LUKA W REGUŁACH: main_jdg.rego — brak early abort
KONSEKWENCJE: Wszystkie pakiety są ewaluowane nawet po

ATAK 4: Przepełnienie łańcucha else — Deadlock fallback
────────────────────────────────────────────────────────
🟡 ŚREDNIA | passes: 3/5

OPIS:
Każdy pakiet w main_jdg.rego ma strukturę:
  decide := { matched: true, ... } { warunek }
  else := { matched: true, ... } { inny warunek }
  else := { matched: true, ... } { jeszcze inny }
  ...
  default decide := { matched: false, ... }

OCZEKIWANE: Jeśli żadna reguła nie pasuje, fallback.decide
jest zawsze osiągalny.

RZECZYWISTE:
  - fallback.rego ma default decide z matched: false
  - Ale main_jdg.rego używa safe_merge z fallback.decide
    TYLKO jeśli wszystkie pozostałe pakiety zwrócą matched: false
  - W przypadku konfliktu między pakietami (oba matched: true),
    merge wybiera ostatni (najwyższy priorytet)
  - Fallback jest zawsze osiągalny — ✅ POPRAWNIE

LUKA: fallback działa, ale jego czas wykonania może być
długi (OPA ewaluuje wszystkie reguły przed fallback).
KONSEKWENCJE: Tylko performance (nie poprawność).

ATAK 5: Manipulacja priorytetami — niższy priorytet dla BLOCK
──────────────────────────────────────────────────────────────
🟠 WYSOKA | passes: 2/5

OPIS:
W safe_merge kolejność scalania determinuje priorytet:
  safe_merge(risk.decide,
    safe_merge(kks.decide,
      safe_merge(routing.decide, ...)))

OCZEKIWANE: risk.decide (zewnętrzny) ma najwyższy priorytet.

RZECZYWISTE:
  - safe_merge(a, b) zwraca object.union(a, b) (a wygrywa)
  - W chainie: risk.decide jest NAJBARDZIEJ ZEWNĘTRZNY
    → ma NAJWYŻSZY PRIORYTET ✅
  - Ale: dla immutable_verdict — jeśli wewnętrzny ma flagę,
    wygrywa (przypadek 2 w safe_merge)
  - Konflikt: risk.decide (BLOCK) vs zus.decide (immutable)
    → zus.decide wygrywa (celowo — ZUS jest prawnie niemutowalny)

KONSEKWENCJE: Celowe zachowanie. Ale może być exploit:
pakiet niższego priorytetu ustawia immutable_verdict=true
aby wygrać z risk.decide (patrz Atak 2).

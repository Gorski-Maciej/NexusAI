1.1. nexus-crypto — architektura Rust+PyO3 + pure-Python fallback
------------------------------------------------------------------

nexus-crypto to WLASNY modul kryptograficzny NexusAI, zbudowany wg
zasady minimalnej powierzchni ataku: **3 algorytmy, nic wiecej**.

Architektura dwuwarstwowa:

Warstwa 1 — Rust (nexus_ai/rust/src/):
  - aead.rs — ChaCha20-Poly1305 (RFC 8439)
  - argon2.rs — Argon2id KDF (RFC 9106)
  - sha256.rs — SHA-256 (FIPS 180-4)
  - vault.rs — bezpieczny magazyn kluczy (mlock)
  - Budzet LOC: max 1500 linii kodu

Warstwa 2 — Pure-Python fallback (nexus_ai/rust/nexus_crypto/__init__.py):
  - ChaCha20-Poly1305: cryptography.hazmat
  - Argon2id: argon2-cffi
  - SHA-256: hashlib (stdlib)
  - BLAKE2b: hashlib (stdlib)
  - JWT HS256: pyjwt
  - PriorityEngine + TemporalManager: legacy

ADR-007 uzasadnia wybor wlasnego modulu:
+ Minimalna powierzchnia ataku — tylko 3 algorytmy vs 50+ w cryptography
+ Statyczna kompilacja w Nuitke — zero zewnetrznych .so
+ Pelna kontrola lancucha dostaw
+ Szybkosc: ChaCha20-Poly1305 ~1 GB/s (Rust) vs ~300 MB/s (PyCryptodome)
+ Wymuszenie best practices na poziomie API

Ocena architektury: ★★★★★ (5/5)

+ Dwuwarstwowa architektura (Rust + pure-Python) — doskonala
+ Budzet LOC (1500 linii) — wymusza minimalizm
+ Wlasny modul = pelna kontrola
+ Pure-Python fallback dziala bez kompilacji Rusta
+ To samo API w obu wersjach — przezroczysta podmiana

- Rust jest opcjonalny — domyslnie uzywany pure-Python
  (2-5x wolniejszy, ale dla <1000 operacji/dzien nieodczuwalny)
- Brak hardware-accelerated AES (celowo — ChaCha20 jest portable)

1.2. AEAD ChaCha20-Poly1305 — poprawnosc implementacji
--------------------------------------------------------

Parametry AEAD (zgodne z RFC 8439):

| Parametr     | Wartosc                     | Zgodnosc |
|-------------|-----------------------------|----------|
| Szyfr        | ChaCha20 (stream cipher)    | RFC 8439 |
| MAC          | Poly1305                    | RFC 8439 |
| Klucz        | 256 bit (32 bajty)          | OK       |
| Nonce        | 96 bit (12 bajtow)          | OK       |
| Tag          | 128 bit (16 bajtow)         | OK       |
| AAD          | Opcjonalne                  | OK       |

Implementacja (pure-Python fallback):
  def encrypt(key, plaintext):
      nonce = os.urandom(12)              # CSPRNG nonce
      chacha = ChaCha20Poly1305(key_bytes)
      ciphertext = chacha.encrypt(nonce, plaintext, None)
      return nonce + ciphertext           # nonce prepended

  def decrypt(key, data):
      nonce = data[:12]                   # Wyodrebnij nonce
      ciphertext = data[12:]
      chacha = ChaCha20Poly1305(key_bytes)
      return chacha.decrypt(nonce, ciphertext, None)

Ocena poprawnosci: ★★★★★ (5/5)

+ Nonce generowany przez os.urandom (CSPRNG) — NIGDY nie powtorzony
+ Nonce prepended do ciphertextu — standardowe podejscie
+ Brak AAD (None) — dla backupow i sekretow wystarczajace
+ Decrypt rzuca DecryptionError przy nieudanym uwierzytelnieniu
+ Biblioteka cryptography uzywana w fallbacku jest audytowana

- Brak key commitment (nie mozna udowodnic, ze dany klucz
  zostal uzyty do szyfrowania — atak "invisible salamander")
  To zaawansowana slabsoc — akceptowalna dla aplikacji desktopowej
- Brak nonce misuse resistance (XSalsa20/Poly1305 bylby lepszy,
  ale wolniejszy)

Zastosowania AEAD w NexusAI:
  - Vault.encrypt/decrypt — szyfrowanie danych aplikacyjnych
  - LocalSecretsCache.save/get — szyfrowanie cache sekretow
  - Backup encryption

1.3. Argon2id KDF — parametry bezpieczenstwa
-----------------------------------------------

Parametry Argon2id (zgodne z RFC 9106):

| Parametr          | Wartosc  | RFC 9106 min | Ocena |
|-------------------|---------|-------------|-------|
| Memory cost       | 64 MB   | 46 MB       | OK    |
| Time cost (iter)  | 3       | 1           | OK    |
| Parallelism       | 4       | 1           | OK    |
| Salt length       | 16 B    | 16 B        | OK    |
| Output length     | 32 B    | 32 B        | OK    |

Implementacja (pure-Python fallback):
  def derive_key(password, salt=None):
      if salt is None:
          salt = os.urandom(16)
      key = hash_secret_raw(
          secret=password.encode("utf-8"),
          salt=salt,
          time_cost=3,
          memory_cost=65536,      # 64 MB
          parallelism=4,
          hash_len=32,
          type=Type.ID,           # Argon2id
      )
      return key, salt

  def hash_password(password):
      ph = PasswordHasher()       # Uzywa domyslnych argon2-cffi
      return ph.hash(password)

  def verify_password(password, encoded):
      ph = PasswordHasher()
      return ph.verify(encoded, password)

KRYTYCZNA UWAGA: hash_password() uzywa PasswordHasher() z DOMYSLNYMI
parametrami argon2-cffi, NIE parametrami zdefiniowanymi w derive_key()!
PasswordHasher domyslnie uzywa:
  - memory_cost=65536 (64 MB) — OK, zgodne
  - time_cost=3 — OK, zgodne
  - parallelism=4 — OK, zgodne

ALE: Te parametry MOGLYBY zostac zmienione w przyszlej wersji argon2-cffi
bez wiedzy NexusAI. Brak explicite przekazania parametrow.

Ocena: ★★★★☆ (4/5)

+ Parametry zgodne z RFC 9106
+ Argon2id (hybryda) — odporny na side-channel i GPU
+ derive_key explicite przekazuje parametry
- hash_password NIE przekazuje explicite parametrow do PasswordHasher
  (polega na domyslnych argon2-cffi)
- Brak mechanizmu rehash (rehash_needed w wersji Rust istnieje)

Zastosowania Argon2id:
  - Hashowanie hasel uzytkownikow (login)
  - Wyprowadzanie klucza SQLCipher
  - derive_key dla szyfrowania backupow

1.5. mlock() — ochrona sekretow w pamieci
--------------------------------------------

Vault implementuje mlock() dla ochrony klucza szyfrowania:

  def _mlock_key(self):
      buf = (ctypes.c_char * len(self._key)).from_buffer(self._key)
      libc.mlock(buf, len(self._key))

  def _zeroize_key(self):
      buf = (ctypes.c_char * len(self._key)).from_buffer(self._key)
      ctypes.memset(buf, 0, len(self._key))
      self._key = None

  def __del__(self):
      self._zeroize_key()

Ocena: ★★★★☆ (4/5)

+ mlock() chroni przed swapem
+ memset() zeruje klucz po uzyciu
+ __del__ zapewnia zerowanie przy garbage collection
+ bytearray (mutable) — bezpieczne dla mlock i memset

- mlock() tylko na kluczu Vault, NIE na kluczu LocalSecretsCache
- Brak mlock w pure-Python fallbacku derive_key
- mlock wymaga uprawnien roota na niektorych systemach
  (fallback: tylko log warning)
- Brak ochrony przed cold boot attack (klucz w RAM)

1.7. Vault — bezpieczny magazyn kluczy
----------------------------------------

Vault (core/crypto.py) zarzadza kluczem szyfrowania:

Hierarchia kluczy:
  1. NEXUS_ENCRYPTION_KEY (base64-urlsafe, 32 bajty) → bezposrednio
  2. NEXUS_SQLCIPHER_KEY → Argon2id derive_key
  3. Fallback: plaintext mode (log warning)

Funkcje:
  - encrypt(plain_text) → base64(ciphertext)
  - decrypt(encrypted_text) → plain_text
  - mlock() klucza
  - zeroize przy __del__

Ocena: ★★★★☆ (4/5)

+ Hierarchia kluczy (bezposredni → KDF → plaintext)
+ Graceful degradation (plaintext mode gdy brak klucza)
+ Base64 output — bezpieczny dla JSON/TOML

- Ten sam klucz dla wszystkich danych — brak key separation
  (osobny klucz dla backupow, osobny dla sekretow)
- Brak key versioning — nie mozna rotowac klucza bez re-encrypt
  wszystkich danych

  1. Login → access_token (15min) + refresh_token (30 dni)
  2. Refresh → nowy access_token + rotacja refresh_token

Natychmiastowe uniewaznianie:
  - jwt_version w tabeli users
  - Token zawiera jwt_version w extras
  - Przy kazdym requescie: token.jwt_version vs db.jwt_version
  - Jesli token < db → odrzucony

Ocena JWT: ★★★★★ (5/5)

+ Krotki TTL (15 min) — minimalizuje skutki kradziezy
+ Refresh token rotation — zapobiega replay
+ jwt_version — natychmiastowe uniewaznienie wszystkich sesji
+ Dual auth (Bearer + Cookie) — elastycznosc
+ Sekret z env var — brak hardcoded
+ Rust verify_jwt w TenantContextMiddleware — 10-50x szybsze

- HS256 zamiast RS256 — wspoldzielony sekret (nie公私钥)
  Ale dla aplikacji desktopowej (single-user) to wystarczajace
- Brak JWT kid (Key ID) dla rotacji klucza bez uniewazniania

3.2. Key derivation i PRAGMA rekey
-------------------------------------

Key derivation:
  - Klucz z env var NEXUS_SQLCIPHER_KEY
  - PRAGMA key = x'hex(key)'
  - 64000 iteracji PBKDF2_HMAC_SHA512

Key rotation (KeyRotation):
  - PRAGMA rekey = x'hex(new_key)'
  - BEGIN IMMEDIATE → rekey → COMMIT
  - Automatyczny backup przed rekey
  - Walidacja integralnosci po rekey
  - Harmonogram: co 90 dni

Ocena: ★★★★★ (5/5)

+ PRAGMA rekey — rotacja bez dump/restore
+ Transakcyjnosc (BEGIN IMMEDIATE)
+ Automatyczny backup przed rekey
+ Harmonogram rotacji

- Klucz przechowywany w env var (nie w HSM/keyring)
- Brak automatycznej rotacji (trzeba recznie wywolac)

4.1. Lancuch SHA-256 — projekt i implementacja
------------------------------------------------

ProofChain (services/proof_chain.py):

Struktura wpisu:
  - audit_id: UUID
  - transaction_id: ID transakcji
  - trace_json: pelny slad decyzyjny
  - context_snapshot: kontekst z dnia decyzji
  - previous_hash: SHA-256 poprzedniego wpisu
  - current_hash: SHA-256(previous + payload + timestamp)

Algorytm:
  1. Pobierz ostatni hash
  2. Serializuj payload (msgspec, sort_keys=True)
  3. current = SHA-256(previous_hash + payload + timestamp)
  4. Zapisz w DuckDB (append-only)

Weryfikacja lancucha (verify_chain):
  - Sprawdza wszystkie wpisy po kolei
  - previous_hash == poprzedni current_hash?
  - Zwraca {valid, total_decisions, invalid_links}

Ocena: ★★★★★ (5/5)

+ Append-only — brak UPDATE, tylko INSERT
+ previous_hash tworzy nieprzerwany lancuch
+ Weryfikowalny w czasie O(n)
+ msgspec sort_keys=True — deterministyczna serializacja

- DuckDB jako storage (nie append-only filesystem)
  — teoretycznie mozna zmodyfikowac plik DuckDB
  Ale DuckDB z WAL mode jest bezpieczny
- Brak podpisu cyfrowego (tylko hash)
  — brak non-repudiation (nie mozna udowodnic KTO dodal wpis)

4.2. Weryfikowalnosc przez strone trzecia
-------------------------------------------

API do weryfikacji:
  - GET /api/v2/audit/tax-decision/{transaction_id} — explain_decision
  - IntegrityVerifier — cykliczne przeliczanie

explain_decision() zwraca:
  - transaction_id, audit_id, timestamp
  - hash_valid (boolean)
  - decision (rule_id, vat_rate, action)
  - context (category, tax_form, vendor_country)
  - chain_integrity: INTACT / COMPROMISED

Ocena: ★★★★☆ (4/5)

+ Publiczne API do weryfikacji
+ Explainer czytelny dla czlowieka
+ hash_valid per wpis
+ chain_integrity dla calosci

- Brak eksportu calego lancucha do formatu
  zewnetrznego (np. JSON-LD, Merkle proof)
- Brak zakotwiczenia w publicznym blockchain
  (timestamping przez KSeF/rejestr publiczny)

11. 12 INNOWACYJNYCH USPRAWNIEN WYPRZEDZAJACYCH PROFESJONALISTOW
================================================================================

[INNOWACJA 1] Key Separation przez HKDF:
Zamiast jednego klucza dla wszystkich danych, uzyc HKDF-SHA256
do wyprowadzenia osobnych kluczy dla kazdego kontekstu:
  - root_key → HKDF(info="backups") → backup_key
  - root_key → HKDF(info="secrets") → secrets_key
  - root_key → HKDF(info="vault") → vault_key
Kazdy klucz ma inny cel — compromise jednego nie zagraza pozostalym.

[INNOWACJA 2] Nonce Misuse Resistance przez XChaCha20:
Zastapic ChaCha20-Poly1305 przez XChaCha20-Poly1305
(192-bit nonce). Większy nonce = bezpieczne losowe
generowanie, zero ryzyka powtorzenia.

[INNOWACJA 3] Argon2id Explicit Parameters:
Przekazywac parametry (memory, iterations, parallelism)
explicite do PasswordHasher, zamiast polegac na domyslnych.

[INNOWACJA 4] Constant-Time JWT Verification:
Uzywac hmac.compare_digest() dla porownania tokenow,
eliminujac timing attack na refresh tokeny.

[INNOWACJA 5] Memory Encryption dla klucza SQLCipher:
Przechowywac klucz SQLCipher w Vault (z mlock), nie w env var.
Env var jest widoczny w /proc/<pid>/environ.

[INNOWACJA 6] Transaction Signing dla Proof Chain:
Dodac HMAC-SHA256 z kluczem per-instance jako podpis kazdego
wpisu. To daje non-repudiation (mozna udowodnic, ze wpis
pochodzi z TEJ instancji NexusAI).

[INNOWACJA 7] Blockchain Timestamping:
Publikowac Merkle root co miesiac w publicznym rejestrze
(np. KSeF, Ethereum, lub polski Rejestr Dokumentow
Elektronicznych). Daje to dowod istnienia dokumentu
w danym momencie (timestamping).

[INNOWACJA 8] DLP (Data Loss Prevention) w Pipeline:
Rozszerzyc PiiScanMiddleware o konfigurowalne reguly DLP:
  - blokuj wysylke NIP/PESEL przez niezabezpieczone kanaly
  - maskuj dane wrazliwe w logach
  - audytuj wszystkie operacje na danych osobowych

[INNOWACJA 9] Runtime Application Self-Protection (RASP):
Monitorowac aplikacje w runtime pod katem:
  - nieautoryzowanych zapytan SQL
  - nadmiernego zuzycia CPU/RAM
  - podejrzanych wzorcow dostepu
Zatrzymywac ataki zanim osiagna cel.

[INNOWACJA 10] Biometric MFA:
Dodac biometrie (odcisk palca / Face ID) jako drugi
skladnik uwierzytelniania dla krytycznych operacji
(zatwierdzanie przelewu > 50k PLN, zmiana planu kont).

[INNOWACJA 11] Confidential Computing przez Intel SGX:
Dla instalacji serwerowych, uruchomic TigerBeetle i
Vault w enklawie SGX. Nawet administrator z rootem
nie moze odczytac kluczy.

[INNOWACJA 12] AI-Powered Anomaly Detection:
Uzywac GraphSAGE + autoencoder do wykrywania
anomalii w grafie FraudGraphScanner. ML wykryje
wzorce ktorych regulowe reguly nie zobacza.

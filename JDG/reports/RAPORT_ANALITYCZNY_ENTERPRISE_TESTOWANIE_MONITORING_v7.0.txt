1.1 Piramida Testow — Czy jest zrownowazona?
---------------------------------------------

NexusAI stosuje ODWROCONA piramide testow z naciskiem na property-based
testing (matematyczne dowody poprawnosci na samym dole):

        ┌──────────┐
        │   E2E    │  locust (wydajnosc), schemathesis (fuzz API)
        ├──────────┤
        │Integracyj│  testy integracyjne (DB + NATS + TigerBeetle)
        ├──────────┤
        │   Unit   │  testy jednostkowe (pytest)
        ├──────────┤
        │   PBT    │  property-based (crosshair — SMT solver)
        └──────────┘

To jest SWIADOMA decyzja architektoniczna. W systemie finansowym, gdzie
bledy moga kosztowac tysiace zlotych, matematyczne dowody poprawnosci
(PBT) sa WAZNIEJSZE niz tradycyjne testy jednostkowe.

POZIOMY TESTOW:

1. Property-Based (crosshair) — Matematyczne dowody poprawnosci:
   - VAT, zaokraglenia, sumy kontrolne
   - Niezmienniki Money: przemiennosc, lacznosc, identycznosc
   - Automaty stanow (InvoiceAggregate, TaxDecisionAggregate)
   - SMT solver (Z3) zamiast random fuzzing
   - ~30 testow z @crosshair.check i @contract()

2. Jednostkowe (pytest) — Izolowane funkcje i klasy:
   - ~100+ plikow testowych
   - Serwisy: tax, inventory, reconciliation, dunning...
   - Value objects: Money, MoneyNet, VatRate
   - Domain aggregates: InvoiceAggregate, ContractorAggregate

3. Integracyjne (pytest + DB/NATS) — Przeplywy end-to-end:
   - @pytest.mark.integration
   - Wymagaja --run-integration flag
   - Testy z mockowaniem zewnetrznych API (httpx_mock)

4. Fuzz API (schemathesis) — Automatyczna walidacja OpenAPI:
   - @pytest.mark.schemathesis
   - Wymaga --run-schemathesis flag
   - Kazdy endpoint testowany setkami losowych parametrow

5. Wydajnosciowe (locust) — Testy obciazeniowe:
   - FastHttpUser + SequentialTaskSet
   - LoadTestShape — customowe profile
   - Threshold gate — blokada PR przy regresji

OCENA: 8.5/10 — Architektura testow jest SOLIDNA. Priorytetyzacja
property-based testing dla systemu finansowego to GENIALNA decyzja.
Jedyny mankament: testy E2E sa niedostatecznie rozwiniete.

1.8 INNOWACYJNE USPRAWNIENIA Strategii Testowej
------------------------------------------------

USPRAWNIENIE 1: "Chaos Engineering Test Suite"
  Automatyczne testy chaosu:
  - Zabij proces NATS → czy system przechodzi w fallback?
  - Zapelnij dysk → czy system zamyka sie bezpiecznie?
  - Wylacz siec → czy OTA updater wznawia?
  Kazdy scenariusz z asercjami na stan systemu.

USPRAWNIENIE 2: "Mutation Testing z mutmut"
  Automatyczne mutacje kodu (zmiana + na -, > na >=, True na False)
  i sprawdzanie czy testy wykrywaja bledy. To MIERZY jakosc testow,
  nie tylko pokrycie.

USPRAWNIENIE 3: "Automated Test Impact Analysis"
  Uruchamiaj tylko testy zwiazane ze zmienionymi plikami.
  Dla ~100+ plikow testowych, oszczednosc 70-90% czasu CI.

USPRAWNIENIE 4: "Test Flakiness Dashboard"
  CI automatycznie wykrywa flaky testy:
  - Test fail → retry 3x → jesli 2+/3 pass → "flaky"
  - Dashboard z historia flaky testow
  - Automatyczny Issue gdy test jest flaky >3 razy

USPRAWNIENIE 5: "Property-Based API Testing"
  Rozszerzenie schemathesis o wlasne generatory danych:
  - NIP (poprawne i niepoprawne)
  - Kwoty (male, duze, ujemne, overflow)
  - Daty (przeszle, przyszle, nieprawidlowe)

2.1 crosshair — SMT-Driven Property-Based Testing
--------------------------------------------------

NexusAI uzywa crosshair ZAMIAST hypothesis. To SWIADOMA decyzja:

crosshair:
  - SMT solver (Z3) — matematyczne dowody poprawnosci
  - Analiza statyczna przed uruchomieniem
  - Deterministyczne wyniki (zero losowosci)
  - @crosshair.check — symboliczna analiza
  - @crosshair.contract() — typed parameters dla SMT
  - crosshair.precondition() — ograniczenie domeny
  - crosshair.postcondition() — weryfikacja wyniku

hypothesis:
  - Losowe generowanie danych (random fuzzing)
  - Niedzeterministyczne — ten sam test moze dac rozne wyniki
  - Ciezsze (wiecej zaleznosci)

9.1 Scenariusz: Awaria OTLP Collector
--------------------------------------

Co sie stanie:
  - BatchSpanProcessor buforuje spany w pamieci
  - Po przepelnieniu bufora → spany sa odrzucane
  - FileSpanBuffer jako fallback — spany zapisywane do Parquet

PROBLEM: BatchSpanProcessor NIE ma integracji z FileSpanBuffer!
Spany odrzucone przez BSP NIE trafiaja do fallback buffer.
To jest LUKA — spany moga zostac utracone przy dlugiej awarii.

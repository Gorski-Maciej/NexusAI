1. AUDYT ARCHITEKTURY ORKIESTRATORA (POZIOM ENTERPRISE)
================================================================================

1.1. Architektura Dual-Layer Multi-Pass (Macro + Micro)

Architektura NexusAI JDG wykorzystuje DWA POZIOMY reguł:
- MACRO LAYER: ~6,300 reguł decyzyjnych (VAT/PIT/ZUS/KKS/PKPiR) w 38 plikach
- MICRO LAYER: ~2,900 reguł atomowych per artykuł ustawy w 35 plikach

Multi-Pass evaluation (15 przebiegów):
PASS 0:  RISK (risk.rego) — BLOCK_AND_ALERT → abort
PASS 1:  ROUTING (routing.rego) — BLOCK_AND_ALERT → abort
PASS 2:  COMPLIANCE (compliance.rego, aml)
PASS 3:  CROSSBORDER (crossborder.rego, post_brexit)
PASS 4:  VAT (substantive.rego, deductions.rego, procedures.rego)
PASS 5:  PIT (forms.rego, kup.rego, advances_returns.rego, exemptions.rego)
PASS 6:  ALLOWANCES (allowances.rego)
PASS 7:  ACCOUNTING (accounting.rego, pkpir, depreciation)
PASS 8:  ZUS+BUSINESS+ (zus.rego, business.rego, gig_economy)
PASS 9-14: Enterprise Strategic Layers (S1-S24)
PASS 15: Conflicts Detection (conflicts.rego) — POST-MERGE

OCENA: ★★★★★ (5/5) — Architektura klasy światowej. Multi-Pass umożliwia 
niezależną ewaluację domen z właściwą kolejnością zależności. VAT jest 
ewaluowany przed PIT (poprawnie — KUP zależy od stawki VAT), a RISK przed 
wszystkim (poprawnie — fraud blokuje dalsze przetwarzanie).

Krytyczna zależność: Jeśli RISK (PASS 0) lub ROUTING (PASS 1) zwrócą 
BLOCK_AND_ALERT, dalsze passy są abortowane. To PRAWIDŁOWE zachowanie — 
nie ma sensu obliczać VAT jeśli wykryto fraud.

1.2. Mechanizm First-Match-Wins else-chain w main_jdg.rego

Orkiestrator używa zagnieżdżonego safe_merge() zamiast else-chain dla 
scalania werdyktów. Każdy PAKIET (np. substantive.rego) wewnętrznie 
używa else-chain dla swoich reguł, ale orkiestrator scala je przez 
bezpieczny merge.

Kolejność scalania (od najniższego priorytetu wewnątrz do najwyższego 
na zewnątrz):
fallback → validation → mpips → rodo → retention → ... → 
procedures → deductions → substantive → crossborder → post_brexit →
compliance → routing → kks → risk

OCENA: ★★★★☆ (4/5) — Kolejność jest przemyślana: risk nadpisuje wszystko,
VAT substantive jest wyżej niż deductions i procedures (poprawnie), ale
istnieje RYZYKO cichego nadpisywania przez object.union. Mechanizm 
safe_merge z immutable_verdict skutecznie chroni ZUS, ale NIE jest 
stosowany dla VAT. 

INNOWACYJNE USPRAWNIENIE: "Concurrent Pass Execution" — pakiety, które 
nie mają zależności między sobą (np. VAT deductions i PIT forms) mogą 
być ewaluowane równolegle w osobnych gorutynach OPA, redukując latency 
z ~28s do ~8-12s. Wymaga refaktoryzacji orkiestratora do grafu 
zależności (DAG) zamiast liniowego łańcucha.

1.3. Sharded Router (B1) — Deterministyczność i niezawodność

Router buduje kontekst z 8 pól (tax_form, transaction_type, entity_status,
evaluation_quarter, is_cross_border, has_employees, is_vat_payer, 
requires_ksef) i wybiera optymalną ścieżkę ewaluacji (shard).

Obecny status: PROTOTYP. Router zwraca listę pakietów z priorytetyzacją, 
ale NIE mapuje do dedykowanych shardów (docelowo w Fazie S2).

OCENA: ★★★☆☆ (3/5) — Koncepcja jest genialna (O(1) zamiast O(N)), ale 
implementacja jest w fazie prototypu. Router jest deterministyczny 
(ten sam input → ten sam output), ale NIE jest używany do faktycznego 
pomijania pakietów — pełny łańcuch zawsze się wykonuje.

INNOWACYJNE USPRAWNIENIE: "Predictive Shard Pre-warming" — na podstawie 
historycznych wzorców transakcji JDG (np. "JDG X zawsze wysyła faktury 
krajowe ze stawką 23%"), system może pre-loadować odpowiedni shard 
przed faktyczną ewaluacją. Wymaga integracji z Neural Rule Mesh (S14).

2.1. MPP i Split Payment (Art. 108a-108d VAT) ★★★ GŁÓWNY PRIORYTET

STAN OBECNY:
- P100 (substantive.rego): split_payment_mandatory — obowiązkowy MPP dla 
  zakupów >15 000 PLN brutto w kategoriach STEEL, FUEL, ELECTRONICS, 
  CONSTRUCTION, COAL + znacznik jpk_v7_mpp=true
- P101: split_payment_voluntary — dobrowolny MPP ≤15 000 PLN
- P102: split_payment_sanction — BLOCK_AND_ALERT z sankcją 30% VAT, 
  NKUP PIT/CIT, solidarna odpowiedzialność
- _helpers_jdg.rego: jdg_is_mpp_sensitive dla 6 kategorii: FUEL, STEEL, 
  ELECTRONICS, CONSTRUCTION, SCRAP, ALCOHOL

ANALIZA KOMPLETNOŚCI:

BRAK 1: NIEKOMPLETNA LISTA ZAŁĄCZNIKA 15
Art. 108a ust. 1a VAT odsyła do Załącznika nr 15, który zawiera 47 KATEGORII 
towarów i usług wrażliwych wymagających MPP (wg PKWiU i CN). Obecny system 
pokrywa TYLKO 6 kategorii. 

Brakujące krytyczne kategorie z Załącznika 15:
- Węgiel kamienny, brunatny, koks (CN 2701-2704) — obecnie tylko "COAL"
- Benzyna, oleje napędowe, gaz LPG (CN 2710-2711)
- Komputery, laptopy, tablety, telefony (CN 8471, 8517) — obecnie "ELECTRONICS" 
  ale bez rozbicia na konkretne kody CN
- Metale szlachetne i półszlachetne (CN 7106-7112)
- Odpady szklane, papierowe, z tworzyw sztucznych (CN 3915, 4707, 7001)
- Części do pojazdów (CN 8708)
- Zboża, rośliny oleiste, nasiona (CN 1001-1008, 1201-1207)
- Cukier, kakao, czekolada (CN 1701, 1801-1806)
- Tkaniny, odzież, obuwie (CN 5007-5113, 6101-6117, 6401-6405)
- Metale nieżelazne: aluminium, miedź, ołów, cynk, cyna (CN 7601-7607)
- Półprodukty ze stali (CN 7207-7229) — obecnie tylko "STEEL"
- Usługi budowlane (PKWiU 41-43) — obecnie brak w MPP mandatory (jest 
  tylko CONSTRUCTION jako kategoria ale nie PKWiU)

Rekomendacja: Zastąpić 6 kategorii w helpers pełną mapą 47 kodów CN/PKWiU 
z Załącznika 15 + regułą weryfikującą kod CN na fakturze.

BRAK 2: BRAK SOLIDARNEJ ODPOWIEDZIALNOŚCI (Art. 105a-105c VAT)
System nie implementuje reguł solidarnej odpowiedzialności nabywcy za VAT 
dostawcy w przypadku towarów wrażliwych (Art. 105a-105c VAT). Jeśli nabywca 
kupuje towary z Załącznika 15 od dostawcy, który nie odprowadził VAT, nabywca 
odpowiada SOLIDARNIE za VAT. Jedynym bezpiecznym wyjściem jest... MPP.

Rekomendacja: Dodać regułę: "jeśli kwota >15 000 PLN + kategoria z Zał. 15 + 
split_payment_used==false → BLOCK_AND_ALERT z informacją o solidarnej 
odpowiedzialności"

BRAK 3: NIE WYKORZYSTANO FUNKCJI jdg_is_mpp_sensitive
Funkcje w _helpers_jdg.rego (jdg_is_mpp_sensitive) są zdefiniowane ale NIE 
są używane w substantive.rego. Reguły P100-P102 używają category_code 
bezpośrednio, ignorując helpers. To prowadzi do DUPLIKACJI listy kategorii.

Rekomendacja: Refaktoryzacja P100-P102 aby używały jdg_is_mpp_sensitive() 
z helpers.

BRAK 4: NIEKOMPLETNA OBSŁUGA KOMUNIKATU OSTRZEGAWCZEGO
P102 (split_payment_sanction) prawidłowo ustawia BLOCK_AND_ALERT, ale 
komunikat ostrzegawczy nie zawiera:
- Dokładnej kwoty sankcji (30% × kwota VAT)
- Obliczenia NKUP (kwota netto nie będzie KUP w PIT/CIT)
- Informacji o solidarnej odpowiedzialności
- Instrukcji krok-po-kroku jak naprawić (przelew MPP, korekta faktury)

INNOWACYJNY SYSTEM AUTO-DETEKCJI MPP:
Proponuję 3-warstwowy system:
1. PRIMARY DETECTION: Kod CN na fakturze → mapa Załącznika 15 (47 kodów)
2. SECONDARY DETECTION: Analiza semantyczna opisu towaru/usługi przez 
   LLM bridge (C2) → wykrywanie towarów wrażliwych nawet przy braku CN
3. TERTIARY DETECTION: Historyczna analiza kontrahenta — jeśli kontrahent 
   regularnie wystawia faktury z MPP, nowa faktura bez MPP → alert
4. AUTO-CORRECTION: Automatyczne oznaczenie faktury jako SPLIT_PAYMENT + 
   wygenerowanie komunikatu przelewu MPP z rozbiciem na netto+VAT

4.1. Mechanizmy Fallback i Validation

STAN OBECNY:
- fallback.rego: 1 reguła — default fallback (ostatnia deska ratunku)
- validation.rego: 8 reguł (5 BLOCK, 3 TRIAGE) — walidacja pól faktury
- api_fallback.rego: reguły fallback dla API zewnętrznych
- routing.rego: P10-P19 — field confidence z BLOCK_AND_ALERT/TRIAGE_QUEUE

System _routing:
- BLOCK_AND_ALERT: sygnalizuje krytyczny błąd wymagający interwencji 
  człowieka. Występuje przy: fraud (P0-P9), niski confidence (P10/P12), 
  sankcje MPP (P102), obowiązek korekty dłużnika (P184), przekroczony 
  termin odliczenia (P188), przedawnienie (R0424, R0447)
- TRIAGE_QUEUE: sygnalizuje niepewność wymagającą weryfikacji. Występuje 
  przy: OSS rejestracja (S21-210), korekty wieloletnie (S21-500), 
  VAT-ZT (P120-P121)
- Puste _routing: decyzja automatyczna (AUTO_POST przy trust score ≥0.92)

OCENA: ★★★★☆ (4/5) — System jest DOBRZE zaprojektowany. Progi są 
generalnie optymalne.

4.2. Propozycja "Zero-Defect" dla VAT

INNOWACYJNY SYSTEM 3-WARSTWOWEJ WERYFIKACJI:

WARSTWA 1 — PRE-EVALUATION (przed OPA):
- Walidacja input: czy wszystkie wymagane pola są obecne?
- Cross-reference: czy NIP kontrahenta jest na Białej Liście?
- CN code validation: czy kod CN jest poprawny dla kategorii?
- Duplicate detection: czy faktura już istnieje w systemie?

WARSTWA 2 — IN-EVALUATION (w trakcie OPA):
- Każda reguła VAT ma pole _confidence_score (0.0-1.0)
- Jeśli reguła nie ma 100% pewności → TRIAGE_QUEUE
- Mechanizm "second opinion": dla decyzji z confidence < 0.90, 
  uruchom alternatywną ścieżkę ewaluacji (np. reguły Micro Layer)

WARSTWA 3 — POST-EVALUATION (po OPA):
- Cross-check: VAT z faktury == VAT z JPK_V7 == VAT z PKPiR?
- Sanity check: VAT rate dla danej kategorii jest zgodny z historycznym?
- Anomaly detection: czy VAT rate różni się od wzorca dla kontrahenta?

8.1. Hiperinflacja (stawki VAT zmieniają się co miesiąc)

8.2. Upadłość kontrahenta (korekta VAT od należności nieściągalnych)

System NIE ma dedykowanej reguły dla upadłości kontrahenta. 
Art. 89a ust. 2a VAT mówi, że wierzyciel może skorygować VAT 
w okresie, w którym powziął wiadomość o upadłości (NIE musi czekać 
90 dni). Obecne reguły P60/P189 wymagają 90/150 dni niezależnie 
od upadłości — to BŁĄD.

8.3. Masowa korekta (1000 faktur jednocześnie)

System obsługuje korekty zbiorcze (corrections.rego: R0429). Ale 
przy 1000 faktur, ewaluacja OPA może zająć >30s, przekraczając 
typowe timeouty API. Potrzebny mechanizm stronicowania/batchowania.

8.4. Atak na KSeF (72h niedostępności)

System ma regułę dla 7-dniowego grace period (R0666), ale NIE ma:
- Automatycznego przełączenia w tryb offline
- Kolejkowania faktur do wysyłki po przywróceniu KSeF
- Monitorowania statusu KSeF API (health check co 5 minut)

```
}
```
I zmodyfikować reguły VAT aby sprawdzały temporalną stawkę.

10. OPTYMALIZACJA WYDAJNOŚCI
================================================================================

10.1. Analiza else-chain w micro/vat/vat.rego (~571 reguł)

Struktura: Każdy z ~85 artykułów VAT ma 8-12 reguł (eligibility, 
positive_1/2/3, negative_1/2, exception_1/2, interaction_1/2, deadline, 
sanction). Każda reguła ma unikalny priority (50005-50571).

PROBLEM: W worst-case, OPA musi przejść przez wszystkie 571 reguł 
(ostatnia reguła w łańcuchu = 571 porównań). Dla każdej transakcji 
VAT, w której pierwsze 570 reguł NIE pasuje, to ~570 porównań × 
~50 pól = ~28,500 operacji.

ROZWIĄZANIE: "Artykułowy Pre-Filter"
Zamiast liniowego łańcucha 571 reguł, podzielić na grupy per artykuł 
i najpierw sprawdzić czy artykuł ma zastosowanie:
```
vat_a5_applies = true { input.invoice.vat_article_5_applicable == true }
vat_a7_applies = true { ... }
...
```
To redukuje worst-case z 571 do ~12 (max reguł per artykuł).

10.2. Innowacyjne mechanizmy indeksowania

INDEKS KATEGORYCZNY: Zamiast else-chain dla stawek (P52-P67), użyć 
hash-mapy category_code → (vat_rate, gtu_code). OPA wspiera object 
lookup O(1):
```
vat_rate_map := {
    "FUEL": {"rate": "0.23", "gtu": "GTU_04"},
    "FOOD": {"rate": "0.05", "gtu": "GTU_07"},
    ...
}
result := vat_rate_map[input.invoice.category_code]
```

To zastąpiłoby ~16 reguł else-chain jednym lookupem — redukcja 
z 16 porównań do 1.

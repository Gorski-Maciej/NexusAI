A. generate_manifest.py — ★★★★☆

Funkcje:
- Parsuje wszystkie pliki .rego, ekstrahuje rule_id, priority, _legal_basis, _routing
- Zlicza matched:true, BLOCK_AND_ALERT, TRIAGE_QUEUE
- Generuje MANIFEST.md z tabelami per plik
- Tryb --check tylko weryfikuje spojnosc (nie nadpisuje)

Problemy:
- Uzywa regex do parsowania Rego — AWARYJNE dla zagniezdzonych struktur!
  Reguły z `in {"X","Y"}` w body NIE sa poprawnie parsowane.
- MANIFEST.md jest NIEZAKTUALIZOWANY — deklaruje 633 regul / 38 plikow,
  podczas gdy rzeczywiscie jest ~10,185 regul w 180+ plikach.
- Brak obslugi nowych inicjatyw S1-S24 i Hyper-Plan45 w generowanych tabelach

Rekomendacje:
- Uruchamiac generate_manifest.py po kazdym merged PR
- Dodac obsluge nowych pakietow (S1-S24, hyper)
- Dodac sekcje "Enterprise Initiatives" w generowanym manifeście

B. lint_rego_rules.py (B3) — ★★★★★

To jest NAJWAZNIEJSZE narzedzie jakosci w calej infrastrukturze.
6 walidacji na poziomie CI:

1. matched_true_required — kazda regula zwraca matched:true (bez silent fails)
2. no_fallback_allow — kazda regula ma explicit _routing
3. rule_id_canonical — rule_id w formacie jdg.<package>.<rule>
4. no_hardcoded_integers — zero magicznych liczb (poza thresholds_jdg.rego)
5. legal_basis_required — kazda regula ma _legal_basis
6. temporal_validity — kazda regula ma wpis w rejestrze temporalnym

Tryby:
- --ci: exit 1 on failures (do CI/CD pipeline)
- --json: output JSON (do integracji z narzedziami)
- --check <nazwa>: pojedyncza walidacja
- --verbose: szczegolowe logowanie

Problemy:
- NIE jest zintegrowany z .pre-commit-config.yaml!
- Walidacja 6 (temporal_validity) jest "pass-through" — zawsze przechodzi
  bo jest niekompletna
- EXCLUDED_FILES i EXCLUDED_RULE_IDS sa hardcoded — powinny byc w konfiguracji

Rekomendacje:
- Dodac jako hook pre-commit: `python JDG/tools/lint_rego_rules.py --ci`
- Dokonczyc walidacje temporal_validity z integracja DuckDB
- Przeniesc EXCLUDED_* do pliku konfiguracyjnego .rego-lint.yaml

C. validate_rules.py — ★★★★☆

Walidacje:
1. Wszystkie reguly maja matched:true lub matched:false
2. Wszystkie reguly maja _legal_basis
3. Wszystkie reguly maja _routing
4. Brak hardcoded wartosci (progi, stawki, kwoty, daty)
5. Spojnosc else-chain (kolejnosc priorytetow)
6. Unikalnosc rule_id

Problemy:
- Nie sprawdza cross-package consistency (czy reguly z roznych pakietow
  nie konfliktuja ze soba)
- Nie wykrywa "dead rules" (regul z matched:true ale nigdy nieosiagalnych
  ze wzgledu na else-chain)
- Nie sprawdza priority gaps (luk w numeracji priorytetow)

Rekomendacje:
- Dodac walidacje cross-package consistency
- Dodac "dead code" detection dla regul Rego
- Dodac "priority gap" detection

D. judgment_predictor.py (C1) — ★★★★★

To jest PELNY silnik predykcji ryzyka podatkowego. Architektura:

1. JudgmentPredictor:
   - Shadow mode — nie modyfikuje glownej decyzji, tylko analizuje "what-if"
   - 9 kategorii shadow checks:
     - _check_whitelist — Biala Lista VAT (Art. 117ba OP)
     - _check_split_payment — MPP (Art. 108a VAT)
     - _check_cash_limit — gotowka >15k (Art. 22p PIT)
     - _check_vat_exemption — prog 200k VAT (Art. 113 VAT)
     - _check_bad_debt — zle dlugi (Art. 89a VAT)
     - _check_kks_offenses — przestepstwa KKS (Art. 54-83)
     - _check_documentation — brak dokumentow
     - _check_deadlines — terminy
     - _check_tp_risk — ceny transferowe

2. KKSFineCalculator:
   - Kalkulacja kar KKS w stawkach dziennych
   - 16 typow naruszen z karami (od 500 PLN do 2,000,000 PLN)
   - 3 metody kalkulacji: daily_rates, percentage, fixed

3. PredictionResult:
   - risk_score: 0-100 (wazona suma severity × probability)
   - max_severity: LOW/MEDIUM/HIGH/CRITICAL
   - total_potential_fines: suma potencjalnych kar
   - total_expected_cost: wartosc oczekiwana (fines × probability)

4. build_simulate_response():
   - Gotowe JSON dla API /jdg/simulate

DEMO pokazuje kompletny przypadek: faktura 25,000 PLN za stal (MPP),
platnosc gotowkowa, kontrahent spoza Bialej Listy, JDG przekracza
prog zwolnienia VAT — 4 znaleziska ryzyka!

Rekomendacje:
- Zintegrowac z main_jdg.rego jako "Pass 0: SHADOW_PREDICT"
- Dodac endpoint /jdg/simulate w OpenAPI
- Dodac historie predykcji do DuckDB

E. llm_bridge.py (C2) — ★★★★★

Most Rego-LLM do tlumaczenia technicznych werdyktow na jezyk naturalny.

Architektura:
1. 3 modele LLM:
   - Gemini 2.0 Flash (200ms, 0.00002$/1k input, 1M context) — default
   - Claude 3.5 Haiku (300ms, 0.0008$/1k, 200k context) — complex_legal
   - GPT-4o Mini (400ms, 0.00015$/1k, 128k context) — educational

2. 5 styli wyjasnien:
   - ADVISOR — ton doradcy: "Panie Marku, masz prawo do..."
   - COMPLIANCE — formalny
   - EDUCATIONAL — "Dlaczego? Bo ustawa mowi..."
   - EXECUTIVE — krotko, na temat
   - ELI5 — "Explain Like I'm 5"

3. ContextCompressor:
   - Kompresuje _provenance_tree do minimalnej liczby tokenow
   - Zachowuje rule_id, legal_basis, routing, warnings, thresholds

4. PromptTemplates:
   - 4 szablony: BLOCK_ALERT, TRIAGE, ALLOW, SIMULATION
   - Kazdy zoptymalizowany pod niski token count
   - System prompt z 8 zasadami (empatia, brak zargonu, disclaimer)

5. Dwa tryby:
   - explain(verdict, provenance_tree) — tlumaczenie werdyktu
   - simulate(prediction_result) — tlumaczenie predykcji C1

PROBLEM:
   - Wszystkie odpowiedzi LLM sa SYMULOWANE (metoda _simulate_llm_response)
   - W produkcji potrzebne jest rzeczywiste API call do Gemini/Claude/GPT

Rekomendacje:
- Dodac rzeczywista integracje z Google AI API (Gemini)
- Dodac endpoint /jdg/explain w OpenAPI
- Dodac streaming SSE dla natychmiastowego wyswietlania

1.1. Modular Monolith — granice modulow
----------------------------------------

NexusAI stosuje architekture Modularnego Monolitu z wyraznym podzialem na
4 warstwy DDD (Domain-Driven Design):

    PRESENTATION:  Flet UI (Flutter, Material Design 3)
    APPLICATION:   Litestar API, Taskiq Workers, Event Handlers, CQRS
    DOMAIN:        Aggregates, Value Objects, Domain Events
    INFRASTRUCTURE: SQLModel ORM, TigerBeetle, NATS, DuckDB, llama-cpp

ADR-006 uzasadnia wybor Modularnego Monolitu nad mikrousługami:
+ Aplikacja desktopowa — wszystkie komponenty na jednej maszynie
+ Prostsze wdrozenie — jeden proces
+ Latwiejsze debugowanie
+ NATS jako przygotowanie do przyszlego rozproszenia (UNIX socket → TCP)
- Trudniejsze testowanie izolowanych modulow

Granice modulow:
- nexus_ai/api/ — warstwa aplikacji (Litestar)
- nexus_ai/services/ — logika biznesowa (~60+ serwisow)
- nexus_ai/domain/ — agregaty, value objects, domain events
- nexus_ai/events/ — event sourcing, event store, projekcje
- nexus_ai/core/ — infrastruktura (DI, config, NATS, taskiq)
- nexus_ai/db/ — dostep do danych (SQLModel, DuckDB, vector store)

Ocena granic: ★★★★☆ (4/5)

+ Wyrazny podzial na warstwy zgodny z DDD
+ Domain layer jest czysta — nie zalezy od infrastruktury
+ Services layer jest najwiekszy (~60 plikow) — znak bogatej logiki biznesowej
+ Event sourcing z prawdziwym event store (nie tylko log)

- Services layer jest zbyt duzy i nie ma wewnetrznego podzialu na
  podmoduly (bounded contexts). 60+ serwisow w jednym katalogu to
  "Big Ball of Mud" w warstwie aplikacyjnej.
- Brak explicite zdefiniowanych Bounded Contexts (Fakturowanie,
  Kontrahenci, KSeF, TigerBeetle, Analityka)
- Architektura miesza CQRS w API z tradycyjnym CRUD w serwisach

1.2. CQRS + Event Sourcing — separacja Command/Query
------------------------------------------------------

Architektura implementuje CQRS przez:
- Litestar controllers — obsluga Command (POST, PUT, DELETE)
- DuckDB + Polars — obsluga Query (analityka, dashboard)
- ProjectionWorker — buduje CQRS read models na podstawie zdarzen

Domain Events (events/domain_events.py):
- Tagged Unions przez msgspec.Struct z tag_field="event_type"
- Auto-rejestracja przez __init_subclass__
- Kategorie: invoice.created, invoice.approved, decision.made,
  invoice.paid, notification.sent, outbox.emitted
- Serializacja: msgspec.msgpack.encode/decode

InvoiceAggregate (domain/aggregates.py):
- Maszyna stanow z 11 stanami (NEW → PROCESSING → APPROVED → PAID)
- Niezmienniki: kwoty >= 0, waluta ISO 4217, amount_net <= amount_gross
- Optymistyczna kontrola wspolbieznosci przez version
- UUIDv7 (sortowalne, chronologiczne ID)
- Kolekcjonowanie zdarzen: collect_events()

Ocena CQRS: ★★★★☆ (4/5)

+ Czysta separacja — agregaty emituja zdarzenia, projekcje buduja
  read models
+ Event sourcing jest PRAWDZIWY — zdarzenia sa immutable facts, nie
  tylko logiem zmian
+ msgspec.msgpack dla wydajnej serializacji (2-5x szybszej niz JSON)
+ Maszyna stanow InvoiceAggregate jest dobrze zdefiniowana

- Brak Command Bus — komendy nie sa jawnie modelowane, zamiast tego
  uzywane sa bezposrednie wywolania serwisow
- Brak dedykowanych Command Handlers — logika komend jest rozproszona
  miedzy kontrolerami API i workerami
- Query model (DuckDB) nie jest czescia CQRS — jest to osobny OLAP
  zamiast dedykowanych read models per agregat
- Event Store (EventStore w events/) istnieje, ale brak pelnego
  rekonstytuowania agregatow z historii zdarzen

1.3. NATS JetStream jako event bus
-------------------------------------

NATS JetStream pelni role:
- Brokera wiadomosci miedzy API a workerami
- Trwalego logu zdarzen (persistent streams)
- Dead Letter Queue dla nieudanych zadan
- Key-Value Store (NatsConfigStore)
- Object Store (NatsFileStore)

Topologia strumieni (ARCHITECTURE.md):
| Strumien        | Tematy                              | Retencja | Max delivery |
|-----------------|-------------------------------------|----------|-------------|
| invoices        | invoice.received, invoice.extracted | 7 dni    | 3           |
| council         | council.task.request, decision.final| 90 dni   | 5           |
| outbox          | outbox.relay                        | Do ack   | 10          |
| billing         | billing.rules.updated               | 1h       | 1           |
| risk            | risk.thresholds.updated             | 1h       | 1           |
| tax             | tax.rule.updated                    | 1h       | 1           |

ADR-003 uzasadnia wybor NATS nad RabbitMQ:
+ Plik binarny ~10 MB, brak kontenera
+ Wbudowany KV Store i Object Store
+ At-least-once delivery przez JetStream
+ UNIX socket dla komunikacji lokalnej
+ ~15-25 MB RAM w spoczynku

Ocena NATS: ★★★★★ (5/5)

+ Pelna gama funkcji: Pub/Sub, JetStream, KV Store, Object Store
+ Przemyslana topologia strumieni z roznymi retencjami
+ DLQ dla nieudanych zadan
+ Obsluga reconnectu z wykladniczym backoffem
+ NatsSupervisor do monitorowania stanu strumieni

- Konfiguracja strumieni jest "create-or-skip" — brak explicit
  zarzadzania wersjami konfiguracji strumieni (Infrastructure as Code)
- Brak mirroringu/klastrowania NATS dla High Availability

2.2. Middleware — rate limiting, CORS, JWT, CSRF
--------------------------------------------------

Kompletny stack middleware:

Rate Limiting:
  - RateLimitConfig z per-role identifier (_role_aware_identifier)
  - Zalogowani: user:{role}:{user.id}
  - Auth endpoints: auth:{ip} — brute-force protection
  - Niezalogowani: anon:{ip}
  - Konfiguracja: rate_limit_auth=10/min, rate_limit_general=60/min

CORS:
  - CORSConfig z allow_origins z configu
  - allow_credentials warunkowo (nie dla "*")
  - allow_methods=["*"], allow_headers=["*"]

CSRF:
  - CSRFConfig z JWT secret jako CSRF secret
  - safe_methods: GET, HEAD, OPTIONS, TRACE
  - exclude patterns dla auth endpointow
  - wlaczane warunkowo (config.csrf_enabled)

Security Headers (app_after_request):
  - X-Content-Type-Options: nosniff
  - X-Frame-Options: DENY
  - Referrer-Policy: no-referrer
  - Permissions-Policy: geolocation=(), microphone=(), camera=()
  - Content-Security-Policy: default-src 'self'

Tenant Context (TenantContextMiddleware):
  - Ustawia ContextVar tenant_id dla kazdego requestu
  - Ekstrakcja z JWT token (Rust verify_jwt)
  - x-correlation-id, x-tenant-id, x-request-id w odpowiedzi
  - structlog.contextvars dla automatycznego kontekstu logowania

Ocena middleware: ★★★★★ (5/5)

+ Kompletny zestaw middleware dla produkcji
+ Per-role rate limiting (unikalna cecha)
+ Tenant context z ContextVar — thread-safe
+ Security headers zgodne z OWASP
+ CSRF z wylaczeniami dla API

- Brak observability middleware (tracing ID propagacja miedzy
  serwisami przez naglowki W3C Trace Context)

2.3. Granian (Rust ASGI server) — konfiguracja
------------------------------------------------

Granian jest serwerem ASGI napisanym w Rust, skonfigurowanym z
kompletnym zestawem "supermocy" (server.py):

Core networking:
+ Host/Port lub UNIX socket (NEXUS_UNIX_SOCKET)
+ Backlog 2048, Backpressure 100 (ochrona przed zalaniem)
+ HTTP auto-negotiation (HTTP/1.1 + HTTP/2)
+ HTTP/2 flow control tuning (connection/stream windows)

Workers & threading (dla Python 3.13t):
+ Dynamiczna liczba workerow: max(1, cpu_count()-1)
+ Runtime threads: 2, Runtime blocking threads: 4
+ Worker lifecycle: max RSS, lifetime, kill timeout, respawn

Monitoring:
+ Wbudowane Prometheus metrics (:9090)
+ Custom access log format
+ Process name, PID file

Security & performance:
+ no_header_server (ukrywa "Granian")
+ URL path prefix
+ Static file serving w warstwie Rust (zero Python overhead)
+ Proxy headers support (X-Forwarded-For, X-Forwarded-Proto)

Dla produkcji (api-prod):
+ 4 workers
+ Worker max RSS: 1024 MB
+ Worker lifetime: 86400s (24h)
+ Graceful shutdown: 30s

Ocena Granian: ★★★★★ (5/5)

+ Pelna konfiguracja produkcyjna przez zmienne srodowiskowe
+ UNIX socket dla desktop mode (bezpieczenstwo)
+ Dynamiczna liczba workerow (wykorzystanie wszystkich rdzeni)
+ Worker lifecycle management (max RSS, lifetime, respawn)
+ Static file serving w Rust (zero Python overhead)
+ Graceful shutdown z configurowalnym timeoutem

- Brak mTLS dla production deployments
- Brak Let's Encrypt / ACME integracji

3.1. JetStream — exactly-once delivery
----------------------------------------

NATS JetStream zapewnia:

Pull-based consumer (PullBasedJetStreamBroker):
+ max_ack_pending=5 — kontrola wspolbieznosci konsumpcji
+ pull_consume_batch=1 — jeden task na raz
+ pull_consume_timeout=5.0 — timeout na fetch
+ queue_group="nexus-ai-workers" — load balancing

Deduplikacja (task_id_generator):
+ Deterministic task_id = hash(task_name + sorted(kwargs))
+ NATS JetStream Nats-Msg-Id automatycznie odrzuca duplikaty
  w oknie duplicate_window=2min
+ Zastepuje reczna tabele processed_events

Dead Letter Queue:
+ Temat: nexus.dlq.tasks
+ Stream dlq z retencja
+ DLQ stats przez API

Reconnect:
+ max_reconnect_attempts=-1 (nieskonczone)
+ wykladniczy backoff (reconnect_time_wait=2.0s)
+ Callbacki: on_disconnect, on_reconnect, on_close, on_error

Ocena JetStream: ★★★★★ (5/5)

+ Deterministic deduplikacja (genialny pomysl!)
+ Exactly-once semantics przez Nats-Msg-Id
+ DLQ z pelna obsluga przez API
+ Nieskonczony reconnect (nigdy nie traci zadan)
+ Wbudowany KV Store i Object Store

- duplicate_window=2min — co z duplikatami poza oknem?
- Brak dead-letter queue monitoring/alertow

3.2. Taskiq-NATS integracja
-----------------------------

Taskiq jest zintegrowany przez:

Broker (broker.py):
+ PullBasedJetStreamBroker jako jedyny broker
+ Middleware: TaskMetrics, PiiScan, TaskTracing,
  DynamicConcurrency, SentryTask
+ Result Backend: SqliteResultBackend lub HybridResultBackend
  (NATS Object Store + SQLite fallback)
+ Emit_event() — dynamiczne mapowanie typu eventu na task

Middleware:
+ TaskMetricsMiddleware — OTel metryki dla kazdego zadania
+ PiiScanMiddleware — skanowanie NIP/PESEL/REGON/EMAIL
+ TaskTracingMiddleware — OTel tracing (trace_id, span_id)
+ DynamicConcurrencyMiddleware — limit wspolbieznosci + CPU/RAM
  monitoring
+ SentryTaskMiddleware — Sentry scope dla zadan

Result Backend:
+ SqliteResultBackend — SQLite dla audytu wynikow
+ HybridResultBackend — NATS Object Store + SQLite fallback
+ Schemat: taskiq_results z indeksami

State machine zadan (tasks/invoice.py):
+ InvoiceProcessingMachine
+ Proces: uploaded → ocr_completed → extracted → decision_made
+ StateProxy do zarzadzania stanem

Ocena Taskiq: ★★★★☆ (4/5)

+ Kompletny stack middleware
+ Deterministic task_id dla deduplikacji
+ Dual result backend (NATS + SQLite)
+ PiiScan przed wysylka (genialne!)
+ Dynamiczna kontrola wspolbieznosci

- InvoiceProcessingMachine uzywa wlasnej implementacji state
  machine zamiast wbudowanego w agregat InvoiceAggregate
- Brak wizualizacji stanow zadan (dashboard Taskiq)

3.3. Event bus — saga pattern
-------------------------------

Typed EventBus (core/bus.py):

NATS Event Bus (events/jetstream_bus.py):
+ JetStreamEventBus przez DI
+ Zewnetrzna komunikacja miedzy workerami

Saga pattern:
+ Wspomniany w ARCHITECTURE.md jako wzorzec
+ SagaTransitionDTO / SagaStateDTO w api/dto.py
+ Brak pelnej implementacji wzorca Saga (kompensacja,

Ocena Event Bus: ★★★☆☆ (3/5)

+ Typed EventBus jest dobrze zaprojektowany
+ Event history dla late subscribers
+ Structured concurrency

- Saga pattern NIE jest w pelni zaimplementowany — brak
  koordynatora sag, kompensacji, retry policy per krok
- Typed EventBus jest in-process (nie przechodzi przez NATS)
  — ogranicza skalowalnosc do jednego procesu

5.1. Domain Events — Tagged Unions
------------------------------------

System domain events (events/domain_events.py) uzywa msgspec.Tagged
Unions z auto-rejestracja przez __init_subclass__:

Klasy zdarzen:
- InvoiceCreated, InvoiceSubmitted, InvoiceApproved, InvoiceRejected
- InvoiceBlocked, InvoicePaid
- DecisionMade, DecisionOverridden
- OutboxEventEmitted, NotificationSent

Struktura:
- tag_field="event_type" — identyfikacja typu
- Wszystkie pola z domyslnymi wartosciami
- Serializacja: msgpack encode/decode
- JSON Schema auto-generowane z rejestru

Ocena: ★★★★★ (5/5)

+ Tagged Unions — bezpieczenstwo typow dla zdarzen
+ Auto-rejestracja — nie trzeba recznie dodawac do rejestru
+ msgpack — szybka serializacja binarna
+ Auto-generowane JSON Schema

5.2. Event Store
------------------

EventStore (events/event_store.py):
+ SQLite-backed event store
+ Schemat: events z aggregate_id, event_type, payload
+ Append-only — zdarzenia sa niezmienne
+ Wsparcie dla snapshotow

5.3. Projekcje i ProjectionWorker
-----------------------------------

ProjectionWorker (events/projection_worker.py):
+ Buduje CQRS read models z event stream
+ Fallback poll EventStore gdy NATS niedostepny
+ Graceful degradation

10. 10 INNOWACYJNYCH USPRAWNIEN WYPRZEDZAJACYCH PROFESJONALISTOW
================================================================================

[INNOWACJA 1] Command Bus z MediatR-Style:
Wprowadzic Command → CommandHandler → Events pipeline przez NATS.
Kazda komenda (InvoiceSubmitCommand) przechodzi przez:
1. CommandValidator (walidacja)
2. CommandHandler (logika biznesowa, agregat)
3. EventPublisher (NATS JetStream)
Dzieki temu pelna audytowalnosc i mozliwosc replay.

[INNOWACJA 2] Materialized Views przez DuckDB Change Data Capture:
Zamiast budowac read models recznie, DuckDB subskrybuje NATS JetStream
i automatycznie aktualizuje materialized views przy kazdym zdarzeniu.
Zero kodu projekcji — sama konfiguracja SQL.

[INNOWACJA 3] Distributed Saga Coordinator:
Koordynator sag przez NATS JetStream z:
- Saga definition (kroki, kompensacja, timeout)
- Saga state persistence w JetStream KV Store
- Automatyczna kompensacja przy bledzie
- Timeouty i retry per krok

[INNOWACJA 4] Hot-Cold Storage dla Event Store:
Zdarzenia:
- Hot (<30 dni): SQLite, szybki dostep
- Cold (>30 dni): Parquet + ZSTD na dysku
- Query przez DuckDB — laczy hot + cold transparentnie

[INNOWACJA 5] Circuit Breaker per External Service (nie tylko stamina):
Dla kazdego external API (KSeF, GUS, NBP, Biala Lista) osobny circuit
breaker z wlasnymi progami i cooldown. Stamina jest za ogolna.

[INNOWACJA 6] Business Event Versioning:
Kazdy domain event ma wersje schematu. Event store przechowuje
wszystkie wersje. Projekcje obsluguja upcasting (v1 → v2).
Zgodne z EventStoreDB best practices.

[INNOWACJA 7] Natywny GraphQL API przez Litestar Strawberry:
Dodac GraphQL endpoint dla analityki — klienci moga pytac o dokladnie
te dane ktorych potrzebuja, bez over-fetching.

[INNOWACJA 8] Predictive Auto-Scaling Workerow:
Worker monitoruje: CPU, RAM, dlugosc kolejki NATS.
Predykcyjnie uruchamia/zatrzymuje dodatkowe instancje przez
WorkerPoolManager. Cel: kolejka zawsze <10 zadan.

[INNOWACJA 9] Zero-Trust Service Mesh:
mTLS miedzy wszystkimi komponentami (API ↔ NATS, NATS ↔ Worker,
Worker ↔ OPA). Certyfikaty automatycznie rotowane przez
wbudowane CA (Smallstep lub cert-manager).

[INNOWACJA 10] Auditable Configuration Changes:
Kazda zmiana konfiguracji jest zdarzeniem domenowym
(ConfigChanged). Zdarzenia zapisywane w event store. Mozliwosc
rollbacku do poprzedniej konfiguracji. Git-like diff configu.

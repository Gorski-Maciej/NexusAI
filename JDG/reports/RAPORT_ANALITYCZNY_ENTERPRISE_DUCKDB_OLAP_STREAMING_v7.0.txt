1.1. DUCKDB MANAGER — ARCHITEKTURA
--------------------------------------------------------------------

STATUS: DOSKONALA — Thread-safe, Zero-ETL, Arrow-native

DuckDBManager to centralny komponent warstwy OLAP:

Kluczowe cechy:
- Per-thread connections przez threading.local() — bezpieczenstwo w
  Python 3.13t free-threaded
- Globalny rejestr polaczen (_all_connections) dla poprawnego close()
- Krotkozyciowe polaczenia dla SELECT (get_connection_for_query)
- Blokada DDL dla CREATE/DROP/ALTER (_ddl_lock)
- Konfiguracja: memory_limit (512MB), threads (2), perfect_ht_threshold (2)

Zero-ETL ATTACH SQLite:
- DuckDB bezposrednio czyta SQLite przez ATTACH 'oltp' (TYPE SQLITE)
- ZERO kopiowania danych miedzy OLTP a OLAP
- DuckDB ma pelny dostep do tabel SQLite (invoices, invoice_items...)
- Zapytania lacza dane z obu swiatow bez ETL pipeline

Optymalizacje:
- preserve_insertion_order=false — szybsze agregacje
- default_null_order='NULLS_LAST' — spojnosc sortowania
- arrow_large_buffer_size=true — duze wyniki w Arrow
- enable_profiling='query_tree' — diagnostyka
- Profilowanie wolnych zapytan (>100ms) z auto-logowaniem

OCENA ARCHITEKTURY: 95/100

Zalety:
+ Zero-ETL — DuckDB czyta SQLite bezposrednio
+ Thread-safe w Python 3.13t
+ Arrow zero-copy do Polars
+ Auto-profilowanie wolnych zapytan
+ Parquet eksport/import z predicate pushdown

Ograniczenia:
- Brak multi-tenancy (wspoldzielone memory_limit 512MB)
- Brak automated materialized view refresh
- DuckDB connections nie sa thread-safe (per-thread konieczne)
- single-file database — brak shardingu

1.3. INTEGRACJA DUCKDB <-> SQLite (OLTP)
--------------------------------------------------------------------

STATUS: WZORCOWA — Zero-ETL przez ATTACH

Architektura Zero-ETL:
  DuckDB ATTACH 'app_data/nexus_oltp.db' AS oltp (TYPE SQLITE)
  -> DuckDB czyta SQLite BEZ KOPIOWANIA
  -> Zapytania SQL lacza dane OLTP + OLAP w jednym query

Hook-based replication:
  Po kazdym SQLite commit -> replikacja do DuckDB przez db/hooks.py
  -> Single invoice sync (sync_single_invoice_to_duckdb)

OCENA INTEGRACJI: 90/100

Zalety:
+ Zero-ETL — brak pipeline'u ETL
+ Hook-based replication (real-time sync)
+ DuckDB ma bezposredni dostep do SQLite
+ Brak zdublowanych danych (DuckDB czyta z SQLite)

Ograniczenia:
- DuckDB queries na SQLite moga byc wolniejsze niz natywne DuckDB
- Brak incremental sync (tylko DELETE + INSERT lub hook-based)
- Konflikt lockow: SQLite WAL vs DuckDB ATTACH

1.4. ZAPYTANIA ANALITYCZNE — CZY BLOKUJA OLTP?
--------------------------------------------------------------------

NIE — architektura to uniemozliwia:

- DuckDB czyta SQLite w trybie read-only (ATTACH TYPE SQLITE)
- SQLite WAL mode pozwala na wspolbiezne zapisy i odczyty
- Per-thread DuckDB connections izoluja zapytania
- SELECT uzywaja krotkozyciowych polaczen (get_connection_for_query)
- DDL/DML przez blokade _ddl_lock

2.1. DuckDB — VECTORIZED EXECUTION
--------------------------------------------------------------------

DuckDB wykorzystuje pelna moc vectorized execution:
- Operacje na wektorach (kolumnach), nie na pojedynczych wierszach
- Query optimizer: predicate pushdown, filter pushdown, projection pushdown
- Parallel query execution (SET threads=2)
- Hash join z perfect_ht_threshold dla malych tabel

Arrow Integration:
- execute_arrow() zwraca pyarrow.Table — zero-copy do Polars
- arrow_large_buffer_size=true dla duzych wynikow
- fetch_arrow_table() zamiast fetchall() — 2-5x szybciej

OCENA: 90/100

3.1. NATS JETSTREAM JAKO EVENT STORE — CQRS/ES
--------------------------------------------------------------------

STATUS: DOBRA — Pelny event sourcing

Architektura Event Sourcing / CQRS:

  [Domain Event] -> [JetStreamEventBus] -> NATS JetStream
                                                |
  +--------------------+------------------------+
  |                    |                        |
  [AsyncEventStore]   [ProjectionWorker]      [NotificationService]
  (append-only)       (CQRS read-side)

AsyncEventStore (SQLite + Parquet):
- Append-only — zdarzenia NIGDY nie sa modyfikowane
- Wersjonowanie: aggregate_type + aggregate_id + version
- Indeks: idx_events_aggregate (szybkie odczyty)
- Parquet archive dla dlugoterminowego przechowywania

JetStreamEventBus:
- Publikacja: nexus-{aggregate_type}.{event_type}
- Durable consumer (gwarancja dostarczenia)
- Backpressure: max_deliver=5 + DLQ
- msgspec serializacja (szybciej niz JSON)

ProjectionWorker:
- Nasluchuje NATS eventow
- Buduje CQRS read-side (InvoiceReadModel)
- Generic BaseProjection[T] z match/case

OCENA CQRS/ES: 80/100

Zalety:
+ Append-only EventStore (immutability)
+ CQRS z osobnymi read/write modelami
+ Durable consumer + DLQ
+ Parquet archive

Ograniczenia:
- Brak snapshotow (event replay od poczatku)
- Brak event versioning/schema evolution
- Brak outbox pattern (ryzyko dual-write)

1. AUDYT KSeF — KRAJOWY SYSTEM E-FAKTUR (POZIOM ENTERPRISE)
================================================================================

1.1 STRUKTURA INTEGRACJI

Integracja z KSeF opiera się na dwóch kluczowych komponentach:
- KsefService (ksef_service.py) — zarządzanie sesją i komunikacją z API MF
- KsefGenerator (ksef_generator.py) — generowanie XML FA_VAT zgodnego ze schematem XSD

Architektura jest DOPRZE PRZEMYŚLANA — separacja warstwy komunikacyjnej
od warstwy generowania dokumentów to wzorcowe rozdzielenie odpowiedzialności
(Single Responsibility Principle). KsefService odpowiada za autoryzację,
zarządzanie tokenem sesji i komunikację HTTP. KsefGenerator odpowiada za
budowanie poprawnego dokumentu XML na podstawie danych faktury i werdyktu
silnika reguł Zen-Engine.

1.2 ZARZĄDZANIE TOKENEM AUTORYZACYJNYM

KsefService implementuje standardowy flow KSeF Authorisation Challenge:
1. Klient wysyła POST /online/Session/InitToken z NIP + tokenem
2. API MF zwraca sessionToken
3. SessionToken jest przechowywany w atrybucie self.session_token

OCENA: 7/10 — Poprawna implementacja podstawowego flow. 

KRYTYCZNE BRAKI:
- Brak mechanizmu odświeżania tokenu przed wygaśnięciem. Token sesji KSeF
  wygasa po określonym czasie bezczynności. Obecny kod nie monitoruje TTL.
- Brak automatycznego re-login w przypadku 401 Unauthorized.
- Brak timeout managera — token może wygasnąć w trakcie batch send 100 faktur.
- Brak współbieżnego zarządzania tokenem (thread safety) — przy równoległych
  zapytaniach wiele wątków może próbować jednocześnie zainicjować sesję.

1.3 GENEROWANIE XML FA_VAT

KsefGenerator implementuje DWIE ŚCIEŻKI generowania XML:
  ŚCIEŻKA 1 (PREFEROWANA): xsdata — używa wygenerowanych klas z FA_VAT XSD
    - Type-safe serializacja przez XmlSerializer
    - Automatyczna walidacja typów
    - Obsługa namespace'ów z XSD
  ŚCIEŻKA 2 (FALLBACK): lxml.etree — ręczne budowanie drzewa XML
    - Pełna kontrola nad strukturą
    - Działa zawsze, nawet bez xsdata bindingów

Ta architektura dual-path jest GENIALNA w swojej prostocie. Zapewnia:
- Type safety gdy bindingi XSD są dostępne (development/production)
- Graceful degradation gdy xsdata nie jest dostępne (CI/testy)
- Łatwe testowanie — testy mogą działać bez instalacji xsdata

System rezolucji pól KSeF (_resolve_ksef_fields) implementuje TRZY POZIOMY
priorytetu:
  1. verdict["ksef_fields"] — jawne pola z reguły
  2. verdict["gtu_code"] + verdict["procedure"] — legacy pola
  3. CATEGORY_GTU_MAP — mapa kategorii na kody GTU

Mapa CATEGORY_GTU_MAP obejmuje 16 kategorii (FUEL, IT_OFFICE, FOOD, BOOKS,
EDUCATION, HEALTHCARE, TRANSPORT, ADVERTISING, RENT, CONSTRUCTION, ELECTRONICS,
PHARMA, WASTE, METAL, GAMBLING) — pokrycie jest IMPONUJĄCE na tym etapie.

Walicja XSD (validate_ksef_xml) używa lxml.ET.XMLSchema z pełnym error_log
zawierającym numery linii i kolumn każdego błędu. To PROFESJONALNE podejście
do debugowania — księgowy może zobaczyć DOKŁADNIE gdzie jest problem.

1.4 CIRCUIT BREAKER DLA API MF

Zarówno KsefService jak i WhiteListService używają stamina.retry_context
z circuit breaker:
  - 3 próby
  - timeout 10s
  - Automatyczny exponential backoff + jitter
  - Circuit breaker zapobiega przeciążeniu API MF

To PRAWIDŁOWE podejście. API MF (zarówno KSeF jak i Biała Lista) ma limity
zapytań. Circuit breaker chroni przed:
  - Kaskadowym przeciążeniem przy retry storms
  - Blokadą konta przez zbyt wiele nieudanych prób
  - Degradacją wydajności całego systemu przez wolne API zewnętrzne

1.5 CO DZIAŁA DOBRZE

- Separacja komunikacji od generowania XML — czysta architektura
- Dual-path generowania XML (xsdata + lxml) — elastyczność i odporność
- Trójpoziomowa rezolucja pól KSeF — kompletność danych
- Circuit breaker z stamina — ochrona API MF
- Walidacja XSD z pełnym error_log — profesjonalne debugowanie
- Pełna mapa GTU dla 16 kategorii — szerokie pokrycie

1.6 KRYTYCZNE LUKI — NATYCHMIASTOWE REKOMENDACJE

LUKA 1 (KRYTYCZNA): Brak batch send dla KSeF
  Obecnie KsefService nie ma metody wysyłki faktur. Jest tylko _init_session().
  KSeF API obsługuje batch do 100 faktur w jednym zapytaniu.
  REKOMENDACJA: Dodać metodę send_invoice() i send_invoice_batch().

LUKA 2 (WYSOKA): Brak obsługi statusów KSeF
  Po wysłaniu faktury do KSeF, system powinien:
  - Odbierać UPO (Urzędowe Poświadczenie Odbioru)
  - Monitorować status przetwarzania (processing, accepted, rejected)
  - Obsługiwać ponowne wysłanie przy odrzuceniu
  REKOMENDACJA: Dodać KsefStatusMonitor z pollerem statusów.

LUKA 3 (WYSOKA): Brak odbierania faktur przychodzących
  API KSeF umożliwia pobieranie faktur wystawionych dla naszego NIP-u.
  Obecnie nie ma endpointu do inboxa (chociaż docs/API.md wspomina
  o GET /api/v1/ksef/inbox).
  REKOMENDACJA: Zaimplementować KsefInboxService z automatycznym pollerem.

LUKA 4 (ŚREDNIA): Token session nie ma refresh managera
  REKOMENDACJA: Dodać SessionManager z TTL monitorowaniem i auto-refresh.

2.1 GUS BIR — SOAP CLIENT KLASY ENTERPRISE

GusBirClient to imponująca implementacja SOAP klienta dla API GUS BIR.
Kluczowe cechy:

ARCHITEKTURA:
- Czysty SOAP client — BEZ zewnętrznych bibliotek SOAP (zeep, suds)
- Ręczne budowanie XML envelope — minimalna zależność, maksymalna kontrola
- Session-based authentication (sid) z poprawnym login/logout
- Async context manager (__aenter__/__aexit__) — poprawne zarządzanie zasobami

ENDPOINTY:
- login() — autoryzacja z kluczem API, pobranie SID
- search_by_nip() — wyszukiwanie firm po NIP (DaneSzukaj)
- get_full_report() — pełny raport dla REGON (DanePobierzPelnyRaport)
- logout() — poprawne zwolnienie sesji
- enrich_from_nip() — KOMPLETNY PIPELINE wzbogacania danych

RESILIENCE:
- stamina.retry_context z circuit breaker dla każdego endpointu
- 3 próby, timeout 15s
- Obsługa httpx.HTTPStatusError, TimeoutException, RequestError, ConnectionError
- Graceful degradation — błędy nie propagują się kaskadowo

PARSOWANIE XML:
- _extract_result() — ekstrakcja zawartości tagu Result z namespace'ami
- _parse_search_results() — parsowanie XML z html.unescape dla polskich znaków
- _parse_full_report() — parsowanie pełnego raportu z kodami PKD
- _extract_tag() — uniwersalny ekstraktor tagów z obsługą namespace'ów

FUNKCJA enrich_from_nip() to MAJSTERSZTYK inżynierii integracyjnej:
W JEDNEJ METODZIE wykonuje:
  1. login() → pobranie SID
  2. search_by_nip() → znalezienie firmy
  3. get_full_report() → pełne dane z PKD
  4. logout() → zawsze wykonane w finally
  5. Graceful degradation → jeśli cokolwiek pójdzie nie tak, zwraca
     domyślne wartości zamiast propagate błędu

2.2 BIAŁA LISTA MF — CZYSTA IMPLEMENTACJA REST

WhiteListService implementuje weryfikację w Białej Liście Podatników VAT
Ministerstwa Finansów (wl-api.mf.gov.pl).

KLUCZOWE CECHY:
- Cache z TTL 3600s (1h) na poziomie NexusCache
- Oddzielny cache per NIP (dane podmiotu) i per NIP+konto (weryfikacja)
- Circuit breaker z stamina
- 3 próby, timeout 10s
- Graceful degradation — gdy circuit breaker otwarty, zwraca None zamiast
  blokować system

METODY:
- _fetch_nip_data() — pobiera dane podmiotu z API MF (z cachem)
- check_nip() — weryfikuje NIP i zwraca dane podmiotu
- verify_bank_account() — sprawdza czy konto bankowe jest na białej liście

PROBLEM: verify_bank_account() używa cache z TTL 3600s dla wyniku negatywnego
(300s dla null). To DOBRA PRAKTYKA — negatywne wyniki są cache'owane krócej,
bo konta mogą być dodane do białej listy w międzyczasie.

2.3 CO DZIAŁA DOBRZE

- Pełna implementacja SOAP bez zewnętrznych bibliotek — mistrzowska kontrola
- Poprawne zarządzanie sesją GUS BIR (login/logout/finally)
- Async context manager dla clean resource management
- Trójpoziomowy pipeline enrich_from_nip
- Dual cache strategy w WhiteListService (dane vs weryfikacja konta)
- Circuit breaker dla obu integracji
- Staranne parsowanie XML z polskimi znakami (html.unescape)

2.4 KRYTYCZNE LUKI

LUKA 5 (WYSOKA): Cache GUS BIR nie ma warstwy persistence
  Obecnie dane GUS BIR nie są nigdzie trwale przechowywane. Każde
  enrich_from_nip() wykonuje pełny SOAP call chain.
  REKOMENDACJA: Dodać warstwę cache w SQLite/DuckDB z TTL 24h dla
  danych GUS BIR. Dane firm zmieniają się rzadko — codzienne odpytywanie
  API dla tych samych NIP-ów to marnowanie limitów.

LUKA 6 (ŚREDNIA): Brak deduplikacji zapytań GUS BIR
  Jeśli 10 faktur od tego samego kontrahenta jest przetwarzanych równolegle,
  każda wykona osobny SOAP call.
  REKOMENDACJA: Dodać request deduplication — jeśli zapytanie dla danego NIP
  jest w toku, kolejne zapytania czekają na wynik pierwszego.

LUKA 7 (NISKA): StatusNip "AKTYWNY" jest uproszczony
  GUS BIR zwraca więcej statusów: "AKTYWNY", "ZAWIESZONY", "WYKRESLONY",
  "ZAMKNIENTY". Obecnie mapowanie jest binarne: AKTYWNY → active, else inactive.
  REKOMENDACJA: Rozszerzyć mapowanie statusów dla dokładniejszej analizy ryzyka.

3. AUDYT NBP API + ECB FALLBACK (POZIOM ENTERPRISE)
================================================================================

3.1 ARCHITEKTURA WIELOWARSTWOWEGO FALLBACKU

NbpFxClient implementuje CZTEROPOZIOMOWY system pozyskiwania kursów walut:

  POZIOM 1: Cache lokalny (TTL 86400s = 24h)
    - Szybki dostęp, zero latency
    - Per waluta+data

  POZIOM 2: NBP API (api.nbp.pl)
    - Tabela A (średnie kursy walut obcych) — codziennie
    - Tabela B (kursy średnie państw UE) — od 2025
    - Preferowana tabela konfigurowalna

  POZIOM 3: ECB Fallback (Europejski Bank Centralny)
    - Automatyczny fallback gdy NBP niedostępne
    - Przeliczenie EUR/XXX → PLN przez EUR/PLN
    - Zgodność z dyrektywą 2006/112/WE

  POZIOM 4: Last Business Day Fallback
    - Automatyczne wykrywanie weekendów i świąt
    - Rekurencyjne cofanie do ostatniego dnia roboczego
    - Obsługa polskich świąt stałych (9 świąt)

To jest IMPONUJĄCA architektura resilience. W przypadku awarii NBP (częste
w weekendy i święta), system automatycznie:
1. Próbuje cache → jeśli świeży, zwraca natychmiast
2. Próbuje NBP → jeśli dostępne, zwraca i aktualizuje cache
3. Próbuje ECB → jeśli dostępne, przelicza przez EUR/PLN
4. Próbuje ostatni dzień roboczy → zgodne z przepisami podatkowymi
5. Dopiero gdy WSZYSTKIE poziomy zawodzą → rzuca ConnectionError

3.2 ZGODNOŚĆ PODATKOWA

Implementacja jest wprost powiązana z przepisami:
- art. 14c PIT (przychody walutowe): kurs z dnia roboczego poprzedzającego
  dzień uzyskania przychodu
- art. 24 ust. 2 PIT (koszty walutowe)

Metoda convert_to_pln() przyjmuje amount, currency i date_str — zwraca
kwotę w PLN po przeliczeniu przez odpowiedni kurs.

3.3 OBSŁUGA DNI ROBOCZYCH

_last_business_day() implementuje:
- Pomijanie sobót (weekday >= 5)
- Pomijanie niedziel (weekday >= 6)
- Pomijanie 9 polskich świąt stałych

UWAGA: Nie obejmuje świąt ruchomych (Wielkanoc, Boże Ciało). To akceptowalne
na tym etapie — święta ruchome wymagają algorytmu computus (Gaussa lub
Butchera) i są rzadkie w kontekście dni roboczych.

3.4 KRYTYCZNE LUKI

LUKA 8 (KRYTYCZNA): NBP API NIE JEST ZINTEGROWANE — używa symulacji
  Metoda _fetch_nbp() zawiera ZAKOMENTOWANY kod httpx i SYMULOWANE dane:
    data = {"code": currency, "rates": [{"mid": 4.50}] if currency == "EUR" else [{"mid": 3.85}]}
  To oznacza, że kursy są HARDCODED — EUR zawsze 4.50, inne zawsze 3.85.
  REKOMENDACJA: NATYCHMIASTOWA integracja z httpx.AsyncClient dla NBP API.

LUKA 9 (KRYTYCZNA): ECB API również używa symulacji
  _fetch_ecb() ma hardcoded mapę tylko 4 walut (EUR, USD, GBP, CHF) i
  używa stałego EUR/PLN = 4.50.
  REKOMENDACJA: Zintegrować z prawdziwym API ECB (exchangeratesapi.io
  lub ecb.europa.eu).

LUKA 10 (WYSOKA): Brak tabeli C NBP (kursy kupna/sprzedaży)
  Tabela C zawiera kursy kupna i sprzedaży walut — kluczowe dla transakcji
  kantorowych i różnic kursowych. Obecnie system obsługuje tylko średni kurs.
  REKOMENDACJA: Dodać obsługę Tabeli C dla transakcji wymagających
  kursu kupna/sprzedaży.

LUKA 11 (ŚREDNIA): Brak integracji z fx_revaluation.py
  Metoda convert_to_pln() istnieje jako samodzielna. Nie widać integracji
  z systemem przeszacowania walut (fx_revaluation.py).
  REKOMENDACJA: Zintegrować NbpFxClient z modułem przeszacowania walut.

4. ANALIZA RESILIENCE I HTTP (POZIOM ENTERPRISE)
================================================================================

4.1 STACK HTTP — httpx + hishel + stamina

NexusAI używa TRÓJWARSTWOWEGO stosu HTTP:

WARSTWA 1: httpx — async HTTP client
  - Nowoczesny, async-first
  - HTTP/1.1 i HTTP/2
  - Timeouty na poziomie połączenia i zapytania

WARSTWA 2: hishel — HTTP caching
  - Zgodny z RFC 7234 (HTTP Caching)
  - Cache w SQLite lub plikach
  - Automatyczne odświeżanie przez ETag/Last-Modified
  - Integracja przez CachedHttpClient w nexus_ai.core.cache.http_client

WARSTWA 3: stamina — retry + circuit breaker
  - Dekoratory retry_context i retry
  - Circuit breaker z wykładniczym backoff + jitter
  - Konfigurowalna liczba prób, timeout, okno czasowe
  - Obsługa konkretnych typów wyjątków

Każda integracja używa WSZYSTKICH trzech warstw:
  - WhiteListService: CachedHttpClient + stamina.retry_context
  - GusBirClient: CachedHttpClient + stamina.retry_context
  - KsefService: CachedHttpClient + stamina.retry_context

To jest KLASYCZNY wzorzec resilience w systemach finansowych. Każda warstwa
dodaje kolejny poziom ochrony bez zwiększania złożoności kodu biznesowego.

4.2 CachedHttpClient — CENTRALNY PUNKT HTTP

Wszystkie integracje przechodzą przez CachedHttpClient. To zapewnia:
- Jednolitą konfigurację timeoutów
- Współdzielony cache HTTP
- Centralne logowanie requestów
- Możliwość mockowania w testach

JEDNAK — CachedHttpClient jest używany jako instancja tworzona w __init__
każdego serwisu. To tworzy OSOBNE POŁĄCZENIA HTTP dla każdego serwisu.
Lepszym podejściem byłoby wstrzyknięcie współdzielonego klienta przez
Dependency Injection (di.py).

4.3 KONFIGURACJA RETRY

Wszystkie integracje używają podobnych parametrów retry:
  - attempts: 3
  - timeout: 10-15s
  - circuit_breaker: True
  - on: HTTPStatusError, TimeoutException, RequestError, ConnectionError

To jest DOBRA KONFIGURACJA dla API rządowych (KSeF, GUS, MF, NBP), które
są znane z okresowych niedostępności.

4.4 CO DZIAŁA DOBRZE

- Trójwarstwowy stos HTTP — kompletna ochrona
- Jednolite użycie CachedHttpClient
- Stamina z circuit breaker dla każdej integracji
- Graceful degradation zamiast propagate błędów
- Szczegółowe logowanie każdej nieudanej próby

4.5 KRYTYCZNE LUKI

LUKA 12 (WYSOKA): Brak współdzielonego klienta HTTP
  Każdy serwis tworzy własną instancję CachedHttpClient. Przy 10+ serwisach
  oznacza to 10+ osobnych pul połączeń HTTP.
  REKOMENDACJA: Przenieść CachedHttpClient do DI i wstrzykiwać jako singleton.

LUKA 13 (ŚREDNIA): Brak timeoutu per-integracja
  Wszystkie integracje mają ten sam timeout (10-15s). API MF (Biała Lista)
  jest zazwyczaj szybsze niż GUS BIR (SOAP).
  REKOMENDACJA: Różnicować timeouty: 5s dla Białej Listy, 15s dla GUS BIR,
  10s dla KSeF.

LUKA 14 (NISKA): Brak health checka dla integracji zewnętrznych
  System nie monitoruje zdrowia zewnętrznych API przed wysłaniem zapytania.
  REKOMENDACJA: Dodać periodical health check (co 60s) dla każdego API
  i cache'ować status dostępności.

5. AUDYT VENDOR INTELLIGENCE I IMPORTU BANKOWEGO

5.1 VENDOR INTELLIGENCE — LOKALNA ANALITYKA KONTRAHENTÓW

VendorAnalyst to fascynujący komponent analityczny, który DZIAŁA CAŁKOWICIE
LOKALNIE — nie wymaga zewnętrznych API. To realizacja filozofii "local-first"
NexusAI.

ARCHITEKTURA:
- DuckDB jako silnik analityczny (OLAP)
- NexusCache (L1 RAM + L2 SQLite) dla wyników vendor context
- Refresh co 3600s (1h)
- Trzy tabele: vendor_intelligence, vendor_price_alerts

METRYKI KONTRAHENTA:
  1. avg_payment_delay — średnie opóźnienie płatności w dniach
  2. price_volatility_index — indeks zmienności cen (w %)
  3. total_volume_ytd — całkowity wolumen od początku roku
  4. reliability_score — ocena wiarygodności (0-5)
  5. rating_stars — ocena gwiazdkowa (1-5)
  6. smart_alerts — inteligentne alerty (np. "Always pays late")

SYSTEM ALERTÓW CENOWYCH:
  - Wykrywa wzrosty cen >5% w porównaniu do średniej 6-miesięcznej
  - Śledzi każdą pozycję (item_name) per kontrahent
  - Automatycznie generuje alerty PRICE_ALERT

To jest IMPONUJĄCY system analityczny, który:
- Działa w 100% lokalnie — nie wysyła danych kontrahentów na zewnątrz
- Daje biznesową wartość od pierwszego dnia
- Skaluje się z ilością danych (DuckDB columnar storage)
- Jest odporny na niedostępność zewnętrznych API

5.2 IMPORT BANKOWY — WZORCOWA IMPLEMENTACJA

IdempotentBankImporter to KLASA MISTRZOWSKA w swojej dziedzinie:

KLUCZOWE CECHY:
- IDEMPOTENTNOŚĆ przez SHA-256 + UUID5
  - generate_idempotency_id() tworzy UUID v5 na podstawie SHA-256 danych
  - Batch deduplication przez DuckDB
  - Niemożliwość podwójnego zaksięgowania przelewu

- WALIDACJA CIĄGŁOŚCI SALDA
  - validate_balance_continuity() sprawdza czy saldo początkowe wyciągu
    zgadza się z saldem końcowym poprzedniego importu
  - Wykrywa luki w wyciągach bankowych

- INTEGRACJA Z TIGERBEETLE
  - Każdy przelew tworzy transfer w TigerBeetle (double-entry accounting)
  - user_data_128 przechowuje UUID idempotentności
  - user_data_64 przechowuje datę księgowania

- FSSPEC DLA ELASTYCZNOŚCI STORAGE'U
  - Wyciągi mogą być z pliku lokalnego, S3, HTTP
  - Meta mapper dla metadanych importów
  - Obsługa CSV przez PyArrow (typowanie kolumn, C++ performance)

- CSV STATEMENT PARSER przez PYARROW
  - pyarrow.csv.read_csv() z ConvertOptions — automatyczne typowanie
  - Operacje w C++ (10x szybciej niż csv.DictReader)
  - Null handling przez pc.is_valid() + pc.filter()

To jest ARCHITEKTURA REFERENCYJNA dla systemów importu finansowego. Każdy
element (idempotentność, ciągłość salda, double-entry accounting, fsspec
abstrakcja storage'u) jest zaimplementowany poprawnie i kompletnie.

5.3 CO DZIAŁA DOBRZE

- 100% lokalna analityka kontrahentów — prywatność i szybkość
- Pełna idempotentność importu bankowego przez SHA-256

- Integracja z TigerBeetle — spójność księgowa
- PyArrow dla wydajności — 10x szybciej niż pure Python
- fsspec dla elastyczności storage'u

  Obecnie refresh co 1h. Nagły wzrost ceny o 50% zostanie wykryty dopiero

6. ANALIZA FSSPEC — ABSTRAKCJA STORAGE'U
================================================================================

6.1 FSSPEC COMPATIBILITY LAYER

fsspec_compat.py to IMPONUJĄCA warstwa kompatybilności (zredukowana
z 767 → ~200 LOC przez metaprogramowanie).

KLUCZOWE CECHY:
- Auto-detekcja 11 modułów fsspec przez metaprogramowanie (_FS_MODULES dict)
- Fallback dla TransactionalFileSystem gdy natywny niedostępny
- AsyncFsWrapper — czyste async API dla każdego protokołu
- FSSpecFactory — singleton z async wrapper support
- Obsługa chainowania (simplecache::file, cached::s3)
- Konfiguracja globalna przez fsspec.config.conf

WSPIERANE SYSTEMY PLIKÓW:
- TransactionalFileSystem — atomowe operacje
- ZipFileSystem — archiwa ZIP jako system plików
- TarFileSystem — archiwa TAR
- HTTPFileSystem — HTTP(S) jako system plików
- CachingFileSystem — cache'owanie z lokalnym storage
- SimpleCacheFileSystem — prosty cache
- BlockCacheFileSystem — blokowy cache
- WholeFileCacheFileSystem — cache całych plików
- ReferenceFileSystem — referencje do danych
- MemoryFileSystem — storage w RAM
- TqdmCallback — paski postępu

Każdy moduł jest sprawdzany przez _try_import() i oznaczany w _HAS dict.
To umożliwia graceful degradation — system używa dostępnych modułów
bez twardych zależności.

6.2 ASYNC WRAPPER

AsyncFsWrapper opakowuje synchroniczne API fsspec w async przez
anyio.to_thread.run_sync(). To KLUCZOWE dla integracji z asynchronicznym
backendem Litestar — operacje I/O na plikach nie blokują event loopu.

6.3 FSSPEC FACTORY — SINGLETON

FSSpecFactory implementuje wzorzec singleton dla zarządzania systemem plików:
- Jedna instancja na całą aplikację
- Konfigurowalny protokół, cache, transakcyjność
- Automatyczne tworzenie AsyncFsWrapper i TransactionalFileSystem
- get_mapper() dla dict-like dostępu do storage'u

6.4 CO DZIAŁA DOBRZE

- Metaprogramowanie eliminujące 500+ LOC boilerplate'u
- Graceful degradation — brak twardych zależności
- Async wrapper — bezpieczne dla event loopu
- Wsparcie dla 11+ protokołów storage'u
- Chainowanie dla zaawansowanych strategii cache'owania

8. ANALIZA TEMPORALNA — SPÓJNOŚĆ CZASOWA INTEGRACJI
================================================================================

8.1 SYNCHRONIZACJA CZASU

Wszystkie integracje zewnętrzne operują na datach:
- NBP API: data kursu walut (YYYY-MM-DD)
- KSeF: data wystawienia faktury, data sprzedaży
- GUS BIR: data weryfikacji NIP
- Biała Lista MF: data sprawdzenia (target_date w zapytaniu)

System używa pendulum.now() dla wszystkich operacji czasowych — to DOBRA
PRAKTYKA (pendulum jest świadome stref czasowych i DST).

8.2 KRYTYCZNE ZAGADNIENIA CZASOWE

ZAGADNIENIE 1: Wyścig czasowy w cache'u kursów walut
  Cache NBP ma TTL 86400s (24h). Jeśli kurs zostanie pobrany o 23:59,
  będzie używany przez kolejne 24h — potencjalnie NIEAKTUALNY kurs
  dla transakcji z następnego dnia.
  REKOMENDACJA: Dodać "time window" — cache ważny tylko dla daty zapytania,
  nie dla timestampu pobrania.

ZAGADNIENIE 2: Import wyciągów bankowych — data vs timestamp
  IdempotentBankImporter używa daty księgowania (booking_date) do sortowania.
  W przypadku dwóch przelewów z tą samą datą, kolejność jest nieokreślona.
  REKOMENDACJA: Dodać secondary sort po amount i title dla determinizmu.

ZAGADNIENIE 3: KSeF — strefa czasowa API MF
  API KSeF operuje w czasie polskim (CET/CEST). System musi uwzględniać
  zmianę czasu (DST) przy wysyłce faktur tuż przed północą.
  REKOMENDACJA: Jawne określenie timezone w nagłówkach KSeF.

  - Automatycznego alertu przy anomalii kursowej (>2 sigma)
  To DAJE przedsiębiorcy przewagę w planowaniu płatności walutowych.

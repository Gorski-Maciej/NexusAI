1.1 AgentOrchestrator — Centralny Mózg (CFO)
─────────────────────────────────────────────

AgentOrchestrator to NAJWIĘKSZY i NAJBARDZIEJ ZŁOŻONY komponent w całym
systemie NexusAI (~1000+ LOC). Jest to Wirtualny Dyrektor Finansowy,
który koordynuje pracę pozostałych 4 agentów.

ARCHITEKTURA WEWNĘTRZNA (GENIALNE POMYSŁY):
AgentOrchestrator integruje WSZYSTKIE innowacje NexusAI w jednej klasie:

v5.0 — ProactiveWorkflowScheduler (autonomiczne zadania)
v5.1 — ActionCardGenerator ("1-Click CFO")

v5.3 — KnowledgeMesh (Collective Bayesian Field + Cross-Agent Replay)
v5.4 — DecisionTracer + MultiModelEnsemble + ConfidenceCalibrator + FeedbackLoop
v6.0 — Silent Partner (StrategyEngine + ExecutiveSummary)
v7.0 — ShadowSimulator (DuckDB Shadow Ledger)

PROCES DECYZYJNY (process_invoice):
Pipeline 12-etapowy:
  1. DecisionTrace — OTel tracing start
  2. Decision Cache — k-NN przez sqlite-vec (pominięcie jeśli HIT)
  3. KnowledgeMesh Predictive Routing — optymalna ścieżka agentów
  4. AgentDataExtraction — ekstrakcja danych OCR + KSeF
  5. Adaptive Thresholds — Bayesian per-vendor
  6. MultiModelEnsemble — >=3 modele z diversity check
  7. QualityValidator — 4-Eyes + tax + fraud
  8. Weighted Voting — Orchestrator 0.40, QualityValidator 0.60
  9. ConfidenceCalibrator — Platt Scaling
  10. Decision Final — AUTO_POST / REVIEW / BLOCK
  11. Decision Cache — zapisz embedding
  12. ExecutiveSummary — dodaj do dashboardu

MODEL DECYZYJNY:
  Actor:    Granite 3.2 3B — Główny Decydent (podejmuje decyzję)
  Guardian: Granite Guardian 0.5B — Strażnik Merytoryczny (weryfikuje)
  Communicator: Qwen3-Nano 0.5B — Komunikator (kontakt z użytkownikiem)

TRYBY DECYZYJNE (JEDEN poziom automatyzacji):
  AUTO_POST (>=0.92): Agent księguje samodzielnie
  SUGGEST  (>=0.75): Agent proponuje, użytkownik zatwierdza
  ASK_USER (<0.75):  Agent pyta użytkownika

SILENT PARTNER v6.0:
  Gdy włączony, DOMYŚLNIE wszystkie workflow → AUTO_POST.

1.2 AgentDataExtraction — Forteca Precyzji (OCR + KSeF)
───────────────────────────────────────────────────────

AgentDataExtraction to wyspecjalizowany agent odpowiedzialny za:

- Generowanie XML KSeF (FA_VAT)
- Wysyłkę i odbiór faktur z KSeF API
- Walidację krzyżową 4x4 (każde pole z 4 silników)

STRUKTURY DANYCH (modele msgspec):
- DataExtractionRequest — żądanie ekstrakcji
- DataExtractionResult — wynik z polami:
  - extracted_data: wyekstrahowane dane (numer, NIP, kwoty)
  - cross_validation: wyniki walidacji krzyżowej 4x4
  - field_confidences: confidence per pole
  - template_match: dopasowanie do wzorca faktury
  - engine_results: wyniki per silnik OCR
  - validation_issues: problemy walidacji

WALIDACJA KRZYŻOWA 4x4 (CrossValidationResult):
Każde pole (NIP, kwota, data) jest odczytywane przez 4 silniki:
  Tesseract → PaddleOCR → DocTR → EasyOCR
Konsensus:
  - 3/4 zgodnych → wartość przyjęta, confidence 0.75
  - 2/4 zgodnych → Granite 3.2 Vision rozstrzyga, confidence 0.50

OCENA: 8.5/10 — Solidna implementacja. Walidacja krzyżowa 4x4 to
podejście klasy Enterprise. Brakuje integracji z KSeF Inbox (odbieranie
faktur przychodzących) i batch send (do 100 faktur jednocześnie).

2.1 KnowledgeMesh — Samoucząca się Siatka Wiedzy Agentów
─────────────────────────────────────────────────────────

KnowledgeMesh to TRÓJWARSTWOWY system wymiany wiedzy między agentami:

WARSTWA 1: Cross-Agent Experience Replay
  Agent A uczy Agenta B na podstawie własnych doświadczeń.
  5 predefiniowanych typów zdarzeń:
    quality.tax_error → extraction: SET_SCRUTINY_HIGH
    quality.fraud_detected → orchestrator: FORCE_4EYES
    extraction.low_consensus → quality: INCREASE_SCRUTINY
    orchestrator.decision_corrected → extraction: LEARN_CORRECTION
    analytics.anomaly_detected → quality: TRIGGER_DEEP_CHECK

  Każda reguła ma priorytet (1-10) i jest przechowywana w DuckDB
  z embeddingiem 768d dla wyszukiwania k-NN przez sqlite-vec.

WARSTWA 2: Collective Bayesian Field
  Współdzielone pole Bayesiańskie — JEDNA prawda dla wszystkich agentów.
  Dla każdego NIP+kategoria+zakres kwot przechowuje:
    alpha — liczba poprawnych decyzji
    beta — liczba błędnych decyzji
    Trust Score = alpha / (alpha + beta)
    Confidence = 1 - skalowana wariancja

  Agenty NIE uczą się osobno — aktualizują WSPÓLNE pole.

WARSTWA 3: Predictive Task Router
  Dynamiczny router zadań — optymalizuje ścieżkę agentów:
    Trust >= 0.92 → POMIŃ Quality + Analytics (50ms zamiast 15s)
    Trust 0.75-0.92 → normalna ścieżka
    Trust < 0.75 → ROZSZERZONA (dodaj Analytics + 4-Eyes)
    Trust < 0.30 → CIRCUIT BREAKER → zawsze ASK_USER

KnowledgeMesh używa JEDNEJ bazy DuckDB (mesh.db) zamiast 3 osobnych,
co jest wynikiem TOP-3 optymalizacji. To PROFESJONALNE — jedna baza
zamiast trzech oszczędza pamięć i upraszcza zarządzanie.

OCENA: 9.5/10 — To jest ARCHITEKTURA REFERENCYJNA dla systemów
wieloagentowych. Trzy warstwy są niezależne, ale zintegrowane.
Cross-Agent Experience Replay to koncept, który wyprzedza większość
komercyjnych systemów AI. Predictive Task Router z circuit breakerem
to mistrzowska implementacja resilience na poziomie agentów.

2.2 DecisionTrace — Pełny OTel Tracing Każdej Decyzji
──────────────────────────────────────────────────────

DecisionTracer implementuje OTel-compatible tracing dla KAŻDEJ decyzji:

- DecisionTrace: pełny trace z trace_id (32 hex chars)
- DecisionSpan: pojedynczy krok agenta (extraction, quality_check, ensemble)
- Każdy span ma: started_at, ended_at, duration_ms, status (OK/ERROR)
- Trace kończy się final_status, final_trust_score, quality_score

QUALITY SCORE (0-100%):
  - Wszystkie spany OK = 40%
  - Brak błędów w spanach = 30%
  - Szybkość (< 5s total = 20%, < 15s = 10%)
  - Minimum 2 spany (wieloagentowe) = 10%

Każdy trace jest zapisywany w AgentTelemetryStore (DuckDB + Parquet)
dla pełnej odtwarzalności decyzji.

OCENA: 9.0/10 — Pełny tracing każdej decyzji to ZŁOTY STANDARD
dla systemów finansowych. Możliwość odtworzenia DLACZEGO agent podjął
daną decyzję jest kluczowa dla audytu i zgodności regulacyjnej.

2.3 MultiModelEnsemble — Zespół >=3 Modeli z Diversity Check
─────────────────────────────────────────────────────────────

Zamiast pojedynczego modelu, Orkiestrator używa ZESPOŁU modeli:

Modele w zespole:
  1. Granite 3.2 3B — Główny Decydent (Actor)
  2. Granite Guardian 0.5B — Strażnik Merytoryczny
  3. DynamicErrorHandbook — Few-Shot z przeszłych korekt
  4. Qwen3-Nano 0.5B — Komunikator (opcjonalnie jako 4. głos)

ALGORYTM ROZSTRZYGANIA:
  1. Każdy model głosuje: AUTO_POST / REVIEW / BLOCK
  2. Wagi są adaptacyjne (Bayesian update po każdej decyzji)
  3. Weighted voting z wagami per-model
  4. Diversity check: jeśli wszystkie modele IDENTYCZNE → flaga
     (prawdopodobny overfitting lub błąd w prompcie)
  5. Consensus >= 66% ważonej większości
  6. Final trust = średnia ważona x consensus_factor x diversity_factor

DIVERSITY CHECK — GENIALNY POMYSŁ:
  Jeśli wszystkie 3 modele dają IDENTYCZNĄ odpowiedź, diversity_score
  spada do 0.0, a final_trust jest MNOŻONE przez 0.7. To zapobiega
  sytuacji, gdy jeden błąd w prompcie propaguje się na wszystkie modele.

OCENA: 9.3/10 — Multi-model ensemble z diversity check to KONCEPT
WYPRZEDZAJĄCY PROFESJONALISTÓW. Nikt w komercyjnych systemach księgowych
nie używa zespołu modeli z diversity check. To daje NexusAI przewagę
w accuracy i odporności na błędy pojedynczego modelu.

2.4 ConfidenceCalibrator — Platt Scaling dla Trust Score
─────────────────────────────────────────────────────────

Problem: modele AI często są źle skalibrowane — mówią "95% pewności"
ale w rzeczywistości accuracy = 70%.

Rozwiązanie: Platt Scaling (regresja logistyczna):
  calibrated = 1 / (1 + e^(-a * raw - b))

Parametry a, b są aktualizowane ONLINE przez Stochastic Gradient Descent
po każdej decyzji. Learning rate maleje z 0.01 do 0.001 w miarę
zbierania próbek (decay = 0.01 / sqrt(samples)).

OCENA: 8.5/10 — Online Platt Scaling to eleganckie rozwiązanie problemu
kalibracji. Wymaga jednak minimum ~100 próbek by być skuteczny.

2.5 FeedbackLoop — Metryki Interakcji Człowiek-AI
──────────────────────────────────────────────────

FeedbackLoop mierzy JAKOŚĆ interakcji człowiek-AI:
  - Correction rate: % decyzji poprawionych przez użytkownika
  - Avg response time: średni czas odpowiedzi użytkownika
  - Avg feedback latency: czas od decyzji AI do feedbacku
  - Avg quality score: średni Decision Quality Score

Cel: correction_rate < 5% (95% decyzji agenta jest akceptowanych)

OCENA: 8.0/10 — Kluczowe metryki dla ciągłego doskonalenia systemu.

2.6 DynamicErrorHandbook — Few-Shot Learning z Przeszłych Korekt
─────────────────────────────────────────────────────────────────

DynamicErrorHandbook to SYSTEM SAMOUCZĄCY SIĘ:

Każda korekta użytkownika jest zapisywana jako przykład few-shot:
  - AI decision: co agent zdecydował
  - User correction: co użytkownik poprawił
  - Context: NIP, kategoria, kwota, typ dokumentu

Przy następnej podobnej fakturze, Handbook wstrzykuje przykłady
few-shot do promptu modelu:
  "UWAGA: W przeszłości dla podobnych faktur (NIP X, kategoria Y)
   popełniłeś następujące błędy: [przykład 1, przykład 2, przykład 3].
   NIE popełniaj ich ponownie."

To jest REALNY few-shot learning — model uczy się na własnych błędach
bez fine-tuningu.

OCENA: 9.0/10 — Few-shot learning z DynamicErrorHandbook to jedna
z NAJLEPSZYCH innowacji w NexusAI. Rozwiązuje problem "model popełnia
ten sam błąd wielokrotnie" bez kosztownego fine-tuningu.

2.7 UserDecisionProfile — Progressive Autonomy Engine
──────────────────────────────────────────────────────

Progressive Autonomy Engine obserwuje wzorce decyzyjne użytkownika:

Decision Autonomy Score = AUTO_POST / (AUTO_POST + ASK_USER) x 100%

Gdy użytkownik wielokrotnie akceptuje decyzje agenta dla danego
kontrahenta, próg AUTO_POST jest automatycznie obniżany (łatwiej
o automatyczne księgowanie). Gdy użytkownik często koryguje —
próg jest podnoszony.

WeeklyAutonomyReport: "Przejąłem 73% decyzji, zaoszczędziłem 45 kliknięć"

OCENA: 8.5/10 — Elegancki mechanizm stopniowego zwiększania autonomii.
Użytkownik zachowuje kontrolę, a system uczy się kiedy może działać
samodzielnie.

  RÓŻNE błędy, więc ensemble jest bardziej odporne.

PROBLEM: 13 modeli x 0.8-3.0 GB = 10-39 GB RAM przy pełnym załadowaniu.
ResourceOptimizer z TTL auto-unload (5 min) jest KLUCZOWY.

3.2 InferenceService — Silnik Inferencji GGUF
───────────────────────────────────────────────

InferenceService to generyczny silnik inferencji GGUF:

KLUCZOWE CECHY:
- llama-cpp-python jako jedyna zależność AI/ML
- Lazy loading — model ładowany dopiero przy generate()/chat()
- TTL auto-unload — model zwalniany po 5 minutach bezczynności
- Obsługa CPU (n_threads) i GPU (n_gpu_layers)
- generate() i chat() API (zgodne z OpenAI API)
- check_ttl() sprawdza czy minął czas — jeśli tak, zwalnia pamięć

OSZCZĘDNOŚĆ PAMIĘCI:
  TTL = 300s (5 minut). Po 5 minutach bezczynności model jest
  odładowywany, zwalniając 0.8-3.0 GB RAM. Przy 13 modelach,
  oszczędność może wynosić nawet 25-35 GB RAM vs pełne załadowanie.

  Kolejne wywołanie → model jest ponownie ładowany (lazy loading),
  co zajmuje 1-3 sekundy.

OCENA: 8.5/10 — Prosty, elegancki i skuteczny. TTL auto-unload to
rozwiązanie problemu ograniczonej pamięci RAM przy wielu modelach.
Brak zaawansowanych funkcji (continuous batching, speculative decoding),
ale są one niepotrzebne dla 1-5 równoczesnych użytkowników.

3.3 ModelManager — Zarządzanie Pamięcią
─────────────────────────────────────────

ModelManager zarządza wieloma instancjami InferenceService:

- get_or_create() — pobiera istniejący model lub tworzy nowy
- cleanup_expired() — zwalnia modele z wygasłym TTL
- unload_all() — zwalnia wszystkie modele (po batchu OCR)
- loaded_models — lista załadowanych modeli

INTEGRACJA Z DI:
  ModelManager jest wstrzykiwany przez Litestar DI zamiast globalnego
  singletona (chociaż get_model_manager() nadal istnieje dla kompatybilności).

OCENA: 8.0/10 — Poprawna implementacja. Przejście z singletona na DI
to dobry kierunek, ale nie jest jeszcze w pełni zrealizowane.

3.4 IPC Vision — Granite 3.2 Vision
─────────────────────────────────────

ImageMemoryManager używa Python shared_memory do bezstratnego
przesyłania obrazów między procesami:

- store_image(bytes, width, height) → metadane (nazwa shm)
- retrieve_image(metadata) → (bytes, dimensions)

Granite 3.2 Vision 2B jest używany jako "rozjemca" w konsensusie OCR:
gdy 2/4 silników daje różne wyniki, Vision model analizuje obraz
i rozstrzyga, która wartość jest poprawna.

OCENA: 8.0/10 — Python shared_memory to dobre rozwiązanie dla IPC
obrazów. Zero kopii, zero serializacji. Vision model jako rozjemca
to innowacyjne zastosowanie modelu wizyjnego.

3.5 ProtocolExecutor — Deterministyczne SOP
─────────────────────────────────────────────

ProtocolExecutor to WARSTWA WYKONAWCZA Standard Operating Procedures:

- Ładuje protocols.toml (scentralizowane definicje protokołów)
- Buduje systemowe prompty z protokołów
- Waliduje decyzje modelu względem matryc decyzyjnych
- Obsługuje protokoły awaryjne (np. model_timeout → ASK_USER)
- Hot-reload: zmiana protocols.toml na dysku → automatyczne przeładowanie

MATRYCA DECYZYJNA (validation_verdict):
  Kombinacje głosów Alpha/Beta/Gamma:
    APPROVE + APPROVE + APPROVE → LEVEL_1_AUTO_POST
    APPROVE + APPROVE + REJECT  → LEVEL_2_SUGGEST
    APPROVE + REJECT  + REJECT  → LEVEL_3_ESCALATE
    REJECT  + REJECT  + REJECT  → LEVEL_4_BLOCK
    ERROR   + *       + *       → LEVEL_4_BLOCK

ADAPTACYJNE PROGI:
  ProtocolLoader.get_thresholds_with_adaptations() dostosowuje progi
  na podstawie:
    - Kategoria wydatku (recurring → niższy próg, problematic → wyższy)
    - Znajomość kontrahenta (znany/nowy → znany niższy próg)
    - Kwota (mała → niższy próg, duża → wyższy)

OCENA: 9.0/10 — Scentralizowane SOP z hot-reloadem to ARCHITEKTURA
KLASY ENTERPRISE. Deterministyczne protokoły gwarantują, że nawet
gdy model AI zawiedzie, system nadal działa według zdefiniowanych
procedur. To kluczowe dla zgodności regulacyjnej.

5.1 Izolacja Agentów
─────────────────────

Każdy agent działa jako OSOBNY byt z własnym modelem i stanem.
Komunikacja przez NATS JetStream (message-based, nie shared memory).
To zapewnia izolację — awaria jednego agenta nie wpływa na pozostałe.

5.2 Circuit Breaker na Poziomie Agenta
────────────────────────────────────────

KnowledgeMesh implementuje Circuit Breaker dla NIP-ów z niskim trust:
  Trust < 0.30 → Circuit Breaker OPEN → zawsze ASK_USER
  Automatyczne otwieranie przy fraud_detected
  Zamknięcie po ręcznej weryfikacji

5.3 Proof Chain SHA-256
─────────────────────────

Każda decyzja tworzy ProofBlock z SHA-256 hashem poprzedniego bloku.
Modyfikacja dowolnego bloku → wszystkie kolejne unieważnione.
Zgodne z nexus-crypto (Rust+PyO3).

5.4 Cognitive Audit Trail
──────────────────────────

Rozszerzenie Proof Chain o CognitiveProofBlock:
- correction_embedding (768d) — embedding korekty dla k-NN
- correction_count — ile razy ta sama korekta
- opa_rule_ref — referencja do reguły OPA
- auto_patched — czy reguła została automatycznie poprawiona

To UMOŻLIWIA auto-naprawę reguł: jeśli ta sama korekta pojawia się
10+ razy, reguła OPA jest automatycznie aktualizowana.

OCENA BEZPIECZEŃSTWA: 9.0/10 — Izolacja agentów, circuit breaker,
proof chain i cognitive audit trail tworzą WIELOWARSTWOWY system
bezpieczeństwa na poziomie agentów.

6. ANALIZA TEMPORALNA I SPÓJNOŚĆ DECYZJI
================================================================================

6.1 Deterministyczność vs Niedeterministyczność
────────────────────────────────────────────────

SYSTEM JEST ZAPROJEKTOWANY JAKO HYBRYDA:
- Deterministyczne: ProtocolExecutor, matryce decyzyjne, thresholdy
- Niedeterministyczne: Inferencja LLM (temperatura wpływa na output)

Dla temperature=0.0 (Guardian, QualityValidator) output powinien być
deterministyczny. Dla temperature=0.1 (Actor) może być niewielka
zmienność.

6.2 Decision Cache
───────────────────

Decision cache (k-NN przez sqlite-vec) zapewnia, że IDENTYCZNE
faktury dostają IDENTYCZNĄ decyzję — nawet jeśli model dałby
inny wynik. To kluczowe dla spójności.

6.3 Idempotentność
──────────────────

process_invoice() NIE jest w pełni idempotentny na poziomie API.
Wielokrotne wywołanie dla tej samej faktury może dać różne decyzje
jeśli cache nie trafi (k-NN threshold 0.1 może nie złapać).

REKOMENDACJA: Dodać idempotentność na podstawie invoice_id + hash
danych faktury.

7.1 Scenariusz: 100 faktur jednocześnie
─────────────────────────────────────────

Przy 100 fakturach:

- Każda tworzy trace z 5-8 spanami

- DuckDB mesh.db: concurrent writes z wielu agentów
- Pamięć RAM: 100 requestów x 0.8 GB/model = katastrofa

ROZWIĄZANIA (częściowo zaimplementowane):
- TTL auto-unload → modele są już załadowane między requestami
- ResourceOptimizer → ogranicza liczbę workerów
- Decision cache → k-NN pomija inferencję dla podobnych faktur

7.2 Scenariusz: Awaria modelu Granite 3.2
───────────────────────────────────────────

Gdy Granite 3.2 jest niedostępny:
- _rule_based_evaluate() jako fallback
- MultiModelEnsemble działa z pozostałymi 2 modelami
- KnowledgeMesh może obniżyć próg do ASK_USER

OCENA STRESS: 7.5/10 — System ma mechanizmy obronne, ale nie były
testowane pod pełnym obciążeniem. Brakuje testów chaos engineering.

8. GENIALNE POMYSŁY — 15 INNOWACYJNYCH USPRAWNIEŃ
================================================================================

INNOWACJA 1: "Agent Swarm Optimization" — Dynamiczny Dobór Agentów
  Zamiast sztywno 5 agentów, system dynamicznie dobiera liczbę i typ
  agentów w zależności od złożoności faktury:
  - Prosta faktura (1 pozycja, znany kontrahent) → 1 agent (Orchestrator)
  - Średnia (3-5 pozycji) → 3 agenty
  - Złożona (>10 pozycji, nowy kontrahent) → wszystkie 5 agentów + 4-Eyes
  Redukcja zużycia RAM o 60% dla 80% faktur.

INNOWACJA 2: "Cross-Model Knowledge Distillation"
  Granite 3.2 3B (nauczyciel) destyluje wiedzę do Qwen3-Nano 0.5B (uczeń).
  Uczeń uczy się na decyzjach nauczyciela + korektach użytkownika.
  Po 1000 decyzjach, uczeń osiąga 90% accuracy nauczyciela przy 5x
  mniejszym zużyciu RAM.

INNOWACJA 3: "Predictive Model Preload"
  KnowledgeMesh analizuje wzorce użycia i PREŁADUJE modele zanim są
  potrzebne:
  - Poniedziałek 8:00 → załaduj Granite 3.2 (najwięcej faktur)
  - Piątek 15:00 → załaduj modele analityczne (raport tygodniowy)
  - Koniec miesiąca → załaduj wszystkie (zamknięcie miesiąca)
  Redukcja latency pierwszego requestu z 2-3s do ~50ms.

INNOWACJA 4: "Agent Reputation System"
  Każdy agent ma reputation score na podstawie historycznej accuracy.
  Agenty z niską reputacją są pomijane lub ich głos ma mniejszą wagę.
  Nowe modele startują z neutralną reputacją i budują ją przez decyzje.
  To tworzy RYNEK wewnętrzny — słabe modele są naturalnie eliminowane.

INNOWACJA 5: "Federated Learning of Corrections"
  Opcjonalna, anonimizowana wymiana embeddingów korekt między
  instancjami NexusAI (za zgodą użytkownika):
  - Tylko embeddingi, nigdy dane finansowe
  - Differential privacy (epsilon=1.0)
  - Wszystkie instancje korzystają z kolektywnej wiedzy o błędach
  To DAJE przewagę sieciową — im więcej użytkowników, tym mniej
  błędów dla wszystkich.

INNOWACJA 6: "Cognitive Chain-of-Thought Debugger"
  Gdy agent podejmie BŁĘDNĄ decyzję (korekta użytkownika),
  system automatycznie:
  1. Odtwarza trace (DecisionTrace)
  2. Analizuje który span zawiódł
  3. Generuje "post-mortem" — dlaczego decyzja była błędna
  4. Sugeruje poprawkę (prompt, threshold, reguła)
  To REDUKUJE czas debugowania z godzin do sekund.

INNOWACJA 7: "Multi-Tenant Agent Isolation"
  Każdy tenant (biuro rachunkowe) ma OSOBNY KnowledgeMesh,
  DecisionProfile i ErrorHandbook.
  Ale Collective Bayesian Field może być opcjonalnie współdzielony
  między tenantami dla rzadkich przypadków (np. nowy kontrahent
  w bazie — użyj danych od innych tenantów).

INNOWACJA 8: "Agentic RAG with Tool Use"
  Agenty mogą używać NARZĘDZI:
  - search_invoices(nip) — przeszukaj DuckDB
  - fetch_gus(nip) — pobierz dane z GUS BIR
  - check_whitelist(nip) — sprawdź Białą Listę MF
  - calculate_vat(amount, rate) — oblicz VAT
  Zamiast polegać tylko na danych z promptu, agent AKTYWNIE
  pobiera dodatkowe informacje. To Radykalnie zwiększa accuracy.

INNOWACJA 9: "Automated A/B Testing of Prompts"
  System automatycznie testuje różne wersje promptów na 5% ruchu:
  - Prompt A (control): obecny prompt
  - Prompt B (test): zmodyfikowany prompt
  Po 100 decyzjach → porównaj correction_rate.
  Lepszy prompt → automatycznie wdrożony na 100% ruchu.
  To ELIMINUJE ręczne dostrajanie promptów.

INNOWACJA 10: "Agent Emotion Detection"
  AgentAnalytics monitoruje TON komunikacji z użytkownikiem:
  - Jeśli użytkownik często poprawia decyzje → frustracja
  - Jeśli użytkownik szybko akceptuje → zaufanie
  - Jeśli użytkownik ignoruje → brak zaangażowania
  System dostosowuje poziom autonomii: sfrustrowany użytkownik
  dostaje WIĘCEJ auto-postów (mniej klikania), użytkownik z niskim
  zaufaniem dostaje WIĘCEJ sugestii.

INNOWACJA 11: "Shadow Mode: Compare Agents"
  Uruchom DWA zestawy agentów równolegle:
  - Production: obecny zestaw (podejmuje rzeczywiste decyzje)
  - Shadow: nowy model/konfiguracja (tylko porównuje wyniki)
  Jeśli Shadow jest lepszy przez 30 dni → automatyczna migracja.
  Zero-ryzyko testowania nowych modeli w produkcji.

INNOWACJA 12: "Cost-Aware Agent Selection"
  Każdy model ma koszt (RAM x czas):
  - Granite 3.2 3B: 2.1 GB RAM x 2s = "drogi"
  - Qwen3-Nano 0.5B: 0.5 GB RAM x 0.3s = "tani"
  Dla prostych faktur system wybiera tańszy model.
  Oszczędność: 40% RAM i 60% czasu dla 80% faktur.

INNOWACJA 13: "Decision Explainability Engine"
  Gdy użytkownik widzi decyzję, może kliknąć "DLACZEGO?":
  - Agent pokazuje PEŁEN ślad decyzyjny
  - Które modele głosowały, z jaką pewnością
  - Które reguły OPA zostały zastosowane
  - Jakie przykłady few-shot wpłynęły na decyzję
  - Link do odpowiednich przepisów (Dz.U.)
  To BUDUJE zaufanie i umożliwia audyt.

INNOWACJA 14: "Adaptive Prompt Compression"
  Dla faktur od znanych kontrahentów, prompt jest KOMPRESOWANY:
  - Pełny prompt: 2500 tokenów (nowy kontrahent, złożona faktura)
  - Skompresowany: 500 tokenów (znany kontrahent, prosta faktura)
  - Kompresja przez usuwanie przykładów few-shot które nie pasują
    do kontekstu (k-NN similarity < 0.3)
  Redukcja kosztu inferencji o 60% i czasu o 50%.

INNOWACJA 15: "Continuous Fine-Tuning Pipeline"
  Co 1000 decyzji, system automatycznie:
  1. Zbiera wszystkie korekty jako dane treningowe
  2. Tworzy LoRA (Low-Rank Adaptation) na bazie modelu bazowego
  3. Trenuje LoRA przez 10 epok na korektach
  4. Testuje LoRA vs model bazowy na 10% danych
  5. Jeśli LoRA lepsza → automatyczne wdrożenie
  Model STALE się doskonali na podstawie rzeczywistych korekt.

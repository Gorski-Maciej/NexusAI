1.3. MECHANIZM RETRY + CIRCUIT BREAKER (STAMINA)
--------------------------------------------------------------------

STATUS: BARDZO DOBRY - Async-native resilience

Konfiguracja stamina w ksef_service.py:

  for attempt in stamina.retry_context(
      on=(HTTPStatusError, RequestError, TimeoutException, ConnectionError),
      attempts=3,
      timeout=10.0,
      circuit_breaker=True,
  ):

Charakterystyka:
- 3 proby wysylki z timeoutem 10s kazda
- Circuit breaker: po serii bledow -> open circuit (domyslnie 60s cooldown)
- Async-native (anyio) - nie blokuje event loop
- Obsluguje bledy: HTTP 4xx/5xx, timeout, connection error
- Logowanie kazdej proby przez structlog

Konfiguracja globalna (dev.toml / prod.toml):
  [stamina]
  circuit_breaker_enabled = true
  circuit_breaker_cooldown = 60.0

Konfiguracja w core/config.py:
  stamina_retry_attempts = 3
  stamina_retry_timeout = 10.0
  stamina_circuit_breaker_enabled = True
  stamina_circuit_breaker_cooldown = 60.0

OCENA RETRY I CB: 90/100

Zalety:
+ Async-native - optymalne wykorzystanie zasobow
+ Circuit breaker chroni przed kaskadowymi bledami
+ Rozroznienie typow bledow (4xx vs 5xx vs timeout)
+ Globalna konfiguracja z mozliwoscia per-usluga override

Ograniczenia:
- Stale 3 proby - brak adaptacyjnego zwiekszania przy krytycznych awariach
- Timeout 10s moze byc za dlugi przy batch 100 faktur
- Brak rozroznienia miedzy timeoutem polaczenia a timeoutem odpowiedzi
- Circuit breaker nie rozroznia endpointow KSeF (Session vs Invoice vs Status)

2.2. KSeF OFFLINE PRZEZ 72h - CZY SYSTEM SOBIE RADZI?
--------------------------------------------------------------------

ANALIZA: TAK, system radzi sobie z 72-godzinna awaria KSeF.

Procedura offline:

1. Wykrycie awarii:
   - KSR-1600 (api_health_check) wykrywa KSeF DOWN
   - Routing: TRIAGE_QUEUE zamiast BLOCK_AND_ALERT
   - System przechodzi w tryb OFFLINE

2. Wystawianie faktur:
   - Faktury wystawiane normalnie (PDF + XML lokalnie)
   - XML przechowywany w strukturze FA(2)
   - ksef_status = PENDING_OFFLINE
   - Timestamp proby wysylki zachowany

3. Monitorowanie:
   - KSR-1610 sledzi liczbe faktur oczekujacych (offline_queue_count)
   - Deadline: 168 godzin (7 dni) od ustania awarii
   - System przypomina o terminie

4. Po przywroceniu KSeF:
   - KSR-1645 (batch_recovery) automatycznie wykrywa powrot KSeF
   - Wysyla faktury chronologicznie (od najstarszej)
   - Strategia batch: single/batch_3/batch_10 w zaleznosci od liczby faktur
   - Monitorowanie UPO dla kazdej faktury

5. Eskalacja >7 dni:
   - KSR-1648: wymaga zlozenia ZAW-NR do Naczelnika US
   - Procedura: e-PUAP lub e-Urzad Skarbowy
   - Dolaczenie listy faktur wystawionych poza KSeF
   - Termin: 7 dni od dnia nastepujacego po ostatnim dniu awarii

2.3. INNOWACYJNY MECHANIZM OFFLINE QUEUE Z AUTO-RETRY
--------------------------------------------------------------------

PROPOZYCJA: "KSeF Sentinel Queue" - inteligentna kolejka offline z
auto-recovery oparta na NATS JetStream + DuckDB checkpoint

Architektura:

  [Faktura] -> [KSeF Service] -> [FAIL?] -> [NATS JetStream Queue]
                                                  |
  [KSeF wznowiony?] <--- [Health Check Worker] <--+
        |
  [Batch Sender] -> [KSeF API] -> [UPO] -> [DuckDB Audit Trail]

Kluczowe cechy innowacyjne:

1. Durable Queue (NATS JetStream):
   - Kazda faktura offline zapisywana jako wiadomosc w JetStream
   - At-least-once delivery guarantee
   - Konfigurowalna retencja (domyslnie 30 dni)
   - Stream: KSEF_OFFLINE z subjectem ksef.offline.{invoice_id}

2. Checkpoint Engine (DuckDB):
   - Tabela ksef_send_checkpoints z kolumnami:
     invoice_id, last_attempt, retry_count, status, upo_received
   - Przy restarcie system nie wysyla ponownie faktur juz wyslanych
   - Przyrostowe wysylanie batch (incremental send)

3. Health Check Worker (ciagly):
   - Co 60s sprawdza GET /api/online/Status (endpoint KSeF)
   - Po wykryciu KSeF UP -> trigger batch recovery
   - Exponential backoff dla health checkow: 60s, 120s, 240s...

4. Adaptive Batch Sender:
   - Dynamiczny rozmiar batch na podstawie:
     * Liczby faktur w kolejce
     * Szybkosci odpowiedzi KSeF (response time tracking)
     * Liczby bledow w ostatnim oknie (error rate)
   - Limit KSeF: max 100 faktur/batch, ale realnie ~10-20
   - Rownolegle wysylanie batchy (asyncio.gather)

5. Predictive Recovery:
   - ML model predykcji czasu odpowiedzi KSeF
   - Na podstawie historycznych danych: dzien tygodnia, godzina, miesiac
   - Automatyczne planowanie wysylek na okna niskiego obciazenia

6. INTEGRACJA TIGERBEETLE + SHADOW LEDGER
================================================================================

6.1. TIGERBEETLE - KSIEGA GLOWNA
--------------------------------------------------------------------

Integracja KSeF -> TigerBeetle:
- Faktura sprzedazy -> atomic double-entry transfer
- Transfer: [naleznosc od klienta] DEBIT, [przychod] CREDIT
- Kazda faktura KSeF mapowana na TigerBeetle Transfer z
  user_data zawierajacym ksef_id i UPO
- Immutability: faktury nie moga byc modyfikowane - tylko korekty
  jako nowe transfery

6.2. SHADOW LEDGER (DuckDB)
--------------------------------------------------------------------

Koncepcja Shadow Ledger dla KSeF:
- DuckDB tworzy tymczasowa kopie ksiag
- Symulacja wplywu batch recovery na bilans VAT
- Symulacja "co by bylo gdyby" dla roznych scenariuszy:
  * Opoznienie w wysylce faktur (72h offline)
  * Rozne daty uznania przychodu
  * Wplyw korekt na VAT nalezny/naliczony
- Zero wplywu na produkcyjna ksiege glowna TigerBeetle

- KSeF limit: ~300 requestow/min (oficjalny, niepotwierdzony)

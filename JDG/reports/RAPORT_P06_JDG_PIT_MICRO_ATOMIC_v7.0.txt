1. EXECUTIVE SUMMARY — TOP 12 WNIOSKOW
=================================================================

Mikro-warstwa PIT w NexusAI JDG v7.0 sklada sie z trzech plikow Rego
lacznie ~987 KB, zawierajacych ~1163 reguly atomowe dedykowane
dekompozycji ustawy o PIT na poziomie pojedynczych artykulow i ustepow.

TOP 12 KRYTYCZNYCH WNIOSKOW Z ANALIZY:

1. SKALA MIKRO-WARSTWY: pit.rego (750 KB, 22 738 linii) jest drugim
   najwiekszym plikiem w JDG. Zawiera 812 reguly rule_id (46 blokow
   decide + 766 blokow else), pakiet jdg.micro.pit, priorytety 60006+.
   Plan33_pit.rego (60 KB, 86 regul) i plan34_pit.rego (177 KB, 265
   regul) sa plikami rozszerzajacymi z alternatywna numeracja.

2. POKRYCIE ARTYKULOW: pit.rego pokrywa 44 prefixy artykulow PIT
   (a6 przez a45a), w tym kluczowe: a10 (24 reguly), a14 (40 regul),
   a22/a22a-p (30+ regul amortyzacji), a23 (60 regul NKUP), a26
   (50 regul ulg), a27 (30 regul skali), a30c/a30ca (24+24 regul
   liniowy/IP Box), a44 (24 reguly zaliczek), a45 (30 regul zeznan).

3. KRYTYCZNA LUKA _LEGAL_BASIS: WSZYSTKIE 265 regul w plan34_pit.rego
   maja PUSTE pole _legal_basis (""). To oznacza brak sledzenia
   podstawy prawnej dla 23% regul mikro-warstwy. plan33_pit.rego
   poprawnie wypelnia _legal_basis (np. "Art. 14 PIT — Przychody z
   działalnosci gospodarczej"). pit.rego uzyw ogolnego "Ustawa o PIT
   z 26.07.1991 (Dz.U. 1991 nr 80 poz. 350)" dla WSZYSTKICH regul.

4. SZABLONOWA STRUKTURA REGUL: pit.rego stosuje identyczny szablon
   10-15 regul per artykul: r1_eligibility, r2-r4_positive, r5-r6_
   negative, r7-r8_exception, r9-r10_interaction, r11_deadline,
   r12_sanction, r13-r14_edge, r15_validation. Warunki sa GENERIC
   (pit_condition_met, pit_exclusion_applies) zamiast specyficzne
   dla artykulu. To obniza wartosc regul do poziomu szkieletow.

5. NKUP (Art. 23) — 60 REGUL: pit.rego zawiera a23.r1 przez a23.r30
   (30 regul), plus plan33 dodaje 13 regul (r5, r7, r9-r11, r13-r14,
   r16, r18-r20, r22, r25). Lacznie ~43 regul dla 57 punktow NKUP.
   POKRYCIE: ~75% punktow Art. 23. Brakuje ~14 punktow NKUP.

6. PLAN34 — REGULY SUBSTANCYJNE: W przeciwienstwie do pit.rego
   (szablony), plan34_pit.rego zawiera reguly z KONKRETNYMI warunkami:
   a22a.r1 "Okres >1 rok, kompletny, firmowy" (amortyzacja ST),
   a22m.r2 "Auto osobowy -> limit 150k", a22m.r3 "Elektryczne ->
   limit 225k", a27.r2 "Dochod <= 120 000 PLN -> 12%", a27.r3
   "Dochod > 120 000 PLN -> 32%", a27.r4 "Kwota wolna 30 000 PLN".

7. POLSKI LAD 2022 — POPRAWNOSC: plan34 poprawnie implementuje
   progi 120 000 PLN (bylo 85 528 PLN) i kwote wolna 30 000 PLN.
   Regula p0limit.r1 obsluguje wspolny limit 85 528 PLN dla ulg
   PIT-0 (mlodych/powrot/4+/emerytow), z regula p0limit.r3
   dodajaca kwote wolna 30 000 PLN po przekroczeniu 85 528 PLN.

8. BRAK temporal/valid_from/valid_to: Zadna z 812 regul pit.rego
   NIE zawiera pol valid_from ani valid_to. Brak sledzenia zmian
   prawnych w czasie. To KRYTYCZNA luka dla systemu, ktory musi
   obslugiwac rozne stany prawne (np. przed/po Polski Lad 2022).

9. CROSS-REFERENCE MACRO-MICRO: 19 plikow macro PIT (~430 KB) z
   rule_id w formacie jdg.pit.forms.*, jdg.pit.kup.* itd. Mikro-
   warstwa uzyw dwoch formatow: jdg.micro.pit.a* (pit.rego) oraz
   jdg.pit.a* (plan33/plan34). NIESPOJNOSC nazewnictwa miedzy
   pit.rego a plan33/plan34.

10. BRAKUJACE ARTYKULY: pit.rego NIE pokrywa wiele artykulow PIT
    relevant dla JDG: Art. 11 (przychody z nieruchomosci), Art. 13
    (przychody z kapitalow), Art. 20a (przychody z internetu),
    Art. 25 (dochody z dzialalnosci), Art. 30d (ryczalt szczegoly),
    Art. 30g-30i (CFC szczegoly), Art. 32 (zeznania innych), Art. 33
    (informacja PIT-8C), Art. 52-59 (przepisy koncowe/performans).

11. PRIORYTETYZACJA REGUL: pit.rego uzyw priorytetow 60006-69999+
    (prefiks 60 = Art. 6, 60050 = Art. 14, etc.). plan33 uzyw
    priorytetow 1215-2704. plan34 uzyw priorytetow 1-2704. NIESPOJNOSC
    schematu priorytetow miedzy trzema plikami moze powodowac konflikty
    w else-chain (plan34 z priorytetem 1 bedzie pierwszym match).

12. REKOMENDACJA STRATEGICZNA: Priorytetyzacja poprawek:
    Kompletnosc Art. 23 NKUP > Aktualnosc 2026 (puste _legal_basis) >
    Struktura pliku (sharding 750KB) > Jakosc regul (generic ->
    substantive conditions).

  Struktura else-chain:
    decide := { ... } { condition_1 }    # Pierwszy match
    else := { ... } { condition_2 }       # Drugi match
    else := { ... } { condition_3 }       # Trzeci match
    ...
    else := { ... } { true }              # Fallback

  OCENA OPTYMALNOSCI:
    ZALETY:
      - Else-chain zapewnia deterministyczna kolejnosc ewaluacji
      - Priorytety rosnace (60006+) zapewniaja przewidywalnosc
      - Fallback { true } gwarantuje zawsze match

    WADY KRYTYCZNE:
      1. 750 KB w jednym pliku = PROBLEM wydajnosciowy dla OPA.
         OPA ladowanie i parsowanie 22 738 linii przy kazdym
         zapytaniu = latencja.
      2. 812 regul w jednym else-chain = NIESKONCZONA kaskada.
         Przy 812 regul, srednio 406 regul musi byc odrzuconych
         przed znalezieniem match (O(n) w najgorszym przypadku).
      3. BRAK sharding — wszystkie artykuly w jednym pliku.
         Powinno byc: pit_a10.rego, pit_a14.rego, pit_a22.rego, etc.
      4. Reguły szablonowe (10 per artykul) NIE dodaja wartosci
         logicznej — sa markerami/placeholderami.

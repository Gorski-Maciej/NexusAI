SEKCJA 1: AUDYT ARCHITEKTURY MULTI-PASS
════════════════════════════════════════════════════════════════════════════════

1.1 STRUKTURA PASS-ÓW (ADR-001)
─────────────────────────────────
INPUT → PASS 0: RISK → PASS 1: ROUTING → PASS 2: COMPLIANCE →
PASS 3: CROSSBORDER → PASS 4: VAT → PASS 5: PIT →
PASS 6: ALLOWANCES → PASS 7: ACCOUNTING → PASS 8: ZUS+BUSINESS+

Każdy PASS może zwrócić BLOCK_AND_ALERT → gated_abort_verdict (early abort).
Implementacja w main_jdg.rego: 3 gates (risk BLOCK, routing BLOCK, i pełny łańcuch).

1.2 SAFE MERGE (INV-018/042)
─────────────────────────────
Trzy przypadki safe_merge:
1. a.immutable_verdict=true → zwróć a (chronione)
2. b.immutable_verdict=true → object.union(b, a) (b wygrywa)
3. Brak immutable → object.union(a, b) (a wygrywa)

Immutable verdict allowlist:
  jdg.zus, jdg.zus.sickness_benefits, jdg.zus.enterprise_benefits,
  jdg.zus.health_contribution, jdg.business, jdg.security.fortress

1.3 FINAL VERDICT CHAIN (80+ iteracji)
───────────────────────────────────────
final_verdict = final_verdict_enforced
  = safe_merge(final_verdict_enforcement, final_verdict_post_merge)
  = safe_merge(runtime_invariants.enforce(p80), safe_merge({_routing_context}, p80))

Chain: p01→p02→p03→...→p24→p25→p26→...→p42→p43→...→p80

1.4 SHARDED ROUTER v7.0
────────────────────────
routing_context := {tax_form, transaction_type, entity_status, 
  evaluation_quarter, evaluation_date, is_cross_border, has_employees,
  is_vat_payer, requires_ksef}

Trzy ścieżki:
• gated_abort_verdict (risk/routing BLOCK)
• sharded_sale_verdict (DOMESTIC_SALE + ACTIVE)
• sharded_purchase_verdict (DOMESTIC_PURCHASE + ACTIVE)
• full_final_verdict (cross-border / non-ACTIVE)

1.5 WCZYTAANE PAKIETY (200+ importów)
──────────────────────────────────────
Liczba pakietów w _package_decisions: 200+
Liczba pakietów w full_final_verdict: ~93 core + ~38 enterprise = ~131
Liczba iteracji final_verdict: 80+ (p01→p80)

SEKCJA 2: SHARDED ROUTER — ANALIZA I WDROŻENIE
════════════════════════════════════════════════════════════════════════════════

2.1 KONTEKST ROUTINGU
─────────────────────
routing_context buduje hash kontekstu z:
• tax_form: SCALE/LINEAR/LUMP_SUM/TAX_CARD
• transaction_type: DOMESTIC_SALE/DOMESTIC_PURCHASE/CROSS_BORDER_SALE/EXPORT/IMPORT
• entity_status: ACTIVE/SUSPENDED/IN_SUCCESSIO/UNREGISTERED
• evaluation_quarter: 1-4 (z daty ewaluacji)
• is_cross_border: true/false (vendor/delivery/service country != PL)
• has_employees: boolean
• is_vat_payer: boolean
• requires_ksef: boolean (od 2026-02-01)

2.2 DECYZJA ROUTINGU (selected_final_verdict)
──────────────────────────────────────────────
if risk.BLOCK → gated_abort_verdict
else if routing.BLOCK → gated_abort_verdict
else if DOMESTIC_SALE + ACTIVE → sharded_sale_verdict (~50 safe_merge)
else if DOMESTIC_PURCHASE + ACTIVE → sharded_purchase_verdict (~50 safe_merge)
else → full_final_verdict (~93 safe_merge)

2.3 REDUKCJA LATENCY
────────────────────
Typowa transakcja krajowa: ~50 pakietów zamiast ~131 → redukcja ~62%
Estymowany spadek latency: ~28s → ~10-12s dla DOMESTIC_SALE

SEKCJA 10: GENIALNE POMYSŁY ENTERPRISE (12 INNOWACJI)
════════════════════════════════════════════════════════════════════════════════

10.1 SELF-ADAPTING ORCHESTRATOR (INN-01)
─────────────────────────────────────────
Automatyczna regulacja głębokości łańcucha safe_merge na podstawie
historii ewaluacji. Transakcje niskiego ryzyka → krótszy łańcuch.
Metryka: rolling window 100 ewaluacji, adaptive depth 30-93.

10.2 HOT-RELOAD GRADUAL (INN-02)
─────────────────────────────────
Zmiana reguły → shadow deployment (5%) → shadow comparison →
100% → monitoring 24h → status "ZMIANA WDROŻONA".
MTTR ≤ 5 min, fail-closed.

10.3 FORECASTING ENGINE (INN-03)
─────────────────────────────────
Predykcja zmian progów/stawek na podstawie:
• Historycznych zmian prawa (10 lat)
• Wskaźników makro (CPI, PKB, kurs EUR/PLN)
• Harmonogramu RMK (Reverse Monitoring Mechanism)

10.4 CROSS-DOMAIN INTELLIGENCE (INN-04)
────────────────────────────────────────
Graf zależności między domenami:
• VAT ↔ PIT (proporcja odliczenia)
• ZUS ↔ PIT (składka zdrowotna vs odliczenie)
• KSeF ↔ VAT (fakturowanie → deklaracja)
Automatyczne wykrywanie konfliktów międzydomenowych.

10.5 CONFIDENCE PROPAGATION (INN-05)
─────────────────────────────────────
Pewność OCR propagowana przez łańcuch decyzyjny:
fc_final = min(fc_vat_rate, fc_vendor_nip, fc_amount, fc_date)
Niska pewność → TRIAGE_QUEUE (nie BLOCK bez powodu).

10.6 DEAD RULE DETECTOR (INN-06)
──────────────────────────────────
Automatyczne wykrywanie reguł, które nigdy nie matchują:
• Zero matchów w ostatnich 10 000 ewaluacjach
• Zero odwołań w innych regułach
• Alert: "Potencjalnie martwa reguła — przeanalizuj usunięcie"

10.7 TEMPORAL SNAPSHOT ENGINE (INN-07)
───────────────────────────────────────
Routing epok prawnych: pre-2019, 2019-2021, 2022-H1, 2022-H2,
2023-2025, 2026+. Bundle OPA per epoka → szybki time-travel.

10.8 ADAPTIVE PRIORITY ENGINE (INN-08)
───────────────────────────────────────
Efektywny priorytet = bazowy + waga_ryzyka + waga_historyczna + waga_temporalna.
Dynamiczne przeliczanie per ewaluacja (Python bridge).

10.9 MERKLE PROOF CACHE (INN-09)
─────────────────────────────────
Cache werdyktów z dowodem integralności Merkle:
input_hash → verdict + proof → weryfikacja integralności.
Zapobiega podmianie cache'u.

10.10 KILL-SWITCH & FEATURE FLAGS (INN-10)
────────────────────────────────────────────
Per-pakietowy kill-switch: jika pakiet generuje >20% błędów,
automatyczne wyłączenie na TTL 5 min + fallback.
Feature flagi: control plane → Rego data.

10.11 GRAPH DEPENDENCY ANALYZER (INN-11)
─────────────────────────────────────────
Analiza zależności import↔export per pakiet.
Wykrywanie cyklicznych zależności (fail-closed).
Wizualizacja grafu (Mermaid).

10.12 PROVENANCE CERTIFICATE (INN-12)
──────────────────────────────────────
Pełny certyfikat provenance z:
• decision_hash (SHA-256)
• bundle_version + rule_version + threshold_version
• evaluation timestamp
• operator signature (HSM)
Gotowość pod pieczęć kwalifikowaną (eIDAS).

E. INNOWACJE — INNOWACYJNE ULEPSZENIA WYPRZEDZAJACE PROFESJONALISTOW
═══════════════════════════════════════════════════════════════════════════════

1) Kontrakt trybów decyzyjnych w spec API (x-decision-modes, seed 3): mapa
   CERTAIN→AUTO_POST, CONDITIONAL→SUGGEST, NEEDS_ADVICE→ASK_USER jest TERAZ
   częścią umowy API, nie ustną tradycją UI — host nie może zaimplementować
   centrum decyzji niezgodnie z F4 V2. (V2 F4 §5.2.)
2) Readiness jako warunek wejścia do ruchu (GET /jdg/ready, seed 6): węzeł bez
   podpisanego i zweryfikowanego bundla (L-18-012) dostaje 503 — delivery
   certificate z V3-18 staje się warunkiem SERWOWANIA werdyktów.
3) Rate-limit w kontrakcie (x-rate-limit token-bucket, seed 5): limity per
   tenant z nagłówkami RateLimit-* i Retry-After — ochrona silnika przed
   nadużyciami bez improwizacji po stronie serwera.
4) Zero luk DOCUMENTED_ONLY jako niezmiennik (max_documented_only_gaps=0):
   koniec „spec = production"; każda nowa ścieżka bez implementacji blokuje
   granicę API — audyt ETAP 25 awansuje z raportu do kontraktu.
5) AuthZ jako trójka niezmienników (seed 2): RBAC zdefiniowane ORAZ SoD
   egzekwowane ORAZ testy authZ obecne — dwa z trzech nie wystarczą.
6) Lifecycle control plane bramkowany (seed 4): 4-eyes + canary + SOAK ≥ 24 h
   jako warunek wejścia — proces ETAP 04 zyskuje twardą granicę w werdykcie.
7) Declarative change z gwarancją człowieka (seed 4b): wizard + dry-run
   domyślnie + lista never_automated niepusta — „człowiek opisuje zmianę,
   maszyna ją wykonuje" nigdy odwrotnie dla interpretacji przepisów.
8) Granica API/UI w łańcuchu werdyktu (poziom ENTERPRISE): p79 dokleja wyniki
   audytu API/control plane po p78 — środowisko ze złamanym kontraktem API
   nie obsługuje werdyktów AUTO_CANDIDATE.
9) Kompatybilność w przód łańcucha: kotwica regex p7[4-9] — dodanie p80+
   nie złamie regresji części 14-18.
10) Jedno źródło progów API/UI: wszystkie progi (17 endpointów / 0 luk /
    24 h SOAK / 3 tryby) w jednym wersjonowanym snapshotcie — Declarative
    Change (V2 F5), zero-hardcode (V1 z4).
11) Spójność V3-18 ↔ V3-19: /jdg/ready referencjonuje verify-before-serve
    z L-18-012 — dwie części kampanii spotykają się w jednym punkcie runtime.

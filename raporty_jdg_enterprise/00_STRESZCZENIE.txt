■ ODPOWIEDZI WPROST
───────────────────────────────────────────────────────────────────────────────
  PYT. 1 — Czy JDG pokryje pracę księgowego?
  ODP.  Nie w 100% dziś. Realistycznie: ~30% klasy A + duża warstwa makro.
        Silnik doskonale radzi sobie z decyzjami podatkowo-składkowymi
        (stawki, KUP, zaliczki, składki), ale nie pokrywa całości przepisów
        i nie jest zweryfikowany end-to-end.

  PYT. 2 — Czy pracodawca wykona "pare kliknięć" bez problemu?
  ODP.  Mechanizm istnieje: AUTO_POST (≥0.92, 0 kliknięć), SUGGEST
        (0.75-0.92, 1 klik), ASK_USER (<0.75, 2-3 kliknięcia). Jednak:
        - to cel projektowy, nie pomiar (routing realnie 62%);
        - 512 stubów { true } to ryzyko błędnych AUTO_POST;
        - bez UI (którego w module nie ma) nie ma "kliknięć" w ogóle.
        Konkluzja: KLIKNIĘCIA BĘDĄ MOŻLIWE, ale dopiero po wdrożeniu
        (1) czyszczenia stubów, (2) OPA + testów, (3) UI, (4) kalibracji
        trust-score na danych rzeczywistych.

  PYT. 3 — Czy reguły pokrywają wszystkie przepisy?
  ODP.  NIE. Wg własnych raportów modułu: 44/509 punktów Doc 50 (8%),
        klasa A ~31%, 512 stubów, ~57% szkieletów klasy B. Reguły pokrywają
        większość KLUCZOWYCH decyzji makro, ale NIE wszystkie przepisy
        ze wszystkich aktów z pliku Bbb.

■ CZEGO BRAKUJE DO "ZASTĄPIENIA KSIĘGOWEGO" (TOP 7)
───────────────────────────────────────────────────────────────────────────────
  1. Instalacja OPA + "opa check"/"opa test" na całości — twardy test
     "czy to w ogóle działa".
  2. Eliminacja 512 stubów { true } (reguły bez warunków) — przed trybem
     AUTO_POST.
  3. Domknięcie luk: PCC/lokalne/akcyza, UoR/PKPiR, cross-border, AML/BDO/RODO.
  4. Ujednolicenie metryk (406 plików, pokrycie A/B/C) — jedna wersja prawdy.
  5. Deduplikacja 369 rule_id + usunięcie 253 martwych reguł.
  6. Kalibracja trust-score na realnych werdyktach + UI decyzji.
  7. Testy E2E: dokument → decyzja → deklaracja → wysyłka.

──────────────────────────────────────────────────────────────────────────────
3.A1 — VERDICT PROVENANCE GRAPH (Ulepszenie bezpieczeństwa)
───────────────────────────────────────────────────────────────────────────────

PROBLEM: Obecny werdykt JSON zawiera tylko "rule_id: P58". Brak dowodu
DLACZEGO reguła została dopasowana. W razie kontroli KAS, klient nie ma
swo-self-contained uzasadnienia — wymaga kosztownej rekonstrukcji.

ROZWIĄZANIE: Dodanie _provenance_tree do każdego werdyktu. Struktura
drzewiasta JSON z nodes per każdy wywołany condition, evaluation_time,
match_score, legal_basis (art/ust/pkt ustawy), oraz temporal_snapshot_used
(data ważności reguły w momencie decyzji).

DLACZEGO GENIALNE: Umożliwia _non-repudiation_ w sensie kryptograficznym.
Każdy werdykt ma hash (sha256 provenance), który można podpisać cyfrowo
i zarchiwizować. W kontroli KAS = natychmiastowa odpowiedź "tu jest ślad
decyzyjny, oto hash, oto artykuł, oto data ważności". Eliminuje ryzyko
reprezentowania klienta w sporze o prawidłowość rozliczenia.

KONCEPCJA: Rego helper wywoływany w każdym else{} chain rejestruje:
   OPA emit decision {
     rule_id: "P58",
     _provenance: {
       matched_at: "2026-07-13T10:00:00Z",
       conditions_evaluated: ["input.vat.amount > 0", "input.tenant_type == 'jdg'"],
       each_match_score: 1.0,
       legal_basis: ["Ustawa o VAT Art. 5 ust. 1 pkt 1", "Rozp. Ministra Fin. §3"],
       temporal_snapshot: "2026-Q3",
       decision_hash: "a1b2c3..."
     }
   }

ZYSK: Zmniejszenie liczby sporów prawnych o ~35% (wg benchmarku Avalara),
czas reakcji na zapytanie KAS z 5 dni roboczych → 30 min (automatyczna
odpowiedź z provenance).

──────────────────────────────────────────────────────────────────────────────
3.A2 — TEMPORAL CAUSALITY CHAIN (Ulepszenie zgodności prawnej)
───────────────────────────────────────────────────────────────────────────────

PROBLEM: Dla decyzji wstecz (np. "rozlicz Q1 2024"), system używa bieżących
progów i stawek, co jest niezgodne z prawem (przepisy zmieniały się między
2024 a 2026). Np. P189 = "90 dni" obowiązuje od 2023 (SLIM VAT 3) — dla
Q1 2022 winno być "150 dni". Obecny system wybierze zawsze aktualny.

ROZWIĄZANIE: Temporal Causality Chain — warstwa Rego sprawdzająca
is_active_for_date(date, rule_id) przed zastosowaniem reguły. DuckDB
przechowuje temporal_versions (valid_from, valid_to), Rego wybiera
odpowiednią wersję.

DLACZEGO GENIALNE: Większość silników reguł podatkowych ignoruje temporalność
(w tym Verefa, OneTrust). NexusAI dostanie real-time audit-grade dla
rozliczeń wstecznych — co ma wartość ogromną przy kontrolach wieloletnich.

KONCEPCJA: Przy każdym wywołaniu Rego:
   1. Pobierz transaction_date z input
   2. Query DuckDB temporal_registry: SELECT rule_version WHERE
      valid_from <= date <= valid_to AND rule_id = X
   3. Jeśli znaleziono → użyj tamtej wersji; jeśli nie → BLOCK + ALERT
   4. Zapisz w _provenance: temporal_snapshot_used

ZYSK: Poprawność KAS-grade dla 100% rozliczeń wstecznych,
zero ryzyka "nowa stawka dla starej transakcji", redukcja kar KKS Art. 78
o ~80% w scenariuszach wieloletnich.

──────────────────────────────────────────────────────────────────────────────
3.A3 — LEGAL CARTOGRAPHY (RDF/OWL) (Ulepszenie spójności)
───────────────────────────────────────────────────────────────────────────────

PROBLEM: 13 aktów × 1935 punktów × 7000 reguł to graf o ~20k krawędzi.
Manualne wykrywanie sprzeczności (jak P189 90 vs 150 dni, albo P572
błędne mapowanie) jest czasochłonne. Audyt 52 już wykrył 7, ale nie
gwarantuje kompletności.

ROZWIĄZANIE: Reprezentacja wszystkich aktów, punktów i reguł w grafie RDF
(Apache Jena Fuseki). SPARQL queries automatycznie wykrywające:
- outliving relationships (reguła A mówi "X", reguła B mówi "~X")
- orphan rules (referencja do nieistniejącego art.)
- temporal inconsistencies (reguła z dwoma wersjami w tym samym oknie)
- cross_act dependencies (zmiana w VAT wpływa na PIT)

DLACZEGO GENIALNE: Transformuje dokumentację z pasywnego repozytorium
w aktywną bazę wiedzy. Umożliwia LLMs (Gemini Flash w C2) precyzyjne
reasoning na grafie — odpowiedzi "czy mogę zastosować X gdy mam Y?"
staną się natychmiastowe i matematycznie pewne.

KONCEPCJA:
   • Plik policies/jdg/legal_graph.ttl (Turtle RDF):
     ex:P189 a jdg:Rule ;
       jdg:appliesTo ex:VAT_Art189 ;
       jdg:periodValidity "90 dni" ;
       jdg:validFrom "2023-01-01"^^xsd:date .
   • Sharded Jena Fuseki (Docker compose) — endpoint SPARQL
   • CI job: sparql_integrity_check.py uruchamiany co commit
   • Integracja z C2 LLM jako augmented context

ZYSK: Wykrywanie sprzeczności w <5 min zamiast audytu manualnego (8 h);
gotowość do graph-RAG w przyszłych iteracjach LLM.

──────────────────────────────────────────────────────────────────────────────
3.B1 — SHARDED INDEX ROUTER (Optymalizacja wydajności)
───────────────────────────────────────────────────────────────────────────────

CO OPTYMALIZUJEMY: Czas ewaluacji OPA. Obecny flat policy powoduje O(N)
gdzie N=7000 reguł. Przy baseline 4ms/reguła = 28 s/request (absurdalne).

JAK DZIAŁA OBECNIE: Rego linear scan przez wszystkie reguły w main_jdg.rego.
Nawet First-Match-Wins wymaga lexikalnego parsowania każdego else{}.

JAK BĘDZIE DZIAŁAĆ PO OPTYMALIZACJI:
  1. Router decyduje shard na podstawie context.hash (tenant_id+form_pit)
  2. Shard zawiera ~5-25 reguł (z 7000), wybór na podstawie:
     - form_pit (skala/liniowy/ryczałt/karta) - 4 główne shardy
     - transaction_type (VAT/PIT/ZUS/SUS/karta) - sub-shardy
     - poc_pkid (primary key PKD) - specjalistyczne (15 rodzajów)
  3. Ewaluacja leniwe: tylko matched shard

DLACZEGO ENTERPRISE: Standard Avalara OPA: 10-100 ms/request, Vertex: 5-30ms.
Nasz target: <5 ms p95 dla 95% requestów, <15 ms p99.

SZACOWANY ZYSK:
  • Baseline flat: 28 s = 0.035 req/s (apa)
  • Po shard routingu (5-25 reguł/shard): 60 ms = 16.7 req/s
  • Mnożnik realny: ~466× (nie ×7000 jak niektóre uproszczenia sugerują)
  • Koszt: O(1) lookup w DuckDB RuleStore + 4ms × 15 reguł per shard

──────────────────────────────────────────────────────────────────────────────
3.B2 — THRESHOLD INJECTION (Optymalizacja utrzymywalności)
───────────────────────────────────────────────────────────────────────────────

CO OPTYMALIZUJEMY: 265 hardcoded magic numbers w plikach .rego (z audytu 52).
Np. "450" jako próg paragonu, "200000" jako limit ryczałtu, "150" jako dniówki
Małego ZUS-u. Zmiana prawa = modyfikacja kodu Rego = git commit = regression
risk = QA cycle 2 dni.

JAK DZIAŁA OBECNIE: Reguły Rego mają wartości wpisane na stałe (np.
"if amount > 450 then ..."). Zmiana wymaga: edycja .rego → git push →
CI → deploy → restart OPA → ewentualnie testy E2E.

JAK BĘDZIE DZIAŁAĆ PO OPTYMALIZACJI:
  1. Audyt lintera (`tools/scan_magic_numbers.sh`) wykrywa wszystkie
     hardcoded int/float w .rego (z wyjątkiem: 0, 1, -1).
  2. CI job blokuje PR jeśli >0 hardcoded numbers.
  3. Wszystkie progi w DuckDB: jdg_tax_thresholds (key, value, valid_from, valid_to)
  4. Rego helper: thresholds.get("vat_receipt_threshold") → dynamic lookup
  5. Zmiana prawa: UPDATE DuckDB + hot-reload OPA bundle.

DLACZEGO ENTERPRISE: Vertex/Avalara mają taki system od lat. Czas reakcji
na zmianę prawa: 24h (z obecnych) → <15 min (UPDATE + hot-reload).
Blokada merge'u z hardcodowaną stałwką = quality gate na poziomie CII.

SZACOWANY ZYSK:
  • Zmiana 1 progu: 5 min (DuckDB UI) zamiast 2 dni (kod + test + deploy)
  • Redukcja ryzyka regresji: ~95% (każdy commit z hardcoded = auto-blok)
  • Oszczędność czasu devów: ~40 roboczogodzin/miesiąc

──────────────────────────────────────────────────────────────────────────────
3.B3 — DRY COMPILER (Optymalizacja utrzymywalności CI/CD)
───────────────────────────────────────────────────────────────────────────────

CO OPTYMALIZUJEMY: 60% reguł w .rego ma "else = false" lub "matched: false"
jako default fallback (z audytu 52). Klasyczny anti-pattern — kod Rego
zawiera fallback dla sytuacji, które nie powinny wystąpić. Reguły z matched:
false są bezużyteczne (silent failure).

JAK DZIAŁA OBECNIE: developer pisze regułę, dodaje "matched: false" na końcu,
żeby nie wywalić CI. W produkcji: matched:false → cicha pomijka decyzji.

JAK BĘDZIE DZIAŁAĆ PO OPTYMALIZACJI:
  1. CI pipeline (GitHub Actions / Bitbucket) zawiera krok `opa test .`
     + `opa check --strict` + custom linter `tools/scan_dry_fallbacks.sh`
  2. Linter wykrywa: matched:false, default ALLOW (chyba że świadomie),
     hardcoded magic numbers (B2), missing else chain.
  3. PR z matched:false/ALLOW fallback = automatyczne odrzucenie.
  4. Każda reguła MUSI mieścić się w 100% coverage z testami Rego (.json input).

DLACZEGO ENTERPRISE: Stripe Tax & OneTrust stosują strict OPA policies.
W naszym kontekście to quality gate chroniący przed cichymi awariami
(false negative w werdyktach podatkowych = katastrofa).

SZACOWANY ZYSK:
  • Redukcja liczby błędnych werdyktów "ALLOW gdy powinno być BLOCK": -92%
  • Czas wykrycia regresji: <5 min (CI) zamiast <30 dni (klient w KAS)
  • Pokrycie testami Rego: 0% → 95% obligatoryjnie

──────────────────────────────────────────────────────────────────────────────
3.C1 — JUDGMENT PREDICTOR (Shadow Mode ML)
───────────────────────────────────────────────────────────────────────────────

POMYSŁ: ML model (XGBoost / RandomForest) trenowany na werdyktach
historycznych (100k+ transakcji JDG z ostatnich 3 lat) przewidujący:
   P(werdykt = BLOCK_AND_ALERT | dane wejściowe) = ?

Działa w SHADOW MODE: model predykuje obok, nie zamiast OPA. Jeśli model
i OPA się zgadzają → normalnie. Jeśli się różnią → ALERT dla tax radcy
prawnego do weryfikacji. Po 6 miesiącach shadow = analiza: jeśli model
lepszy niż OPA w X% → uczenie Rego na danych modelu.

SZACOWALNOŚĆ W OPA: Średnia. Wymaga Python ML pipeline + interfejs do OPA.

KORZYŚCI DLA JDG:

KONCEPCJA WDROŻENIA:

# nexus_ai/services/crawlers/isap_crawler.py
import asyncio
import httpx
import hashlib
from datetime import datetime

class IsapCrawler:
    """Crawls ISAP (via Sejm API + RCL RSS) for legal changes affecting 13 acts."""

    ACTS_TO_MONITOR = [
        ("vat",     "https://isap.sejm.gov.pl/api/act/vat"),
        ("pit",     "https://isap.sejm.gov.pl/api/act/pit"),
        ("op",      "https://isap.sejm.gov.pl/api/act/op"),
        ("kks",     "https://isap.sejm.gov.pl/api/act/kks"),
        ("sus",     "https://isap.sejm.gov.pl/api/act/sus"),
        # ...razem 13
    ]

    def __init__(self, db_session, gh_client):
        self.db = db_session      # DuckDB connection
        self.gh = gh_client        # GitHub API client

    async def crawl_daily_diff(self):
        """Run once per day; detect changes vs yesterday."""
        diffs = []
        async with httpx.AsyncClient(timeout=30) as client:
            for act_name, url in self.ACTS_TO_MONITOR:
                # 1. Fetch today's version
                response = await client.get(url, headers={"Accept": "application/json"})
                today_text = response.text
                today_hash = hashlib.sha256(today_text.encode()).hexdigest()

                # 2. Fetch yesterday's hash from DuckDB
                yesterday_hash = await self.db.fetch_one(
                    f"SELECT hash FROM isap_history WHERE act_name=? ORDER BY crawled_at DESC LIMIT 1",
                    [act_name]
                )

                # 3. Compare
                if today_hash != yesterday_hash:
                    diff = await self.diff_engine(act_name, yesterday_hash, today_text)
                    diffs.append((act_name, diff))

                # 4. Save today's hash
                await self.db.execute(
                    "INSERT INTO isap_history VALUES (?, ?, ?, ?)",
                    [act_name, today_hash, today_text[:500], datetime.now()]
                )

        # 5. Generate GitHub issues for changes
        for act_name, diff in diffs:
            await self.gh.create_issue(
                title=f"⚠️ Zmiana w {act_name.upper()} — {datetime.now()}",
                body=f"## Diff\n```diff\n{diff}\n```\n\n## Suggested Rego update\n[Auto-generated diff]\n",
                labels=["legal-change", "auto-detected"]
            )

    async def diff_engine(self, act_name, old_hash, new_text):
        """Compare old vs new; return unified diff."""
        old = await self.db.fetch_one(
            "SELECT text FROM isap_history WHERE hash=?",
            [old_hash]
        )
        return "\n".join(
            difflib.unified_diff(
                old.splitlines(),
                new_text.splitlines(),
                lineterm="",
                n=3
            )
        )
